# ADR-146: UI Page Bases and the List Shell (Bases Own Plumbing, Pages Own Model and Service Call)

## Status
Accepted (2026-11-12). Released in MMCA.Common v1.289.0 (`MMCA.Common/CHANGELOG.md:7`, entries at `:38` to `:41`); the adopting pages are in MMCA.ADC and MMCA.Store.

## Context

An admin create form and an admin list page in a consumer are mostly plumbing that is the same on every page: a page-scoped cancellation source and its dispose method, a dirty flag for the unsaved-changes guard, the failed save `Result` kept for the error summary, a submit sequence (validate, pre-check, save, clear the dirty flag, navigate, always end the saving state), the delegate that feeds the phone list, and the list chrome (header, cancel-loading button, search row, grid or phone list, empty and failure content, pager, delete confirmation). Both production consumers, MMCA.ADC and MMCA.Store, carry these pages, so a fix to any of those steps written into the page itself lands page by page in two repos.

The cost is visible in what a consumer deletes when a create form moves onto the base: `_cts`, `IsSaving`, `_isDirty`, `MarkDirty`, `_saveResult`, `_form`, the injected `IToastService` and the `Dispose` methods, plus the hand-written submit body (`MMCA.Common/UPGRADING.md:122-125`). The detail page already had a base that owned its cancellation and edit lifecycle (`MMCA.Common/Source/Presentation/MMCA.Common.UI/Pages/Common/DetailPageBase.cs:7-27`), and the list page already had `DataGridListPageBase<TDto>` owning paging, filter, sort and loading state (`MMCA.Common/Source/Presentation/MMCA.Common.UI/Pages/Common/DataGridListPageBase.cs:24`); the create form had no base and the list markup had no shared component.

This ADR builds on [ADR-067](067-ui-module-shell-composition.md) (the shared Blazor shell and `IUIModule` composition the pages live in), [ADR-056](056-blazor-render-mode-strategy.md) (the render-mode transitions the page token cancels across), [ADR-094](094-client-entity-data-access.md) (the client services a page calls), [ADR-013](013-result-pattern.md) (the `Result` a save returns), [ADR-063](063-accessibility-conformance-gate.md) (the accessibility contract the row link serves) and [ADR-015](015-architecture-fitness-functions.md) (rule bodies shipped once in `MMCA.Common.Testing.Architecture` and subclassed per repo).

## Decision

**MMCA.Common.UI provides the page plumbing as bases and components. A consumer page declares its model and its service call and inherits the rest.**

### The shared cancellation base

`CancellablePageBase` (`MMCA.Common/Source/Presentation/MMCA.Common.UI/Pages/Common/CancellablePageBase.cs:16`) owns one page-scoped `CancellationTokenSource` (`:18`) and exposes it as `PageToken` (`:27`), which returns an already-cancelled token after dispose instead of throwing (`:22-26`). `Dispose(bool)` cancels and disposes the source exactly once (`:41-55`); a page with further disposables overrides it and calls the base (`:12-15`). Both `DetailPageBase` (`DetailPageBase.cs:27`) and `CreatePageBase` (`CreatePageBase.cs:21`) derive from it, so the create and detail pages share one cancellation contract. `DetailPageBase` adds the route-load guard and load state on top (`DetailPageBase.cs:34`, `:41`).

### The create-page base and its submit sequence

`CreatePageBase` (`MMCA.Common/Source/Presentation/MMCA.Common.UI/Pages/Common/CreatePageBase.cs:21`) owns the injected `Toast` (`:24`), the `Form` the page binds with `@ref="Form"` (`:27`), `IsSaving` (`:30`), `IsDirty` (`:33`), `SaveResult` (`:36`) and `MarkDirty()` (`:39`). The page still writes its model, its fields (the adopters render a sibling `*FormFields` component and pass it `OnFieldChanged="MarkDirty"`, as in `MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Sponsors/SponsorCreate.razor:26-27` and `MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerCreate.razor:28-29`), its `UnsavedChangesGuard` and `ErrorSummary` markup, and one `SubmitAsync` call carrying its service call and its success step (`:15-20`).

`SubmitAsync<TCreated>(saveAsync, onCreated, options)` (`:53-56`) runs a fixed sequence:

1. It returns `false` when there is no form or a save is already in flight (`:61-64`).
2. It clears `SaveResult` and validates the form; an invalid form raises a warning toast with `ErrorMessages.ValidationError` and stops (`:67-73`).
3. It runs the optional pre-check; a non-null message is shown as a warning toast and stops the submit (`:75-80`).
4. It sets `IsSaving`, calls the page's `saveAsync` with `PageToken` (`:82-85`).
5. On success it clears `SaveResult`, clears `IsDirty` BEFORE calling `onCreated`, so the guard does not block the navigation the success step performs, and returns `true` (`:86-91`).
6. On failure it keeps the result in `SaveResult` for the error summary and, unless told not to, raises the composed failure toast through `NotifyOnFailure` (`:94-100`).
7. A cancellation returns `false` (`:102-105`), and `IsSaving` is always reset in `finally` (`:106-109`).

`CreateSubmitOptions` (`MMCA.Common/Source/Presentation/MMCA.Common.UI/Pages/Common/CreateSubmitOptions.cs:8`) is the per-call options record: `PreCheck`, a `Func<string?>` that returns a warning to stop or `null` to continue (`:14`); `ToastOnFailure`, defaulting to `true` (`:20`); and `Localizer`, passed to `NotifyOnFailure` (`:26`).

A consumer create page is then one call. MMCA.Store's customer form submits through it (`MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerCreate.razor.cs:52`), and MMCA.ADC's sponsor form passes a pre-check for a missing event (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Sponsors/SponsorCreate.razor.cs:82`, `:92`).

### The list-page base: the before-fetch hook and the phone fetcher

`DataGridListPageBase<TDto>` gains two members.

- `OnBeforeFetchAsync(CancellationToken)` is a virtual hook that does nothing by default (`DataGridListPageBase.cs:792`). Every loader of the base and every delegate `MobilePageFetcher` builds awaits it before building the filter bag (the one exception is the persisted pre-render shortcut, which returns its cached rows without calling the hook, `:790`, `:869-883`), so a page that must wait for state its filter callback reads (a picker's options) writes the wait once instead of at the top of each fetch method (`:779-784`). MMCA.ADC's event-filtered list base overrides it to wait for the events list (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Common/EventFilteredListPageBase.cs:213`).
- `MobilePageFetcher(fetchAsync, additionalFilters, defaultSortColumn, defaultSortDirection, afterFetchAsync)` (`DataGridListPageBase.cs:816-822`) turns the grid's fetch delegate plus its filter callback into the phone list's page delegate, so one fetch method and one filter callback serve both. The delegate awaits the hook (`:836`), runs the filter callback on a fresh ordinal bag, so grid column filters are never sent (`:800-802`, `:838-839`), maps the sort direction to `"desc"` or `"asc"` only when a sort column is given (`:826-832`), calls the fetch (`:841`), runs the optional after-fetch step only on success (`:842-844`), and returns the `Result` unchanged with no toast and no page state change, because the phone list owns retry and error display (`:810-815`). Adopters: `MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Activities/ActivityList.razor.cs:71`, `MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Sponsors/SponsorList.razor.cs:69`, `MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerList.razor.cs:38`, and a descending sort in `MMCA.Store/Source/Modules/Catalog/MMCA.Store.Catalog.UI/Pages/Reviews/ReviewList.razor.cs:63`.

### The list shell and the row-link cell

`ListPageShell<TItem>` (`MMCA.Common/Source/Presentation/MMCA.Common.UI/Components/Lists/ListPageShell.razor:1`) is the rendering half of an admin list page and holds no paging, filter, sort, loading or persistence state: every such value arrives as a parameter from the page's `DataGridListPageBase` (`:3-6`). It renders the page header with the cancel-loading button while `IsLoading` (`:7-16`), the search row and the page's `Filters` (`:18-31`), the `MobileInfiniteScrollList` fed by `MobileFetch` on a phone (`:33-42`) or a `MudDataGrid` fed by `ServerData` otherwise (`:45-71`), the shared no-records content with retry (`:64`), the pager (`:68`) and the delete confirmation (`:74-77`). The page supplies its columns through `Columns` (`MMCA.Common/Source/Presentation/MMCA.Common.UI/Components/Lists/ListPageShell.razor.cs:103`) and its phone card through `CardTemplate` (`:75`); defaults are `ShowSearch = true` (`:50`), `MobilePageSize = 10` (`:81`), `RowsPerPage = 10` (`:95`), `Dense = true` (`:98`) and `ShowDeleteConfirmation = true` (`:121`).

`RowLinkCell` (`MMCA.Common/Source/Presentation/MMCA.Common.UI/Components/Lists/RowLinkCell.razor:4`) wraps a grid cell's text in a `MudLink` to the row's detail page, in the row's own colour with no underline, so a keyboard, pointer or screen-reader user reaches the record through a real link (`:1-3`). It takes exactly two parameters, the required `Href` (`:8`) and `ChildContent` (`:11`). Adopters: `MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Activities/ActivityList.razor:10` (shell) and `:52` (cell), `MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Sponsors/SponsorList.razor:10` and `:52`. The shell is adopted by MMCA.ADC's nine admin list pages and by six of MMCA.Store's list pages: `CategoryList`, `ProductList` and `ReviewList` in Catalog (`MMCA.Store/Source/Modules/Catalog/MMCA.Store.Catalog.UI/Pages/Categories/CategoryList.razor:10`, `MMCA.Store/Source/Modules/Catalog/MMCA.Store.Catalog.UI/Pages/Products/ProductList.razor:10`, `MMCA.Store/Source/Modules/Catalog/MMCA.Store.Catalog.UI/Pages/Reviews/ReviewList.razor:11`), `CustomerList` in Identity (`MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerList.razor:10`), and `InventoryItemList` and `ShoppingCartList` in Sales (`MMCA.Store/Source/Modules/Sales/MMCA.Store.Sales.UI/Pages/Inventory/InventoryItemList.razor:10`, `MMCA.Store/Source/Modules/Sales/MMCA.Store.Sales.UI/Pages/ShoppingCarts/ShoppingCartList.razor:10`). Each reads the shell's grid as its `GridRef` (`MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerList.razor.cs:23-24`). Five of the six link their cells with `RowLinkCell` (for example `CustomerList.razor:36`, `:41`, `:47`); `ReviewList` uses none. Three pass `ShowSearch="false"` (`CustomerList.razor:13`, `InventoryItemList.razor:13`, `ShoppingCartList.razor:13`), and two of those also pass `ShowDeleteConfirmation="false"` (`InventoryItemList.razor:13`, `ShoppingCartList.razor:13`). Four MMCA.Store `*List.razor` files are not on the shell, each for a reason in the file: `OrderList` swaps its whole body by viewer, cards for a customer and its own `MudDataGrid` and pager for staff, and the shell has no slot for that (`MMCA.Store/Source/Modules/Sales/MMCA.Store.Sales.UI/Pages/Orders/OrderList.razor:24`, grid at `:84`, pager at `:187`); `CustomerOrderList` is a child card component with no route, not a list page (`MMCA.Store/Source/Modules/Sales/MMCA.Store.Sales.UI/Pages/Orders/CustomerOrderList.razor:1-8`); `RoleList` and `UserList` are thin wrappers over the framework's `RoleAdminList` and `UserAdminList` (`MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Roles/RoleList.razor:10`, `MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Users/UserList/UserList.razor:12`).

### The gate

`FormsConventionTestsBase` (`MMCA.Common/Source/Hosting/MMCA.Common.Testing.Architecture/Bases/Ui/FormsConventionTestsBase.cs:30`) is re-run as a thin subclass in each repo. It discovers every `*Create.razor` under the repo's `Source/Modules`, skipping `obj` and `bin`, and fails when fewer than `MinimumCreateForms` are found (`:284-299`, default `1` at `:56`). Two facts hold the convention:

- `AdminCreateForms_InheritCreatePageBase` (`:178-196`) requires each form to derive from `CreatePageBase`: an `@inherits` line naming the base in the markup, or `: CreatePageBase` / `, CreatePageBase` in the code-behind class declaration, with Razor, HTML and C# comments stripped first so a base named only in a comment does not count (`:159-169`, regexes at `:362` and `:365`). It checks the declaration only: nothing in the fact checks that the form calls `SubmitAsync` or has dropped its private members.
- `AdminCreateForms_KeepUnsavedChangesGuardAndValidation` (`:198-215`) requires the ten literal markers of `RequiredMarkers` (`:73-85`), which name the base's members: `IsDirtyAccessor="() => IsDirty"`, `@ref="Form"`, `Result="SaveResult"` and `Messages="Form?.Errors"` among them.

`RequiredMarkers` is virtual, so a repo can override it, but the inheritance fact never reads it: a form that does not declare `CreatePageBase` fails `AdminCreateForms_InheritCreatePageBase` whatever its marker list says, so overriding the markers cannot stand in for declaring the base (`MMCA.Common/UPGRADING.md:135-136`). A form that does declare the base passes that fact even if it keeps its own private plumbing and a hand-written submit (see Trade-offs).

## Rationale

- **One fix lands once.** The submit sequence, the cancellation contract and the list chrome each live in one Common type. A correction to the sequence (for example the order of clearing the dirty flag against navigating, `CreatePageBase.cs:86-91`) reaches every create form in both consumers with the package bump: all nine in MMCA.ADC (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Sponsors/SponsorCreate.razor:8`) and all four in MMCA.Store (`MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerCreate.razor:2`) declare the base. A correction to the list chrome reaches the nine MMCA.ADC admin list pages and the six MMCA.Store list pages on the shell (`MMCA.Store/Source/Modules/Catalog/MMCA.Store.Catalog.UI/Pages/Categories/CategoryList.razor:10`), but not MMCA.Store's `OrderList`, which keeps its own grid and pager (`MMCA.Store/Source/Modules/Sales/MMCA.Store.Sales.UI/Pages/Orders/OrderList.razor:84`, `:187`).
- **The page keeps what differs.** The base takes the service call and the success step as delegates (`CreatePageBase.cs:53-56`) and the shell takes the columns and card as fragments (`ListPageShell.razor.cs:75`, `:103`), so the model, the fields, the client service and the navigation target stay in the page where a reader expects them. This is the same split `DetailPageBase` already used (`DetailPageBase.cs:15-21`).
- **One fetch serves two layouts.** `MobilePageFetcher` reuses the grid's fetch delegate and the page's own filter callback (`DataGridListPageBase.cs:794-797`), so the page's search and filter state reach both layouts through one method. The grid's column filters and its current sort are not shared (see Trade-offs).
- **A test, not a convention document, holds the line.** Per ADR-015 the rule body ships once and each repo subclasses it; the inheritance fact turns "declare the base" into a red build rather than a review comment. Whether the page then uses the base's submit sequence is not tested (see Trade-offs).

## Trade-offs

- **The base fixes the submit sequence.** A page whose sequence differs keeps its own code around or instead of the base call. MMCA.ADC's room form checks its missing-event precondition before calling `SubmitAsync`, so an invalid form with no event gets the specific message rather than the generic validation toast (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Rooms/RoomCreate.razor.cs:70`, then `SubmitAsync` at `:77` with its own `PreCheck` at `:87`).
- **The hook is all-or-nothing per page.** A page whose wait must sit at a different point than the hook keeps its own wait. MMCA.ADC's public sessions list awaits its event scope itself: on the grid path before entering the base loader, so a load superseded during the wait is still tracked (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Public/Sessions/PublicSessionList.razor.cs:225-229`, `:236`), and at the top of its phone fetch (`:343`). Its comment keeps the wait out of `OnBeforeFetchAsync` because a second `EnsureEventScopeAsync` within the same grid load could re-issue a failed lookup (`:337-340`).
- **The phone list does not see the grid's column filters or sort.** The delegate `MobilePageFetcher` builds fills a fresh bag from the page's filter callback only, so grid column filters are never sent (`DataGridListPageBase.cs:800-802`, `:838-839`), and its sort is the fixed default column the page passes in (`:826-832`). The shell turns column filtering on (`ListPageShell.razor:55`) and adopters mark columns filterable (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Activities/ActivityList.razor:50`), so a column filter or a re-sort set on the grid has no counterpart on a phone.
- **The gate checks the declaration, not the use.** `InheritsCreatePageBase` matches an `@inherits` line or a class declaration naming the base (`FormsConventionTestsBase.cs:159-169`), and no fact checks for a `SubmitAsync` call. A form that declares the base but keeps private plumbing and a hand-written submit passes the inheritance fact; only review catches it.
- **The row-link cell takes no extra attributes.** `RowLinkCell` accepts only `Href` and `ChildContent` (`RowLinkCell.razor:8`, `:11`), so a link that needs an `aria-label` stays a plain `MudLink`, as in MMCA.ADC's question list required-flag cell (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Questions/QuestionList.razor:76`).
- **The shell fixes the grid's settings.** `AllowUnsorted="false"`, filtering, hover and striping are set in the shell (`ListPageShell.razor:53-59`); a page needing different grid behaviour does not use the shell.
- **The shell hands the page no grid while the phone layout is showing.** `Grid` answers `null` whenever `IsMobile` is set (`ListPageShell.razor.cs:127`, `IsMobile` at `:65`), and every adopting page in both consumers reads its `GridRef` from it (`MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerList.razor.cs:24`). The base pushes restored page, page size and sort into a grid only when `GridRef` returns one (`DataGridListPageBase.cs:610`, `:660`, `:681`), so list state restored on a phone is not pushed into a grid that is not rendered, and a window widened from the phone layout to the desktop layout makes its first fetch with the restored sort while the grid header shows the default.
- **Breaking for consumers.** The fitness test turns red in a consumer until every create form moves (`MMCA.Common/UPGRADING.md:109-113`).

## Alternatives rejected

Weighed 2026-11-12.

- **A code generator that emits create and list pages.** Rejected: a generated page is copied plumbing again, and a fix to the sequence would need every page regenerated in both consumers; the pages also differ in fields, pickers and pre-checks that a generator template would have to parameterize. Revisit if the number of create and list pages grows to the point that the per-page model and service call are themselves boilerplate.
- **One universal page component configured by parameters.** Rejected: field layout, filters, cards and success navigation differ per aggregate, so the parameter surface would grow until it restated each page, and a page with a different sequence (the room form above) would need a switch for it. The bases plus the shell keep the page's own markup and code. Revisit if a family of pages emerges whose markup is identical apart from the model type.
- **Leaving the convention to documentation alone.** Rejected: a documented pattern lets a new create form re-implement the sequence and still pass review, and the markers check alone accepts private members that mirror the base's names. The inheritance fact (`FormsConventionTestsBase.cs:178-196`) makes the base declaration checkable. Revisit only if the fitness test proves too coarse for a legitimate form shape, in which case narrow the discovery glob rather than drop the fact.

## Consequences

- **Two components are removed** (`MMCA.Common/UPGRADING.md:49-56`). `PageStateScope`, with its `OnRestore` parameter and `OnPageRestoredAsync` callback, has no replacement: delete the element, and reload in `OnParametersSetAsync` where a page needs a refresh after back navigation (`:54`, `:58-59`). `MobileCardList<TItem>` is replaced by `MobileInfiniteScrollList<TItem>`: rename the element, keep `CardTemplate`, `OnCardClick`, `EmptyMessage`, `EmptyIcon` and `PageSize`, drop the paging parameters and pass `FetchPageResult`, which `MobilePageFetcher` builds (`:56`, `:61-66`). The `registerBfcacheHandler` and `unregisterBfcacheHandler` functions of `_content/MMCA.Common.UI/nav-interop.js` are removed with them, with no replacement (`:55`).
- **Per create page**, an adopter derives from `CreatePageBase` (dropping `IDisposable`), deletes the private cancellation, dirty, saving, save-result, form and toast members and the `Dispose` methods, renames the markup bindings (`_isDirty` to `IsDirty`, `_form` to `Form`, `_saveResult` to `SaveResult`, `_cts.LifetimeToken()` to `PageToken`) and replaces the submit body with one `SubmitAsync` call (`MMCA.Common/UPGRADING.md:115-133`).
- **Per list page**, an MMCA.ADC admin list replaces its header, search, grid, phone list, pager and delete markup with `ListPageShell`, wraps cell text in `RowLinkCell`, builds the phone delegate with `MobilePageFetcher`, and moves any pre-fetch wait into `OnBeforeFetchAsync`. MMCA.Store's six list pages on the shell take the same shape, `CustomerList` among them (`MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerList.razor:10`, phone delegate at `MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerList.razor.cs:38`); MMCA.Store's `OrderList` keeps its own grid and pager markup (`MMCA.Store/Source/Modules/Sales/MMCA.Store.Sales.UI/Pages/Orders/OrderList.razor:84`, `:187`) and builds the phone delegate with `MobilePageFetcher` (`MMCA.Store/Source/Modules/Sales/MMCA.Store.Sales.UI/Pages/Orders/OrderList.razor.cs:161`).
- **Adopters declare the base in the markup.** Every adopter puts `@inherits MMCA.Common.UI.Pages.Common.CreatePageBase` in the `.razor` file (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Sponsors/SponsorCreate.razor:8`, `MMCA.Store/Source/Modules/Identity/MMCA.Store.Identity.UI/Pages/Customers/CustomerCreate.razor:2`), and its code-behind partial class names no base (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Rooms/RoomCreate.razor.cs:10`, `MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Sponsors/SponsorCreate.razor.cs:16`). The fitness test accepts either location (`FormsConventionTestsBase.cs:159-169`, code-behind branch at `:168`).
- **Adopter columns name both type parameters.** Every `PropertyColumn` in the MMCA.ADC pages on the shell names both `T` and `TProperty` (`MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.UI/Pages/Activities/ActivityList.razor:50`, `:55`). The page supplies them through the `Columns` fragment (`ListPageShell.razor.cs:103`), rendered inside the shell's own `MudDataGrid` (`ListPageShell.razor:60-62`), and the shell declares its item type as `TItem` with no `CascadingTypeParameter` (`ListPageShell.razor:1`, `ListPageShell.razor.cs:23`).
- **What to watch.** A new create form that cannot fit the sequence is a signal to extend `CreateSubmitOptions`, not to fork the sequence in the page, once a second page needs the same variation.
