# MMCA.ADC: Architecture Scorecard

> **Canonical, version-controlled scorecard for this repo**: the single source of truth for MMCA.ADC's architecture scores, scored against the rubric at [`ArchitectureEvaluationCriteria.md`](ArchitectureEvaluationCriteria.md); framework-wide facts in [`../MMCA.Common/FACTS.md`](https://github.com/ivanball/MMCA.Common/blob/main/FACTS.md). Remediation lives in [`RemediationBacklog.md`](../governance/adc-RemediationBacklog.md), the single remediation and tech-debt ledger (it carries the tactical `TD-NN` items); the cross-repo comparison lives in the workspace-internal `Docs/Architecture/CrossRepoComparison.md` (not published).

_Evidence as of 2026-10-29 at MMCA.Common.* v1.265.1, git HEAD `360d86eab` (clean tree). Rubric version 2._

## At a glance

- **Maturity index** = Σ(maturity×weight) ÷ Σ(weight×4) = 316 ÷ 324 = **97.5%**
- **Implementation index** = Σ(impl×weight) ÷ Σ(weight×10) = 697 ÷ 810 = **86.0%**
- **Weaker axis:** Implementation, 11.5 points below Maturity.
- **Maturity band:** 3 categories sit below maturity 4 (Sections 10, 12 and 21; 8 weighted points), ranked in the [backlog](../governance/adc-RemediationBacklog.md).
- **Implementation band:** 14 categories sit at implementation 8 or below (32 weighted points short of 9 on every category), ranked in the [backlog](../governance/adc-RemediationBacklog.md).

MMCA.ADC is a .NET 10.0 DDD / Clean Architecture system for the Atlanta Developers Conference, run as four independently hosted services (Identity, Conference, Engagement, Notification) behind a YARP gateway, collaborating over Result-over-the-wire gRPC and MassTransit integration events on the outbox, one database per service, on the lockstep `MMCA.Common.*` packages (21 of the 26 published packages, `Directory.Packages.props:106-144`). Its strongest trait is that architectural intent is executable: 54 architecture-test classes gate CI on rules inherited from the shared `MMCA.Common.Testing.Architecture` library, and recovery, capacity, cost and cross-browser proofs are deploy preconditions sized to measured conference load (~67 peak). The remaining weight sits on the implementation axis, spread across fourteen categories at implementation 8 and led by five weight-3 rows (§7, §10, §11, §18, §21), and on three maturity gaps: §10's broker round-trip tier reaches the deploy only through a freshness gate, §12's capacity proof runs out of band by decision, and §21's manual screen-reader pass is unrecorded.

## Top 5 risks

1. **The manual screen-reader pass is unrecorded:** §21 (mat 3 / impl 8, weight 3; priority 3 in both bands). The chromium E2E/axe suite blocks the deploy (`AccessibilityTests.cs:23`, inside `e2e-gate`, `deploy.yml:808`), cross-engine recency is gated (`cross-browser-freshness`, `deploy.yml:925`, with `freshness` in `deploy.needs` at `:1161`), and the live-moderation dialog carries a keyboard-operability test (`LiveModerationKeyboardTests.cs:23`, a subclass of Common's `KeyboardOperabilityTestsBase`), but the recorded screen-reader pass that the rubric's maturity-4 bar asks for is the empty placeholder row in `adc-ACCESSIBILITY-SCREENREADER-PASS.md:69`. The implementation lever is not yet identified (axe is E2E-only, chromium-only and non-PR, and keyboard coverage is one dialog).
   - _Remediation:_ Record the manual screen-reader pass (needs a human with NVDA or VoiceOver).
   - _Expected:_ §21 maturity 3 to 4 (weight 3).

2. **The broker round-trip is proven out of band, and fault recovery is manual:** §10 (mat 3 / impl 8, weight 3; priority 3 in both bands). Broker faults are wired to alert-as-code: the `broker-error-queue` rule matches "moved to the error queue" (`infra/main.bicep:650-652`), the text Common's `FaultIntegrationEventConsumer.cs:80` logs, beside the outbox dead-letter rule (`infra/main.bicep:626-628`), and `infra/OPERATIONS.md:232` holds the error-queue runbook. Maturity holds at 3 because the broker round-trip tier runs on a weekday schedule (`cross-service-tests.yml:32`) and reaches the deploy only through the `cross-service-freshness` recency gate (`deploy.yml:886`), not as a merge gate. Implementation holds at 8: no compensating saga handler or reconciliation sweep exists (ADC has two compensating steps, not a saga) (`../adr/054-saga-compensation-and-reconciliation.md:210-212`), replay from the error queue is a manual runbook step (`infra/OPERATIONS.md:263`), and message retention is documented only for outbox dead-letter rows (30 days, `infra/main.bicep:1923`).
   - _Remediation:_ Bring the broker round-trip tier inside a merge gate (the recorded maturity lever); the implementation lever is not yet identified.
   - _Expected:_ §10 maturity 3 to 4 (weight 3).

3. **The synchronous call graph has bidirectional pairs and a call loop:** §7 (mat 4 / impl 8, weight 3; implPriority 3). Eight typed gRPC client registrations span the four `*.Contracts` assemblies (`Conference.Contracts/DependencyInjection.cs:46,:76,:104`, `Engagement.Contracts/DependencyInjection.cs:45,:78`, `Identity.Contracts/DependencyInjection.cs:43`, `Notification.Contracts/DependencyInjection.cs:44,:80`), forming two bidirectional pairs (Conference and Engagement, Identity and Notification) and a three-node Conference, Engagement, Notification loop: the rubric's "chatty synchronous call graphs" red flag (`ArchitectureEvaluationCriteria.md:266`). The contracts are frozen by `ProtoContractTests`, the resilience pipeline self-heals peer startup order, and the cached Conference-to-Engagement bookmark-count read is accepted (see the backlog's Deliberate and accepted).
   - _Remediation:_ Lever not yet identified: the modernization-patterns criterion is met in the ADRs (`../adr/007-grpc-extraction.md:26`, `../adr/008-service-extraction-topology.md:52`), and the event-fed projection that would remove the bookmark-count read is rejected.
   - _Expected:_ No score move is scheduled; §7 holds at implementation 8.

4. **SQL data plane: public network access remains:** §11 (mat 4 / impl 8, weight 3) and §17 (mat 4 / impl 9). App-to-database auth is passwordless managed identity in production, with the SQL admin login kept only as a dormant fallback. The residual is network exposure: `publicNetworkAccess: 'Enabled'` (`infra/main.bicep:1017`) plus the AllowAzureServices firewall rule (`:1023`), both deferred by design (no VNet; documented-accepted in `infra/SQL-MANAGED-IDENTITY.md`). §11's other v2 deduction, the missing threat model, is a recorded decision not to schedule it.
   - _Remediation:_ Move the SQL data plane onto private endpoints (disable public network access, drop the 0.0.0.0 rule). This is the VNet and private-endpoint epic, which requires recreating the Container Apps environment, hence deferred.
   - _Expected:_ Closing public network access is the 9 to 10 rung for §17; §11 holds at 8 until a lever other than the unscheduled threat model is named.

5. **UI code-behinds run close to the enforced cap:** §18 (mat 4 / impl 8, weight 3; implPriority 3). `UIArchitectureConventionTests` (`Ui/UIArchitectureConventionTests.cs:10`, a sealed subclass of the shared base) enforces the unoverridden 400-line code-behind cap (`UIArchitectureConventionTestsBase.cs:22`); counted the way the cap counts, `Engagement.UI/Pages/SessionLive/SessionLive.razor.cs` measures 399 lines (1 line of headroom), `Conference.UI/Pages/Speakers/SpeakerDashboard.razor.cs` 397, `EventFeedback.razor.cs` 395 and `CheckInScan.razor.cs` 394, and 15 code-behinds sit within 70 lines of the cap. Presentational sub-component extraction is applied file by file rather than systematically (TD-16, closed by decision).
   - _Remediation:_ None scheduled: the cap's fitness test forces the `SessionLive` or `SpeakerDashboard` split on the change that crosses 400.
   - _Expected:_ §18 holds at implementation 8.
