# MMCA.ADC: Architecture Scorecard

> **Canonical, version-controlled scorecard for this repo**: the single source of truth for MMCA.ADC's architecture scores, scored against the rubric at [`ArchitectureEvaluationCriteria.md`](ArchitectureEvaluationCriteria.md); framework-wide facts in [`../MMCA.Common/FACTS.md`](https://github.com/ivanball/MMCA.Common/blob/main/FACTS.md). Remediation lives in [`RemediationBacklog.md`](../governance/adc-RemediationBacklog.md), the single remediation and tech-debt ledger (it carries the tactical `TD-NN` items); the cross-repo comparison lives in the workspace-internal `Docs/Architecture/CrossRepoComparison.md` (not published).

_Evidence as of 2026-09-22 at MMCA.Common.* v1.209.0, git HEAD `0883e184` (clean tree). Rubric version 2._

## At a glance

- **Maturity index** = Σ(maturity×weight) ÷ Σ(weight×4) = 316 ÷ 324 = **97.5%**
- **Implementation index** = Σ(impl×weight) ÷ Σ(weight×10) = 697 ÷ 810 = **86.0%**
- **Weaker axis:** Implementation, 11.5 points below Maturity.
- **Maturity band:** 3 categories sit below maturity 4 (Sections 10, 12 and 21; 8 weighted points), ranked in the [backlog](../governance/adc-RemediationBacklog.md).
- **Implementation band:** 14 categories sit at implementation 8 or below (34 weighted points short of 9 on every category), ranked in the [backlog](../governance/adc-RemediationBacklog.md).

MMCA.ADC is a .NET 10.0 DDD / Clean Architecture system for the Atlanta Developers Conference, run as four independently hosted services (Identity, Conference, Engagement, Notification) behind a YARP gateway, collaborating over Result-over-the-wire gRPC and MassTransit integration events on the outbox, one database per service, on the lockstep `MMCA.Common.*` packages (20 of the 22 published packages, `Directory.Packages.props:111`). Its strongest trait is that architectural intent is executable: 54 architecture-test classes gate CI on rules inherited from the shared `MMCA.Common.Testing.Architecture` library, and recovery, capacity, cost and cross-browser proofs are deploy preconditions sized to measured conference load (~67 peak). The remaining weight sits on the implementation axis, led by the responsive substance of §22 (implPriority 4), and on three maturity gaps: §10's broker faults have no alert or replay procedure, §12's capacity proof runs out of band, and §21's manual screen-reader pass is unrecorded.

## Top 5 risks

1. **The responsive substance is the lowest implementation score on the card:** §22 (mat 4 / impl 7, weight 2; the top row of the implementation band at implPriority 4). Cross-engine recency is gated (`cross-browser-freshness`, `deploy.yml:1039`, in `deploy.needs` `:1310`, hard condition `:1352`), but both implementation deductions hold: the rubric's density-options criterion has zero adoption in ADC although the framework ships it (`DataGridListPageBase.cs:78` `DenseGrid`, `:898` `ToggleDensity()`; `EventList.razor:73` hardcodes `Dense="true"`), and 19 `.razor` files render raw tables outside the DataGrid's grid-to-card degradation with no mobile alternative (`Engagement.UI/Pages/Points/OrganizerPointsOverview.razor:61,:98`, `Engagement.UI/Pages/CheckIns/OrganizerAttendance.razor:50`).
   - _Remediation:_ Adopt the density toggle on the DataGrid list pages (bind `DenseGrid` / `ToggleDensity()` instead of the hardcoded `Dense`) and give the 19 raw-table pages a card or stacked degradation at the phone breakpoint, starting with the data-dense conference-day surfaces (effort M). The freshness gate is the maturity lever and does not count toward implementation.
   - _Expected:_ §22 impl 7→8 on the first half, 8→9 when the reflow covers every raw-table page.

2. **The manual screen-reader pass is unrecorded:** §21 (mat 3 / impl 8, weight 3). The chromium E2E/axe suite blocks the deploy (`e2e-gate` in `deploy.needs`) and cross-browser recency is gated (`cross-browser-freshness`, `deploy.yml:1039`, in `deploy.needs` `:1310`), but the recorded screen-reader pass that the rubric's maturity-4 bar asks for is still the empty placeholder row in `adc-ACCESSIBILITY-SCREENREADER-PASS.md:64`.
   - _Remediation:_ Record the manual screen-reader pass (needs a human with NVDA or VoiceOver).
   - _Expected:_ §21 maturity 3→4 (weight 3).

3. **Broker faults have no operational path, and the async contract gate misses nullable retypes:** §10 (mat 3 / impl 8, weight 3). `FaultIntegrationEventConsumer.cs:57` logs "faulted ... moved to the error queue", but the only messaging log alert matches the outbox's "dead-lettered" text (`infra/main.bicep:521`), so no alert covers broker faults; ADR-087 records no alert, runbook or replay path (`../adr/087-broker-poison-message-handling.md:200`). `SpeakerLinkedToUserHandler.cs:48` has no ordering guard under a redelivery that reaches 3600 s, and the contract snapshot renders nullables without the type argument, so a nullable retype passes (`IntegrationEventContractTests.cs:17`).
   - _Remediation:_ An alert plus runbook for the broker error queue with a replay procedure, ordering guards on the speaker link handlers, and a type-argument-aware contract snapshot.
   - _Expected:_ The alert, runbook and replay procedure lift §10 impl 8→9; the ordering guards and an `[EventName]` requirement are the maturity 3→4 levers.

4. **SQL data plane: public network access remains:** §11 (mat 4 / impl 8, weight 3) and §17 (mat 4 / impl 9). App-to-database auth is passwordless managed identity in production, with the SQL admin login kept only as a dormant fallback. The residual is network exposure: `infra/main.bicep:764` `publicNetworkAccess: 'Enabled'` plus the AllowAzureServices firewall rule at `:768-775`, both deferred by design (no VNet; documented-accepted in `infra/SQL-MANAGED-IDENTITY.md`). §11's other v2 deduction, the missing threat model, is a recorded decision not to schedule it.
   - _Remediation:_ Move the SQL data plane onto private endpoints (disable public network access, drop the 0.0.0.0 rule). This is the VNet and private-endpoint epic, which requires recreating the Container Apps environment, hence deferred.
   - _Expected:_ Closing public network access is the 9→10 rung for §17; §11 holds at 8 until a lever other than the unscheduled threat model is named.

5. **The API contract guard cannot catch a breaking change, the capacity proof runs out of band, and the MAUI head sits outside CI:** §9 (mat 4 / impl 8), §12 (mat 3 / impl 9) and §15 (mat 4 / impl 8). The shared OpenAPI guard is well-formedness plus a paths-count floor and pinned resource strings, not a baseline diff (`MMCA.Common.Testing/Conformance/OpenApiContractTestsBase.cs:38,:48,:62`), the committed per-service OpenAPI documents' drift gate (`deploy.yml:297-312`) catches an uncommitted change but does not classify a breaking one, and no AsyncAPI-style async contract document exists. The k6 tier executes on a monthly cron plus dispatch (`load-test.yml:23`) and `load-freshness` gates on recency, not execution (`deploy.yml:873`, `:881`, `:1310`). The MAUI `MMCA.ADC.UI` project is in no CI build (`MMCA.ADC.CI.slnf:25,:26` list only the web heads), so its analyzers and its own `NoWarn CA5392` (`MMCA.ADC.UI.csproj:151`) are review-only.
   - _Remediation:_ Commit an OpenAPI baseline per service, diff the live document against it in the integration tier, and publish the seven integration-event contracts as an AsyncAPI-style document (TD-24, effort M); run the k6 tier (or a scaled-down smoke of it) inside the deploy chain; bring the MAUI head inside a CI build (TD-18), verified by a full-solution package-mode restore.
   - _Expected:_ The contract diff plus async document lifts §9 impl 8→9; an in-band capacity proof lifts §12 maturity 3→4; MAUI inside a CI build lifts §15 impl 8→9.
