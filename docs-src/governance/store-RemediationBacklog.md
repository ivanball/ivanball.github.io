# MMCA.Store: Architecture Remediation Backlog

Derived from [`ArchitectureScorecard.md`](../governance/store-ArchitectureScorecard.md): **Maturity 98.4% (311/316) / Implementation 84.2% (665/790)**, evidence as of 2026-09-20 at MMCA.Common.* v1.206.0 (all 17 packages lockstep, HEAD `f983cc08`, clean tree). Items are ranked on both scorecard axes, one band per axis. The **maturity band** holds categories scoring **maturity < 4**, ranked by **priority = (4 − maturity) × weight**. The **implementation band** holds categories scoring **implementation <= 8**, ranked by **implPriority = max(0, 9 − implementation) × weight**; the scheduling target is **9, not 10**, because a 10 is recognition earned at re-score time rather than scheduled work, and ranking against 10 would put nearly every strong category in the band and drown the real gaps. Ties break by weight descending, then category number. A category leaves each band independently and reaches the protect list only at **maturity 4 AND implementation >= 9**; the indices keep their `× 4` and `× 10` denominators, and the 9-target governs scheduling only.

The scorecard is the source of truth for scores, [`../MMCA.Common/FACTS.md`](https://github.com/ivanball/MMCA.Common/blob/main/FACTS.md) for framework-wide facts, and the workspace-internal `Docs/Architecture/ArchitectureRemediation.md` (not published) for the cross-repo `[C→A]` roll-up. Tactical deferrals are recorded here as `TD` sub-items under their category (the single-ledger model). Status: `[ ]` open, `[~]` under way, `[x]` resolved.

## Deliberate and accepted

- **§16 AI-Native Application Architecture is N/A** (rubric v2, [ADR-110](../adr/110-rubric-v2-category-realignment.md)): no product feature calls a language model, so its weight 2 leaves both denominators until one does.
- **#5 layered-by-project hybrid.** Cross-cutting concerns live in the pipeline and module projects keep a layered split; a deliberate design choice that caps §5 at Implementation 8, not a maturity deduction.
- **Chromium-only deploy E2E gate (#22, #21): accepted CI-cost trade-off.** The deploy-gating `e2e-gate` runs a single engine (job at `deploy.yml:692`, rationale `:694-702`, `browsers: '["chromium"]'` at `:706`); firefox and webkit run on the advisory schedule, one alternating engine per week (the `browser` matrix expression at `e2e.yml:139-142`, Monday firefox `:140`, Thursday webkit `:141`, crons `:46-47`, schedule-scoped `continue-on-error` at `:149`). The `cross-browser-freshness` gate bounds each engine's blind window at 10 days as a hard `deploy` condition (`deploy.yml:924`, `:1200`, `:1238`). Revisit if a webkit-only or firefox-only defect reaches production, which is the risk being priced. The UI-scoping of the gate is a separate open TD under #21.
- **TD · #22: the `cross-browser-freshness` gate is break-glass skippable.** The gate proves a green firefox and webkit leg within 10 days (`deploy.yml:936`), not that this exact tree passes on those engines, and the `skip_freshness_gates` `workflow_dispatch` input that also skips #12's `load-freshness` skips it with a justification (`deploy.yml:949-961`). Accepted as priced on the ADC precedent, whose row carries the identical caveat. _Blocker:_ none; a per-change three-engine gate is the Actions-minute cost the chromium-only entry prices. _Resolution path:_ none scheduled; revisit if a single-engine defect reaches production or the break-glass is used outside an incident. _Effort:_ S (denying the skip is one `if:` change).
- **#33 Service Bus emulator tier gates through recency.** `Tests/Integration/MMCA.Store.ServiceBusEmulator.IntegrationTests` runs MassTransit v8 against the official Service Bus emulator (pinned 2.0.1) with the real `ProductVariantChanged` contract, and `cross-service-freshness` requires both it and the RabbitMQ tier to have succeeded in the same nightly run (`deploy.yml:874-894`, job `:834`, in deploy `needs` at `:1200`). The tier needs Docker, so it stays out of both solution filters and reaches the deploy chain through the recency check rather than per PR. Mirrors ADC's TD-17; ADR-066 records the gated end state in both consumers.
- **TD · Product-image derivatives (#12, #23): deferred.** Images are full-size DB blobs streamed as-is and rendered as card thumbnails with no `srcset`/dimensions, so a 12-card browse grid can pull 12 full-size assets. Fixing it is a storage-design decision, not a local change; not scheduled.
- **Single-region deployment**: accepted in `infra/DISASTER-RECOVERY.md` (real load does not justify multi-region cost).
- **All per-service DBs on one physical SQL server**: logical isolation is complete; the shared server is a cost choice (minor §7/§8).
- **SQL public network access (no VNet)**: the documented acceptance behind the §17 cap, the same caveat ADC carries.
- **ADR-042 device capability abstraction: latent.** The core extension point is converged (Store wires browser + MAUI capabilities via `UseMauiDeviceCapabilities`/`AddBrowserDeviceCapabilities` and renders the shared `OfflineBanner`), but Store consumes no further capability in its own product UI: no `ExternalLink`, no `DeviceUIModule`/`DeepLinkListener`, no app actions. No Store product page carries an external anchor, so the WebView dead-end risk is latent, not a live defect. Adopt `ExternalLink` on any Store product page that grows an external anchor, and register a Store `IUIModule` with `DeepLinkListener` (the way ADC's `DeviceUIModule` does) if a Store MAUI feature surface is wanted. The framework side is complete in Common (18 capability contracts + the `MMCA.Common.UI.Maui` package), so this is consumer-side only, not `[C→A]`.
- **ADR-043 adoption (mobile deep links / app association / native OAuth callback): deferred.** Adoption is feature-scale (Store-scheme deep links, iOS/Android manifest entries, associated domains) and rides the same trigger as ADR-042: adopt when a Store MAUI surface is actively wanted.
- **ADR-044 adoption (native push, third notification channel): deferred.** Store has no user-notification pipeline (no ADR-024 inbox, no SignalR channel), so adoption means adopting the whole notification stack first: a product decision, not remediation. Schedule only if Store wants user notifications.
- **#14 dedicated rate-limit fixtures: skipped.** The WAFs neutralize the limiter and a tight-limit variant is low value for the volume; revisit only if abuse is observed.
- **#11 login throttle shared by Blazor Server circuits.** The per-IP anti-spray throttle inherited from Common's `AuthControllerBase` counts every Server-circuit user against the UI host's IP (a 30/min window), because Blazor Server issues the login call server-side. Watch the 429 rate; tune with `AddCommonRateLimiting(authIpPermitLimit: N)`.
- **#1 service constructor ceiling at 9.** Set for `AuthenticationService` together with `HandlerConventionTests` (Store #166/#167); the clock fitness rule carries one allowlist entry, the backfill-only `Order.RepublishFulfillment`.
- **#23 catalog trade-offs**: price sorts fall back to Newest; search is Name-contains.
- **#24 server-only and inline rules**: SKU uniqueness stays server-only (it needs the DB); the Profile-form password fields stay inline by design, in both consumers.
- **#19 silent cart initialization**: `CartStateService.InitializeAsync` loads the cart without raising `OnChange`; initialization is silent and only user-visible mutations notify (pinned intended behavior).
- **`OrderDetail` without `[Authorize]`**: a recorded deliberate choice from the E2E gap review.
