# MMCA.Store: Architecture Scorecard

> **Canonical, version-controlled scorecard for this repo**: the single source of truth for MMCA.Store's architecture scores. Scored against the rubric at [`ArchitectureEvaluationCriteria.md`](ArchitectureEvaluationCriteria.md); framework-wide facts in [`../MMCA.Common/FACTS.md`](https://github.com/ivanball/MMCA.Common/blob/main/FACTS.md). Remediation lives in [`RemediationBacklog.md`](../governance/store-RemediationBacklog.md); the cross-repo comparison in the workspace-internal `Docs/Architecture/CrossRepoComparison.md` (not published).

_Evidence as of 2026-10-29 at MMCA.Common.* v1.265.1 (lockstep), git HEAD e16935cd (clean tree). Rubric version 2._

## At a glance

- **Maturity index** = Σ(maturity×weight) ÷ Σ(weight×4) = 308 ÷ 316 = **97.5%**
- **Implementation index** = Σ(impl×weight) ÷ Σ(weight×10) = 657 ÷ 790 = **83.2%**
- **Weaker axis:** Implementation (execution quality), by ~14 points, a wider gap than ADC's.
- **Below maturity 4:** 3 categories (§10 Messaging, §12 Performance, §21 Accessibility); see the [maturity band](../governance/store-RemediationBacklog.md#maturity-band).
- **Implementation band (implementation <= 8):** 22 categories; see the [implementation band](../governance/store-RemediationBacklog.md#implementation-band).

MMCA.Store is a .NET 10.0 DDD/Clean Architecture e-commerce system (Catalog, Sales, Identity modules; Stripe checkout) running as independently hosted services behind a YARP gateway, database-per-service (`Store_Catalog`/`Store_Sales`/`Store_Identity`, each with its own outbox), collaborating via Result-over-the-wire gRPC and MassTransit integration events, and consuming `MMCA.Common.*` in lockstep with MMCA.ADC. Its strongest ground is inherited framework substance guarded by 62 architecture fitness-test classes, reference front-end security (section 26), and an operational floor of two-phase Bicep IaC, OIDC + managed identity, signed service tokens on the internal gRPC edge that returns customer data, a post-deploy smoke gate, a drilled DR restore and freshness-gated deploys. The weight of the remaining gap sits on the implementation axis: security (section 11) is the one weight-3 category at I7, and 18 categories are at M4/I8, led by the weight-3 SOLID constructor ceilings (section 1), the accepted lockstep deploy (section 7), UI architecture (section 18), state management (section 19) and front-end testing (section 28). Several of those I8 holds are recorded decisions rather than scheduled work (see Deliberate and accepted in the backlog).

## Top 5 risks

1. **Security holds at implementation 7 on accepted red flags**: section 11 (impl 7, weight 3): the Stripe webhook signing secret is cached in plaintext in the shared Redis with a 365-day lifetime (`SharedCacheStripeWebhookSecretStore.cs:79`, lifetime at `:54`), one shared identity is `db_owner` in all three databases (`infra/SQL-MANAGED-IDENTITY.md:80`), every per-app Service Bus SAS rule carries Manage rights (`infra/main.bicep:1126,1138,1150`), internal ingress allows insecure transport (`:1535`), and the SQL server keeps password admin auth with public network access (`:884,887`). Each is a recorded decision (Deliberate and accepted in the backlog), and each is still a rubric red flag, so the row stays below 8. The internal Customers gRPC edge requires a user or service token (`Identity.Service/Program.cs:343`).
   - _Remediation:_ none scheduled beyond the user-side seed-account check; the Data Protection wrap of the cached secret is dropped by decision. _Expected:_ section 11 impl 7 holds while the accepted caps stand.
2. **Messaging maturity holds at 3 after the error-queue procedure shipped**: section 10 (mat 3, impl 8, weight 3): the broker error queue now has an alert (`store-alert-broker-error-queue`, `infra/main.bicep:498`), an inspect, replay and discard runbook (`infra/OPERATIONS.md:178`), and `[EventName]` is required by `EventConventionTests.cs:3`. The real broker round-trip still reaches the deploy only through the `cross-service-freshness` recency check (`deploy.yml:828`), not a merge gate, and the round-trip tier runs nightly (`cross-service-tests.yml:4`).
   - _Remediation:_ lever not yet identified, named at the next re-score. _Expected:_ section 10 stays M3 until one is named.
3. **Accessibility maturity is capped pending a human pass**: section 21 (mat 3, weight 3): the 32-scan axe suite and the cart-drawer keyboard test (`CartDrawerKeyboardTests.cs:21`) gate the deploy (impl 8), but the rubric pairs axe-in-CI with a recorded manual screen-reader pass and the `ACCESSIBILITY-SCREENREADER-PASS.md` results log holds only the placeholder row (`store-ACCESSIBILITY-SCREENREADER-PASS.md:70`), matching ADC's M3.
   - _Remediation:_ record a dated NVDA/VoiceOver pass in the runbook against the running app (needs a human; cannot be done headless). _Expected:_ section 21 mat 3 to 4.
4. **Load evidence is capacity-planning cadence, not a merge gate**: section 12 (mat 3): the k6 suite is real with pass/fail thresholds and a `load-freshness` deploy gate, but the test itself runs monthly/on-demand (`load-test.yml:21` cron, `workflow_dispatch` at `:12`), so a latency regression can merge and deploy inside the 35-day freshness window. `load-freshness` (`deploy.yml:809`) runs the shared freshness-gate action in success mode over a 35-day window (`:818`), keyed on the latest successful run, and carries a break-glass skip.
   - _Remediation:_ none scheduled: the monthly k6 run plus `load-freshness` is the accepted posture, because an in-band k6 run on every deploy would load production at a peak of about 67 users (Deliberate and accepted in the backlog). _Expected:_ section 12 stays M3.
5. **Every merge is a single-revision production deploy**: section 17 (impl 8, weight 2) with section 7 (impl 8, weight 3): the deploy is one `azure/arm-deploy` of the whole `main.bicep` (`deploy.yml:1332`) with all five images pinned to one `IMAGE_SHA` (`:1160`), the accepted lockstep posture for a five-app fleet, into the only environment (`ENVIRONMENT_NAME: prod`, `:41`) under `activeRevisionsMode: 'Single'` (`infra/main.bicep:1528`), with no canary or slot. The rollback reports what it did (per-app outcome `deploy.yml:1536`, counted summary `:1544`) and rolls back only a failed activation: an HTTP-probe failure on a fleet whose newest revisions are live rolls nothing back (`:1504-1507`), the skip-live guard ADR-080 keeps.
   - _Remediation:_ none scheduled: the Bicep what-if and probe-only rollback are closed as over-engineering (Deliberate and accepted in the backlog); the lever for 9 is not yet identified. _Expected:_ section 17 impl 8 holds.

## Top 5 strengths

1. **Clean Architecture + DDD + CQRS depth, fitness-enforced**: §3/§4 (impl 9): inherited framework substance, guarded by the shared NetArchTest suite (62 test classes, `StoreArchitectureMap.cs:14-43`).
2. **Full microservices parity on a race-safe data layer**, §7 (impl 8) / §8 (impl 9): database-per-service + per-service outbox + versioned gRPC + MassTransit broker + RS256/JWKS, extractable modules (`infra/main.bicep:1033-1051` per-service DBs, `:1079` Service Bus), with the oversell race closed by an atomic conditional UPDATE under deterministic lock ordering plus a schema CHECK backstop (`InventoryAllocationService.cs:71-73`, `InventoryItemConfiguration.cs:57-59`) and destructive migrations blocked at the merge gate (`deploy.yml:431-483`).
3. **Observability and test strategy, gate-backed**: §13 (impl 9) / §14 (impl 9): `ObservabilityConventionTests.cs:7` pairs every SLO alert with an `infra/OPERATIONS.md` section and fails below four specs (`:13`), and the required `build-and-test` check holds a self-filtered line floor of 51.6 and an Application-layer branch floor of 72.8 (`deploy.yml:374`, `:407`) over a real-SQL integration tier.
4. **Reference front-end security**, §26 (impl 9): in-memory access token + HttpOnly refresh cookie (no localStorage), hardened origin-pinned CSP, runtime-config fetch (`ServerTokenStorageService.cs:9-12`, `BlazorCspPolicyProvider.cs:105`).
5. **Drilled DR + real erasure path** (§29 impl 9 / §30 impl 8): recorded 28.9-min restore (`DISASTER-RECOVERY.md:209`, drill-history table `:207-212`), the `dr-freshness` deploy gate + weekly cron + CI-gated `GracefulShutdownTests`, `IAnonymizable` anonymize-in-place + export + residency/PII fitness functions.

## Scoring notes

- **Two axes per category:** Maturity (0-4, process/governance) and Implementation (0-10, substance/execution). The indices are computed deterministically from the table: every non-N/A category is in both denominators.
- **N/A (excluded from denominators):** §16 AI-Native Application Architecture (rubric v2, [ADR-110](../adr/110-rubric-v2-category-realignment.md): no product feature calls a model); its weight 2 leaves both denominators, Σweight 79.
- **§10** is Messaging & Integration Architecture under rubric v2, at the v2 default weight 3.
- **§27** is scored: ADR-027 (en-US + es with a CI-gated translation-completeness fitness function) supersedes ADR-011's single-locale exclusion.
- **§32 weight = 2** (default; 3 only for the published framework MMCA.Common).
- The implementation index reads directly against 100%: a 10 is awardable for an almost perfect implementation. The denominators stay ×4 and ×10 so the trend line stays comparable across re-scores.
- **Axis calibration:** a new CI gate is an enforcement gain and scores on the maturity axis, not the implementation axis; a CI-cadence change is not a substance regression; documentation drift scores on the implementation axis.
- **Axis-gap reading:** §10, §12 and §21 are M3/I8, strong substance with enforcement short of automatic, which is the healthy direction of the gap. The maturity-over-implementation gap sits in the 18 categories at M4/I8, where enforcement is automatic but substance is short of 9.
