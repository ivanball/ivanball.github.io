    Architecture Decision Record

    ADR-134: Cloud-Neutral Core With Vendor Adapter Packages

    Status

    Accepted (2026-10-24). The change is the MMCA.Common v1.255.0 entry of the framework changelog (MMCA.Common/CHANGELOG.md:7, Added at :11-17, Fixed at :21, Breaking at :25-29) and its upgrade section (MMCA.Common/UPGRADING.md:35). It amends the records whose Azure integrations moved: ADR-041, ADR-044, ADR-045, ADR-061, ADR-066, ADR-069, ADR-015 and ADR-118; each carries a 2026-10-24 revision.

    Revised 2026-10-25 (MMCA.Common v1.257.0, MMCA.Common/CHANGELOG.md:7): AWS gains the vault configuration, DataProtection key ring and native push Azure already had, plus passwordless PostgreSQL through RDS IAM (Azure covers passwordless SQL Server through Entra instead) (:11-15); a third cloud adapter, MMCA.Common.Gcp, covers storage, secrets, the key ring, push, passwordless PostgreSQL and telemetry for Google Cloud (:16-23); Google Cloud has no MassTransit v8 Pub/Sub transport, so its broker answer is a built-in, cloud-neutral PostgreSql provider (:24); the core gains the INpgsqlDataSourceConfigurator hook and the public NativePushPayloads builders the adapters share (:25-26); the startup tripwires gain one check per new gate and the key-ring rule now fails when more than one of three key-ring gates is set (:27, :33); and the type-level vendor rule, which had passed vacuously for every Azure and AWS type, is fixed (:32). The Decision below reads as the current state; the options weighed on 2026-10-25 are added to Alternatives rejected.

    Context

    Before v1.255.0 the core packages carried the Azure SDKs themselves: MMCA.Common.Infrastructure, MMCA.Common.Aspire, MMCA.Common.API and MMCA.Common.Testing each referenced Azure packages, and MMCA.Common.Testing brought Testcontainers.ServiceBus, Azure.Messaging.ServiceBus and MassTransit.Azure.ServiceBus.Core into every test project that used it (MMCA.Common/CHANGELOG.md:25). A consumer that never runs on Azure (a self-hosted deployment, or one on AWS) still restored, audited and shipped those dependencies, and the broker selection was a closed enum, MessageBusProvider, so a second cloud's transport could only be added by editing the core (MMCA.Common/CHANGELOG.md:26).

    The framework already had a working shape for optional vendor code. The AI boundary (ADR-120) keeps the provider SDKs in separate packages (MMCA.Common.AI.Anthropic, MMCA.Common.AI.OpenAI) and resolves a configured provider name against the factories those packages register, failing at boot when the name matches none (MMCA.Common/Source/Core/MMCA.Common.AI/Providers/AiProviderValidator.cs:6-12, :16). The cloud integrations had no equivalent: their SDKs were unconditional references of the core.

    Decision

    The core packages reference no cloud SDK. Each vendor integration ships in an adapter package that references the core, and a host opts in with one registration call per capability. The framework guide states the rule (MMCA.Common/AGENTS.md:145).

The EnforceCloudVendorBoundary build target fails a core project whose PackageReference is an Azure, AWS or Google Cloud package (an Azure.*, Microsoft.Azure.*, AWSSDK.* or Google.* id, FirebaseAdmin or Grpc.Auth), a vendor MassTransit transport, or whose ProjectReference names an adapter project, MMCA.Common.Gcp included (MMCA.Common/Source/Build/MMCA.Common.LayerEnforcement.targets:109-115, adapters at :128, target at :130, patterns at :138-147, adapter references at :149, errors at :151 and :153).     • The SQS transport works within SQS limits. AmazonSqsTransport registers under the provider name AmazonSqs (MMCA.Common/Source/Hosting/MMCA.Common.Aws/Messaging/AmazonSqsTransport.cs:37, :40) and uses MassTransit.AmazonSQS at 8.5.11, the same version as every other MassTransit pin (MMCA.Common/Directory.Packages.props:125-130). SQS caps a message delay at 900 seconds (MaxDelaySeconds, AmazonSqsTransport.cs:43), so an unconfigured redelivery list defaults to [60, 300, 900] (:55, applied at :128) and a configured interval over 900 fails AddBrokerMessaging instead of being silently shortened (:159-161). The MMCA-* ambient headers (:46) travel in the MassTransit envelope body, not as SQS/SNS message attributes (:30-33, :134-135), so they never compete for the 10-attribute cap (MMCA.Common/CHANGELOG.md:12).
    • The adapters are exercised against real infrastructure. The aws-integration CI job runs MMCA.Common.Aws against LocalStack through Testcontainers (MMCA.Common/.github/workflows/ci.yml:849-850, test run with a floor of 14 tests at :887), and the gcp-integration job runs MMCA.Common.Gcp against fake-gcs-server and the Firestore emulator (:889-890, floor of 14 at :934); neither is a required check (MMCA.Common/CHANGELOG.md:23, :59). The PostgreSQL tier covers a periodic password provider and the PostgreSql broker (:28).

    Rationale

    • A broker that needs a database, not a cloud service, belongs in the core. The SQL transport runs on any PostgreSQL, managed or self-hosted (PostgreSqlBrokerTransport.cs:10-14), so putting it in MMCA.Common.Gcp would have hidden a cloud-neutral broker behind one vendor's package.
    • A consumer pays only for the cloud it runs on. With the SDKs in adapters, a self-hosted or AWS deployment restores, audits and ships no Azure package, and an Azure deployment carries no AWS one.
    • The AI provider shape already worked. Optional vendor code in its own package, selected by name and refused at boot when the name has no registration (AiProviderValidator.cs:6-12), is the model the cloud adapters follow, so a reader of one boundary already knows the other.
    • A string provider is open to extension without editing the core. A closed enum forced every new transport into MMCA.Common.Infrastructure; IBrokerTransport lets an adapter add one, and BrokerTransportPolicies keeps retry, redelivery and backpressure identical across all of them.
    • Unchanged configuration keeps the move to code. A deployment's environment variables, Bicep and Key Vault names stay as they are; only the package reference and the registration calls change.
    • Silent degradation is the failure mode the tripwires remove. Before the move, the core wired each integration itself. After it, a host that keeps its configuration but loses the call would otherwise start with the null storage, the null push sender, no telemetry export, no vault secrets or a per-replica key ring. Failing startup with the call named turns that into a deploy-time error.

    Trade-offs

    • Every Azure host gains calls it did not need before. AddAzureMonitorExporter() after AddServiceDefaults() and AddAzureServiceBusTransport() before AddBrokerMessaging are new, and the Key Vault, DataProtection and push calls are renamed (MMCA.Common/UPGRADING.md:35).
    • Registration order matters in two places. The exporter must follow AddServiceDefaults() (AzureMonitorExporterExtensions.cs:45-50), and an adapter transport must be registered before AddBrokerMessaging resolves it (DependencyInjection.Messaging.cs:148, :177).
    • The Cosmos engine still brings an Azure assembly into Infrastructure. Microsoft.Azure.Cosmos arrives transitively through Microsoft.EntityFrameworkCore.Cosmos, so the core is cloud-neutral in its cloud-service integrations, not free of every Azure assembly (MMCA.Common.LayerEnforcement.targets:115-118).
    • SQS redelivery is shorter than the framework default. The framework default is [60, 600, 3600] (MessageBusSettings.cs:212); SQS cannot delay an hour, so its default stops at 900 seconds (AmazonSqsTransport.cs:55).
    • The AWS and Google Cloud tiers are not required checks. A regression in MMCA.Common.Aws or MMCA.Common.Gcp shows as a red aws-integration or gcp-integration job without blocking a merge (MMCA.Common/CHANGELOG.md:23, :59).
    • Every consumer of MMCA.Common.Infrastructure restores the SQL transport. The built-in PostgreSql provider brings MassTransit.SqlTransport.PostgreSQL and Dapper to every consumer, whichever broker it selects (MMCA.Common/CHANGELOG.md:24).
    • An IAM-only broker database cannot migrate at startup. MassTransit's schema migrator opens its own connections from the connection string, so such a host sets MigrateOnStartup=false and creates the transport schema in a deployment step that connects with a password (PostgreSqlBrokerTransport.cs:33-37).
    • Google Cloud metrics need a collector. AddGoogleCloudTelemetryExporter() ships traces and logs; metrics reach Google only through the Google-built OpenTelemetry Collector (GoogleCloudTelemetryExporterExtensions.cs:78-88).
    • The Google push adapter takes FCM tokens only. An APNs-platform registration fails validation, so an iOS client registers an FCM token (MMCA.Common/CHANGELOG.md:20).
    • Neither managed SQL Server offers IAM database authentication. RDS for SQL Server keeps a password connection string loaded from Secrets Manager (MMCA.Common/CHANGELOG.md:15); Cloud SQL for SQL Server (:21) takes either a password connection string from Secret Manager or, on SQL Server 2022 and later, Entra ID through MMCA.Common.Azure (MMCA.Common/Source/Hosting/MMCA.Common.Gcp/GcpServiceCollectionExtensions.cs:80-83).

    Alternatives rejected

    Weighed and rejected on 2026-10-24.

    • Leave the Azure SDKs in the core. Simplest for the Azure-hosted consumers, but every other consumer keeps restoring, auditing and shipping Azure packages it never calls, and a test project keeps pulling the Service Bus emulator stack through MMCA.Common.Testing. Revisit only if every consumer is permanently Azure-only.
    • Add AWS to the core next to Azure. It would serve AWS deployments without new packages, but it doubles the dependency footprint every consumer carries instead of removing it, and the closed provider enum would grow with each cloud. Revisit never: it worsens the problem this record solves.
    • One package per capability per vendor (for example separate Blob, Key Vault, Service Bus and Monitor packages). It gives the finest-grained dependency control, but multiplies the package count the dual-registry release publishes and versions in lockstep, and the maintenance that comes with each. One package per vendor with one call per capability keeps the opt-in at the call while the package count stays at one per cloud. Revisit if one capability's SDK becomes heavy enough that hosts using the others object to carrying it.

    Weighed and rejected on 2026-10-25.

    • A hand-written MassTransit transport for Google Pub/Sub. It would give Google Cloud a native broker, but no MassTransit v8 Pub/Sub transport exists (MMCA.Common/CHANGELOG.md:24), so the framework would own a broker transport's delivery, redelivery and topology outside the MassTransit project. The PostgreSql provider gives Google Cloud a broker on Cloud SQL instead. Revisit if MassTransit ships a supported Pub/Sub transport on the line ADR-118 pins.
    • MassTransit v9 for a wider transport set. v9 is commercial with a runtime licence key, which ADR-118 already rejects. Revisit on the condition that record names.
    • Google's own DataProtection packages. They are prerelease only, and a stable package cannot depend on a prerelease (NU5104), so the key-ring repository and the Cloud KMS encryptor are the framework's own (MMCA.Common/CHANGELOG.md:19; MMCA.Common/Directory.Packages.props:187-191). Revisit when Google publishes a stable release.
    • Exporting Google Cloud metrics without a collector. The Telemetry API caps a metric request at 200 data points and the OpenTelemetry .NET SDK offers no supported way to split one metric's points across requests, so a host with more than 200 time series would have whole batches rejected (GoogleCloudTelemetryExporterExtensions.cs:78-81). Revisit when the SDK can split a metric or the API cap rises.
    • The PostgreSQL transport inside MMCA.Common.Gcp. It would keep the core free of one more package, but the transport needs only a database and works on any PostgreSQL (PostgreSqlBrokerTransport.cs:10-14), so an AWS, Azure or self-hosted consumer would have to reference the Google adapter to use it. Revisit if the transport ever needs a Google SDK.

    Consequences

    • The change is breaking. The renames, moved types and new calls are mapped once in MMCA.Common/UPGRADING.md:35 (the old-to-new table and the seven-step fix per host) rather than restated here; Microsoft.Data.SqlClient.Extensions.Azure now arrives only through MMCA.Common.Azure, so any process whose SQL connection string uses Authentication=Active Directory ... references that package (MMCA.Common/CHANGELOG.md:25).
    • A configured redelivery list now replaces the default. Making the provider a string came with RedeliveryIntervalsSeconds becoming null when unconfigured (MessageBusSettings.cs:234), which fixes the binder appending a configured list to the old initializer, so [0] turns second-level redelivery off as documented (BrokerTransportPolicies.cs:124-125; MMCA.Common/CHANGELOG.md:21).
    • A new cloud is an adapter, not a core change. A transport implements IBrokerTransport, storage implements IFileStorageService, and a tripwire message names the call, with the build and architecture gates holding the core free of the new SDK.
    • The residual Cosmos dependency stays. The two engine exemptions are the only vendor references in the core; adding a third is a deliberate edit to both gates, not a drift either can miss.
