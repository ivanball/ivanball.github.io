    Architecture Decision Record

    ADR-032: Password Hashing (PBKDF2-HMAC-SHA512) with Legacy-Hash Backward Compatibility

    Status

    Superseded by ADR-102 (2026-08-31). Originally Accepted (2026-06-29, adoption note revised 2026-07-06, registration note revised 2026-08-01, call-site hoist recorded 2026-08-23). Revised 2026-10-26: ADR-102 is itself superseded by ADR-133, which now carries the current decision (032 -> 102 -> 133), and the live sections below are rewritten to describe current source rather than the migration-era design (the migration-era text survives only in the dated revisions): the HMAC branch is gone, the load-bearing legacy branch is now the header-less 64-byte PBKDF2 hash read at 600,000 iterations, new hashes are versioned at 210,000 iterations, and a successful sign-in rehashes a stale record through NeedsRehash for users that opt in. Revised 2026-10-28: the stale opening sentences saying ADR-102 carries the current decision and the body is retained unchanged are removed, the 2026-10-26 sentence drops its clause about that earlier note, and the rehash anchors are refreshed.

    Context

    Identity stores a credential as a (salt, hash) pair, never plaintext. The framework needs one canonical hasher that every consuming Identity flow shares, so the key-derivation algorithm, work factor, and comparison are decided once and not re-implemented per app. Two forces shape the choice:

    • A modern, deliberately slow KDF. A fast hash (or a raw HMAC) makes offline brute force cheap if a credential table leaks, so the format must use a stretched, salted derivation tuned to current guidance, with a timing-safe comparison.
    • An existing corpus of already-stored passwords. Earlier records were written as a bare 64-byte PBKDF2-HMAC-SHA512 digest at a fixed 600,000 iterations, with no header recording the work factor. Those rows cannot be force-reset, and they cannot be re-hashed in place: the plaintext needed to recompute a hash only exists transiently at the user's next sign-in. Verification therefore has to accept the old shape and the current one from the same stored bytes, with no schema flag distinguishing them. (The still older HMAC-SHA512 format with a 128-byte salt is no longer accepted; ADR-102 records its removal.)

    Decision

    Provide a single IPasswordHasher (MMCA.Common.Application.Interfaces.Infrastructure.Auth, IPasswordHasher.cs:6) with one implementation PasswordHasher (Source/Core/MMCA.Common.Infrastructure/Auth/PasswordHasher.cs:22), registered as a singleton via TryAddSingleton (Source/Core/MMCA.Common.Infrastructure/DependencyInjection.cs:335, in the public AddServices extension member at DependencyInjection.cs:315 that AddInfrastructure (DependencyInjection.cs:57) calls at DependencyInjection.cs:254). The call site always runs, but TryAdd semantics mean a host that has already registered its own IPasswordHasher keeps it: the framework supplies the default hasher rather than forcing it. The type is stateless (only const parameters), so the singleton lifetime is safe.

    • New passwords use versioned PBKDF2-HMAC-SHA512. HashPassword (PasswordHasher.cs:61) draws a fresh 32-byte salt from RandomNumberGenerator.GetBytes (PasswordHasher.cs:65) and derives a 64-byte key via Rfc2898DeriveBytes.Pbkdf2 with HashAlgorithmName.SHA512 (ComputePbkdf2Hash, PasswordHasher.cs:141-147). It writes a 69-byte hash: the version byte 0x01, a 4-byte big-endian iteration count, then the 64-byte digest (PasswordHasher.cs:68-71). The constants are SaltSize = 32 (PasswordHasher.cs:25), HashSize = 64 (PasswordHasher.cs:28) and Iterations = 210_000 (PasswordHasher.cs:34), the OWASP figure for PBKDF2-HMAC-SHA512. The versioned format and the work factor are owned by ADR-133.
    • Verification reads the work factor from the stored bytes, not from a flag. VerifyPassword (PasswordHasher.cs:77) returns false unless the salt is SaltSize bytes and TryReadIterations accepts the hash (PasswordHasher.cs:90). TryReadIterations (PasswordHasher.cs:122-138) accepts exactly two shapes: a header-less 64-byte hash, read at LegacyIterations = 600_000 (PasswordHasher.cs:37), or a 69-byte hash whose version byte is 0x01 and whose stored count lies between MinIterations = 100_000 (PasswordHasher.cs:52) and MaxIterations = 2_000_000 (PasswordHasher.cs:58). Any other material verifies nothing, so the same call site verifies both shapes transparently. The bounds cap a tampered row rather than freeze it: such a row can still move the work factor anywhere from 100,000 to 2,000,000, or to 600,000 by taking the header-less shape, but cannot drop below the floor or force an unbounded verification (PasswordHasher.cs:48-58, :126, :133).
    • The legacy branch is load-bearing, not dead code. The 64-byte branch of TryReadIterations (PasswordHasher.cs:124-128) is the only path by which a record written before versioning still verifies. A refactor that "simplifies" it away would compile cleanly, pass the current-format tests, deploy without error, and then silently reject every record not yet upgraded. There is no exception and no startup failure to catch it; the only symptom is that those users cannot sign in.
    • A successful sign-in upgrades a stale record. IPasswordHasher declares NeedsRehash(byte[] hash) as a default interface member returning false (IPasswordHasher.cs:28), so a host-supplied hasher need not implement it. PasswordHasher.NeedsRehash (PasswordHasher.cs:109-115) returns true for a legacy 64-byte hash and for a versioned hash whose stored count differs from Iterations, and false for the current shape and for unrecognized material. After tokens are issued, AuthenticationServiceBase calls RehashPasswordIfNeededAsync (AuthenticationServiceBase.cs:237, declared at :676), which runs only when issuance succeeded and the user implements IPasswordRehashableUser (:678), checks NeedsRehash (:688), hashes the verified plaintext (:693) and saves through the unit of work, all inside BestEffort.ExecuteAsync (:683): a failure is logged and the record is upgraded on a later sign-in, never failing a sign-in that already succeeded. Both apps opt in (ADC User.cs:36, Store User.cs:30).
    • Comparison is constant time. The single PBKDF2 path compares the recomputed digest to the trailing HashSize bytes of the stored hash (PasswordHasher.cs:95) with CryptographicOperations.FixedTimeEquals (PasswordHasher.cs:100), which always reads the full length so the verify time does not leak how many leading bytes matched.
    • Adopted by both apps' Identity flow, through shared bases. Each app's AuthenticationService is a sealed subclass of AuthenticationServiceBase<TUser> (Source/Core/MMCA.Common.Application/Auth/AuthenticationServiceBase.cs:67, IPasswordHasher parameter at :69) that passes the hasher into the base constructor rather than calling it. The base owns every sign-in call site: the login-time VerifyPassword (AuthenticationServiceBase.cs:178), the registration-time HashPassword (AuthenticationServiceBase.cs:277), the timing burn for an unknown account or one with no stored credential such as an external-OAuth account (HashPassword at AuthenticationServiceBase.cs:655, reached from :170-172) and the rehash above. ADC's subclass declares the parameter and forwards it (MMCA.ADC/.../Identity.Application/Users/AuthenticationService.cs:52, forwarded at AuthenticationService.cs:61); Store's does the same (MMCA.Store/.../Identity.Application/Users/AuthenticationService.cs:28, forwarded at AuthenticationService.cs:35). The remaining hasher call sites are hoisted the same way, each into its own shared base. Change-password lives in ChangePasswordHandlerBase<TUser, TCommand> (ChangePasswordHandlerBase.cs:56, IPasswordHasher at :58), which verifies the current password (ChangePasswordHandlerBase.cs:109) before hashing the new one (ChangePasswordHandlerBase.cs:118) and applying the aggregate's ChangePassword (ChangePasswordHandlerBase.cs:119). Reset-password lives in ResetPasswordHandlerBase<TUser, TCommand> (MMCA.Common.Application.Users.UseCases.ResetPassword, ResetPasswordHandlerBase.cs:42, IPasswordHasher at :44), which hashes the new password (ResetPasswordHandlerBase.cs:110). Each app's ChangePasswordHandler and ResetPasswordHandler only declares the IPasswordHasher parameter and forwards it (ChangePasswordHandler.cs:26 in ADC, :31 in Store; ResetPasswordHandler.cs:26 in ADC, :30 in Store). Seeding lives in IdentityModuleDbSeederBase<TUser> (MMCA.Common.Infrastructure.Persistence.DbContexts.Seeding, IdentityModuleDbSeederBase.cs:57, IPasswordHasher through the constructor at :59 and :71), which hashes each seeded account's password (IdentityModuleDbSeederBase.cs:136); each app's IdentityModuleDbSeeder supplies only the account list, an EmailExistsAsync existence check (abstract at IdentityModuleDbSeederBase.cs:114; ADC IdentityModuleDbSeeder.cs:42, Store :45) and a CreateUser factory (abstract at IdentityModuleDbSeederBase.cs:123) and forwards the hasher (IdentityModuleDbSeeder.cs:30 in ADC, :32 in Store). Every hasher invocation both apps depend on therefore sits in framework code; no file under either app's Source/ calls HashPassword, VerifyPassword or NeedsRehash. The one app-side lookup is each app's IdentityModuleSeeder, which resolves IPasswordHasher through GetRequiredService (ADC IdentityModuleSeeder.cs:34, Store IdentityModuleSeeder.cs:33) to construct the seeder rather than injecting it.

    Rationale

    • One framework-owned primitive, not per-app crypto. Putting the algorithm, work factor, salt size, and comparison in a single shared type means a future hardening (raising iterations, changing the KDF) is one edit that every consumer inherits, rather than a hunt across Identity modules.
    • Migrate on the user's own sign-in, with no flag day. Because the stored bytes themselves carry the work factor, legacy records keep working untouched, and there is no bulk migration job, no reset email blast, and no IsLegacy column to maintain. A record moves to the current format the next time its owner signs in (the opt-in rehash) or sets or changes a password (which always writes the versioned shape).
    • Slow-by-design KDF over a fast hash. PBKDF2-HMAC-SHA512 at a high iteration count makes offline cracking of a leaked table expensive, which a single-pass HMAC does not, and storing the count per hash lets that count move without breaking a single stored credential.

    Trade-offs

    • The legacy branch is a correctness dependency that looks deletable. Its load-bearing role is invisible from the method body alone, so it is the most refactor-fragile line in the hasher. The mitigation is this record plus focused regression tests: Tests/Core/MMCA.Common.Infrastructure.Tests/Auth/PasswordHasherSecurityTests.cs:34 verifies a legacy 64-byte digest computed at 600,000 iterations, PasswordHasherSecurityTests.cs:147 pins LegacyIterations, and Auth/PasswordHasherTests.cs:39 asserts NeedsRehash is true for a legacy hash, alongside the current-format coverage at PasswordHasherTests.cs:21 (69-byte versioned hash), PasswordHasherTests.cs:77 and PasswordHasherTests.cs:84 (verify true and false). The removed HMAC format is pinned the other way: PasswordHasherSecurityTests.cs:164 asserts a 128-byte-salt HMAC-SHA512 digest is rejected.
    • Format selection is keyed on hash length and a version byte. It relies on the legacy (64 bytes) and versioned (69 bytes) shapes being distinct. They are, and corrupt or hostile material at worst fails to verify rather than misauthenticates (PasswordHasherSecurityTests.cs:195), but a future format has to claim a new version byte rather than reuse 0x01.
    • The upgrade is opt-in and best effort. A user whose app type does not implement IPasswordRehashableUser, or who never signs in, stays on the old shape indefinitely, and a failed rehash save is only retried on a later sign-in. The design accepts that tail rather than run a bulk job that would need plaintext it does not have.
    • The work factor is a fixed compile-time constant. Iterations = 210_000 is not configurable per host, so raising it is a framework change and a release, not an appsetting. Because each hash stores its own count (accepted only between MinIterations and MaxIterations), raising it re-derives records on their next sign-in rather than breaking them. That keeps the security floor uniform across consumers at the cost of per-deployment tuning.

    Revision (2026-08-23)

    The decision is unchanged: one framework-owned IPasswordHasher, PBKDF2-HMAC-SHA512 for new passwords, salt-length dispatch on verification. What changed is where the last two call sites live.
