    Architecture Decision Record

    ADR-044: Native Push Delivery (the Third Notification Channel)

    Status

    Accepted (2026-07-11). Amends ADR-024. The framework pipeline is implemented and inert by default; each consumer switches it on by provisioning a notification hub with platform credentials and enabling the NativePush configuration section. Revised 2026-10-01 (UI.Maui ships credentialed FCM/APNs token providers and token-rotation re-registration; see Revision below). Revised 2026-10-06: the device DELETE route is /Notifications/Devices/{installationId}. Revised 2026-10-07: anchors refreshed after the v1.233.0 release. Revised 2026-10-21: anchors refreshed after the releases that moved the device controller, the registration service and the registrar. Revised 2026-10-24: the Notification Hubs sender and registrar moved to MMCA.Common.Azure, registered by AddAzureNotificationHubsPush (ADR-134); see Revision (2026-10-24). Revised 2026-10-25: two more delivery adapters ship, SNS mobile push over a DynamoDB registry (MMCA.Common.Aws) and FCM HTTP v1 over a Firestore registry (MMCA.Common.Gcp), and the payload builders moved into the core; see Revision (2026-10-25). Revised 2026-10-26: anchors refreshed after the releases that moved the SNS sender and registrar and the core payload builders.

    Context

    ADR-024 established two notification channels: a durable per-user UserNotification inbox (the source of truth) and a transient SignalR push behind IPushNotificationSender. Both stop at the edge of a connected client: a phone with the app backgrounded, killed, or offline hears nothing until the next launch. Conference announcements ("lunch is served", "room change") are exactly the messages that must reach pockets, not open tabs.

    OS-level delivery needs three things the framework did not have: a per-device registration store keyed to users, a sender that speaks FCM v1 (Android) and APNs (iOS), and a client-side lifecycle that registers the device after sign-in and unregisters it before sign-out. It also needs credentials (a Firebase service account, an APNs auth key) that cannot live in source and may not exist when the code ships.

    Decision

    • Two Application abstractions, Null by default (the ADR-024 pattern): INativePushSender (user-targeted and broadcast native sends) and IPushDeviceRegistrar (installation upsert/delete, MMCA.Common/Source/Core/MMCA.Common.Application/Interfaces/Infrastructure/Notifications/IPushDeviceRegistrar.cs:11, UpsertAsync at :29, DeleteAsync at :48). AddInfrastructure TryAdds no-op defaults.
    • Three delivery adapters, one registration call each. Each call implements both abstractions and swaps them in only when NativePush:Enabled is true AND its own section is complete, so hosts call it unconditionally and deployments flip the channel on by configuration alone:
      • Azure Notification Hubs, AddAzureNotificationHubsPush(configuration) (MMCA.Common.Azure), gated on ConnectionString and HubName. One hub abstracts both platforms behind one API, holds the platform credentials outside our code, and its installation model gives upsert semantics with client-generated stable ids. The free tier covers conference volumes.
      • AWS SNS mobile push, AddAmazonSnsPush(configuration) (MMCA.Common/Source/Hosting/MMCA.Common.Aws/AwsServiceCollectionExtensions.cs:164), gated on NativePush:Sns carrying InstallationsTable, BroadcastTopicArn and at least one of FcmPlatformApplicationArn / ApnsPlatformApplicationArn (:138-147, :170-175). SNS keeps no owner per endpoint, so a DynamoDB table is the installation registry: partition key InstallationId, global secondary index UserId-index on UserId (:150-152; .../MMCA.Common.Aws/Notifications/SnsInstallationRegistry.cs:29). The ownership and handover rule is one conditional write, attribute_not_exists(InstallationId) OR UserId = :me OR PushChannel = :channel (SnsInstallationRegistry.cs:36, applied at :97), so it holds under concurrency without a lock. A broadcast is one publish to the topic every endpoint subscribes to (Notifications/SnsPushDeviceRegistrar.cs:157-167, Notifications/SnsNativePushSender.cs:73-80), and an endpoint SNS reports disabled or missing is removed with its row on send (SnsNativePushSender.cs:99-102).
      • Google FCM HTTP v1, AddFirebaseCloudMessagingPush(configuration) (MMCA.Common/Source/Hosting/MMCA.Common.Gcp/GcpServiceCollectionExtensions.cs:142), gated on NativePush:Fcm carrying ProjectId, InstallationsCollection and BroadcastTopic (:119-123, :148-153), with Application Default Credentials. A Firestore collection is the registry, one document per installation id, and every ownership decision is a Firestore transaction (.../MMCA.Common.Gcp/Notifications/FirestoreInstallationRegistry.cs:10-12, :45). Only FCM registration tokens are accepted: an APNs-platform registration fails validation with PushDevice.UnsupportedPlatform (Notifications/FcmPushDeviceRegistrar.cs:40-46), so an iOS client registers its FCM token on this adapter. A broadcast is one message to the FCM topic (Notifications/FcmNativePushSender.cs:95), and a send that reports the token unregistered, or names it as an invalid registration token, prunes the installation (Notifications/FcmSendOutcome.cs:25-28, FcmNativePushSender.cs:80). The token target is set under a scoped CS0618 suppression (Notifications/FcmPushMessage.cs:31-39): FirebaseAdmin 3.6+ deprecates Message.Token in favour of Firebase installation ids (FIDs), while the topic-subscription APIs the broadcast depends on take registration tokens only. The exit is moving registration and send to FIDs together.
    • A lost adapter call fails startup. NativePush:Enabled=true while INativePushSender is still the Null sender fails validation with a message naming all three calls and their keys (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Configuration/CloudAdapterTripwire.cs:48-53).
    • Sends target users, never raw tokens; a user's every device gets the message. On Notification Hubs installations are tagged user:{id} and tag expressions are OR-chunked at the hub's 20-tag cap (MMCA.Common/Source/Hosting/MMCA.Common.Azure/Notifications/NativePushUserTags.cs:11,20, unit-tested), so audience size is unbounded. The SNS and FCM registries look installations up by their UserId field instead (SnsInstallationRegistry.cs:127; Firestore queries at most 30 users at a time, FirestoreInstallationRegistry.cs:23).
    • One payload shape in the core. NativePushPayloads.BuildFcmV1Payload and BuildApnsPayload are public in MMCA.Common.Infrastructure.Notifications.Push (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Notifications/Push/NativePushPayloads.cs:13,20,42), called by the Notification Hubs sender (MMCA.Common/Source/Hosting/MMCA.Common.Azure/Notifications/AzureNotificationHubNativePushSender.cs:22-23) and the SNS message builder (MMCA.Common/Source/Hosting/MMCA.Common.Aws/Notifications/SnsPushMessage.cs:29-30). The FCM adapter maps the same fields onto FirebaseAdmin's typed Message instead of raw JSON (MMCA.Common/Source/Hosting/MMCA.Common.Gcp/Notifications/FcmPushMessage.cs:7-9, :56-76), with a test pinning the equivalence.
    • SendPushNotificationHandler gains the third leg. After the inbox write and the SignalR attempt, it calls INativePushSender.SendToUsersAsync inside its own non-fatal catch. The audit status (Sent/Failed) stays owned by the SignalR leg: the inbox remains the source of truth, and a hub outage must not fail the command or the other channels.
    • DevicesController (PUT /Notifications/Devices, DELETE /Notifications/Devices/{installationId}, DevicesController.cs:22,35,60) ships in MMCA.Common.API via the existing AddNotificationControllers application part, [Authorize] for any signed-in user and feature-gated with the same Notification.PushNotifications flag as the rest of the pipeline. Ownership is stamped server-side from the current user; installation ids are client-generated GUIDs (not enumerable). DELETE is idempotent and owner-scoped: IPushDeviceRegistrar.DeleteAsync(userId, installationId, ct) takes the owning user, and an unknown id and another user's id both answer success without deleting anything.
    • Client orchestration behind two UI capability contracts (ADR-042 pattern): IPushRegistrationService (register after sign-in, unregister BEFORE sign-out - the delete call is authenticated) and IPushDeviceTokenProvider (the platform token extension point). UI.Maui ships MauiPushRegistrationService (stable installation id in IDevicePreferences, sync over the named API client, with a SemaphoreSlim serializing registration passes, MauiPushRegistrationService.cs:27,44). The token provider defaults to NullPushDeviceTokenProvider (TryAdd, MMCA.Common.UI/Services/Capabilities/DependencyInjection.cs:62); the opt-in AddMauiPushDeviceTokenProvider() (MMCA.Common.UI.Maui/DependencyInjection.cs:124-132) replaces it with FcmPushDeviceTokenProvider on Android (gated on the Push:Fcm section, FcmPushDeviceTokenProvider.cs:33,43-49) and ApnsPushDeviceTokenProvider on iOS/MacCatalyst (gated on Push:Apns:Enabled, ApnsPushDeviceTokenProvider.cs:30,37), while the windows TFM keeps the Null default. A build WITHOUT push credentials is therefore wired but inert end to end. PushRegistrationListener (rendered through the host layout extension point) re-registers on auth-state changes, and on Android MauiFirebaseMessagingService.OnNewToken re-registers when FCM rotates the token (MauiFirebaseMessagingService.cs:26-35). AuthUIService owns the unregister leg: LogoutAsync and RevokeAllSessionsAsync both call UnregisterPushAsync before the local sign-out (AuthUIService.cs:90,143, defined at :361).

    Consequences

    • Sends fan out per 20-user chunk and per platform: an audience of N users costs ceil(N/20) * 2 hub calls. Acceptable at conference scale; a template-based send can consolidate later without touching callers.
    • The handler's third leg is best-effort: it is awaited inside a non-fatal catch (SendPushNotificationHandler.cs:141-154), with no per-device delivery tracking. Because SendPushNotificationCommand is ITransactional, a transient fault on the final status save re-runs the live legs under the execution strategy, so native delivery is at-least-once and a device can receive the same OS push twice (SendPushNotificationHandler.cs:21-30). The hub's telemetry is the observability surface; the inbox remains the recovery path.
    • A delete verifies ownership before it acts: the registrar reads the installation and checks the user:{id} tag UpsertAsync stamped on it (AzureNotificationHubDeviceRegistrar.cs:84-92), so an id belonging to someone else deletes nothing. That costs an extra hub round trip per delete, and the response cannot tell a caller which case it hit: an unknown id and a foreign one both answer success, deliberately, so the endpoint is not an existence oracle for other users' installation ids.
    • Consumers must update PRIVACY.md/store data-safety forms (push tokens are device identifiers) BEFORE store metadata mentions push. Credential provisioning (Firebase service account, APNs key) is a manual runbook step per app; until done, the hub rejects sends and the client token provider yields nothing - both by design.
    • SendPushNotificationHandler gained a constructor parameter (DI-resolved; source-compatible for every host, breaking only for code constructing it manually - none known).

The Decision now describes three adapters.

The exit is moving registration and send to FIDs together.
    6. Rejected alternative: registry rows in each consumer's own database. Keeping the SNS and FCM installations as rows in each consumer's database was weighed on 2026-10-24 and rejected (a design decision recorded here, not in source): an adapter-owned table would need a migration and a PR in every consumer that enables push, and the adapter would no longer hold everything its capability needs. Revisit if a consumer must keep installation data inside its own database for a residency or audit reason.
