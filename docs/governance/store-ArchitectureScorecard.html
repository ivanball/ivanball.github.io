    Architecture governance

    MMCA.Store: Architecture Scorecard

    Canonical, version-controlled scorecard for this repo: the single source of truth for MMCA.Store's architecture scores. Scored against the rubric at ArchitectureEvaluationCriteria.md; framework-wide facts in ../MMCA.Common/FACTS.md. Remediation lives in RemediationBacklog.md; the cross-repo comparison in the workspace-internal Docs/Architecture/CrossRepoComparison.md (not published).

    Evidence as of 2026-10-01 at MMCA.Common.* v1.217.0 (all 17 packages, lockstep), git HEAD 579e395b (clean tree). Rubric version 2.

    At a glance

    • Maturity index = Σ(maturity×weight) ÷ Σ(weight×4) = 308 ÷ 316 = 97.5%
    • Implementation index = Σ(impl×weight) ÷ Σ(weight×10) = 659 ÷ 790 = 83.4%
    • Weaker axis: Implementation (execution quality), by ~14 points, a wider gap than ADC's.
    • Below maturity 4: 3 categories (§10 Messaging, §12 Performance, §21 Accessibility); see the maturity band.
    • Implementation band (implementation <= 8): 21 categories; see the implementation band.

    MMCA.Store is a .NET 10.0 DDD/Clean Architecture e-commerce system (Catalog, Sales, Identity modules; Stripe checkout) running as independently hosted services behind a YARP gateway, database-per-service (Store_Catalog/Store_Sales/Store_Identity, each with its own outbox), collaborating via Result-over-the-wire gRPC and MassTransit integration events, and consuming MMCA.Common.* in lockstep with MMCA.ADC. Its strongest ground is inherited framework substance guarded by 53 architecture fitness-test classes, reference front-end security (§26), and an operational floor of two-phase Bicep IaC, OIDC + managed identity, a post-deploy smoke gate with auto-rollback, a drilled DR restore and freshness-gated deploys. The weight of the remaining gap sits on the implementation axis: security (§11) is the one weight-3 category at I7, and 17 categories are at M4/I8, led by the weight-3 SOLID constructor ceilings (§1), lockstep deploy (§7), UI architecture (§18), state management (§19) and front-end testing (§28).

    Top 5 risks

    1. An internal gRPC edge returns customer PII to any caller: §11 (impl 7, weight 3): Identity maps CustomersGrpcService with .AllowAnonymous(), and it returns email and full name keyed by a raw customer id, so any workload inside the Container Apps environment can enumerate it (Identity.Service/Program.cs:369, the host's own comment at :336-345). ADC requires authorization on the equivalent edge (MMCA.ADC.Identity.Service/Program.cs:362). The same row carries three narrower red flags: one shared identity is db_owner in all three databases (infra/SQL-MANAGED-IDENTITY.md:78), every per-app Service Bus SAS rule has Manage rights (infra/main.bicep:1039), and the Stripe webhook signing secret is written to stderr in production (StripeWebhookRegistrationService.cs:191) and cached in plaintext in Redis for 365 days (SharedCacheStripeWebhookSecretStore.cs:79).
      • Remediation: a Common client-credentials token that Sales mints and JwtForwardingClientInterceptor attaches, then .RequireAuthorization() on the Identity edge (the fix the host comment names at :353-360); stop logging the signing secret. Expected: §11 impl 7→8.
    2. Broker failures have no operating procedure: §10 (mat 3, impl 8, weight 3): the only messaging alert matches the outbox's "dead-lettered" text (infra/main.bicep:435), while a consumer that exhausts its retries logs "moved to the error queue" (Common FaultIntegrationEventConsumer.cs:57), which no Store alert matches; infra/OPERATIONS.md has an outbox-row replay but no error-queue section, and its consumer inventory names one live flow where five consumers run (OPERATIONS.md:140).
      • Remediation: an alert-as-code on the error-queue log line or the broker metric, an OPERATIONS.md runbook with a replay-or-discard procedure, and a fitness rule requiring [EventName] on every event (Common-side). Expected: §10 mat 3→4.
    3. Accessibility maturity is capped pending a human pass: §21 (mat 3, weight 3): the 32-scan axe suite gates the deploy (impl 8), but the rubric pairs axe-in-CI with a recorded manual screen-reader pass and the ACCESSIBILITY-SCREENREADER-PASS.md results log holds only the placeholder row (store-ACCESSIBILITY-SCREENREADER-PASS.md:70), matching ADC's M3.
      • Remediation: record a dated NVDA/VoiceOver pass in the runbook against the running app (needs a human; cannot be done headless). Expected: §21 mat 3→4.
    4. Load evidence is capacity-planning cadence, not a merge gate: §12 (mat 3): the k6 suite is real with pass/fail thresholds and a load-freshness deploy gate, but the test itself runs monthly/on-demand (load-test.yml:21 cron, workflow_dispatch at :12), so a latency regression can merge and deploy inside the 35-day freshness window. load-freshness (deploy.yml:848) runs the shared freshness-gate action in success mode, keyed on the latest successful run (:857-863), and carries a break-glass skip (:865-866).
      • Remediation: right-size deliberately: either accept the monthly cadence as the recorded posture (matching ADC's accepted §12 M3) or add a cheap latency-regression smoke to the merge path. Expected: decision recorded either way; §12 mat 3→4 only with a gate.
    5. Services deploy in lockstep: §7 (impl 8, weight 3): the build half of independent deployability is per-image incremental, but the deploy half is one azure/arm-deploy of the whole main.bicep (deploy.yml:1360) with all five images pinned to one IMAGE_SHA (:1202) and a whole-fleet rollback (:1466, :1524), the rubric's "services that must deploy together" red flag.
      • Remediation: split the container-app image parameters so an unchanged service keeps its current revision and the rollback iterates only the apps the deploy touched, or record the lockstep as the accepted posture for a five-app fleet. Expected: §7 impl 8→9, or a Deliberate and accepted entry.

    Top 5 strengths

    1. Clean Architecture + DDD + CQRS depth, fitness-enforced: §3/§4 (impl 9): inherited framework substance, guarded by the shared NetArchTest suite (53 test classes, StoreArchitectureMap.cs:14-43).
    2. Full microservices parity on a race-safe data layer, §7 (impl 8) / §8 (impl 9): database-per-service + per-service outbox + versioned gRPC + MassTransit broker + RS256/JWKS, extractable modules (infra/main.bicep:943-967 per-service DBs, :995 Service Bus), with the oversell race closed by an atomic conditional UPDATE under deterministic lock ordering plus a schema CHECK backstop (InventoryAllocationService.cs:71-73, InventoryItemConfiguration.cs:57-59) and destructive migrations blocked at the merge gate (deploy.yml:427-478).
    3. Exemplary DevOps / operational floor: §17 (impl 9) / §31 / §12: two-phase Bicep, OIDC + Key Vault MI, passwordless MI-SQL active in prod, post-deploy smoke gate with auto-rollback (smoke deploy.yml:1396, rollback loops :1466/:1524 over the app list at :1404), cost-guard/dr-drill/load-test workflows.
    4. Reference front-end security, §26 (impl 9): in-memory access token + HttpOnly refresh cookie (no localStorage), hardened origin-pinned CSP, runtime-config fetch (ServerTokenStorageService.cs:9-12, BlazorCspPolicyProvider.cs:105).
    5. Drilled DR + real erasure path (§29 impl 9 / §30 impl 8): recorded 28.9-min restore (DISASTER-RECOVERY.md:209, drill-history table :207-212), the dr-freshness deploy gate + weekly cron + CI-gated GracefulShutdownTests, IAnonymizable anonymize-in-place + export + residency/PII fitness functions.

    • N/A (excluded from denominators): §16 AI-Native Application Architecture (rubric v2, ADR-110: no product feature calls a model); its weight 2 leaves both denominators, Σweight 79.
    • §10 is Messaging & Integration Architecture under rubric v2, at the v2 default weight 3.
    • §27 is scored: ADR-027 (en-US + es with a CI-gated translation-completeness fitness function) supersedes ADR-011's single-locale exclusion.
    • §32 weight = 2 (default; 3 only for the published framework MMCA.Common).
    • The implementation index reads directly against 100%: a 10 is awardable for an almost perfect implementation. The denominators stay ×4 and ×10 so the trend line stays comparable across re-scores.
    • Axis calibration: a new CI gate is an enforcement gain and scores on the maturity axis, not the implementation axis; a CI-cadence change is not a substance regression; documentation drift scores on the implementation axis.
    • Axis-gap reading: §10, §12 and §21 are M3/I8, strong substance with enforcement short of automatic, which is the healthy direction of the gap. The maturity-over-implementation gap sits in the 17 categories at M4/I8, where enforcement is automatic but substance is short of 9.
