    Architecture governance

    MMCA.Store: Architecture Scorecard

    Canonical, version-controlled scorecard for this repo: the single source of truth for MMCA.Store's architecture scores. Scored against the rubric at ArchitectureEvaluationCriteria.md; framework-wide facts in ../MMCA.Common/FACTS.md. Remediation lives in RemediationBacklog.md; the cross-repo comparison in the workspace-internal Docs/Architecture/CrossRepoComparison.md (not published).

    Evidence as of 2026-09-20 at MMCA.Common.* v1.206.0 (all 17 packages, lockstep), git HEAD f983cc08 (clean tree). Rubric version 2.

    At a glance

    • Maturity index = Σ(maturity×weight) ÷ Σ(weight×4) = 311 ÷ 316 = 98.4%
    • Implementation index = Σ(impl×weight) ÷ Σ(weight×10) = 665 ÷ 790 = 84.2%
    • Weaker axis: Implementation (execution quality), by ~14 points, a wider gap than ADC's.
    • Below maturity 4: 2 categories (§12 Performance, §21 Accessibility); see the maturity band.
    • Implementation band (implementation <= 8): 20 categories; see the implementation band.

    MMCA.Store is a .NET 10.0 DDD/Clean Architecture e-commerce system (Catalog, Sales, Identity modules; Stripe checkout) running as independently hosted services behind a YARP gateway, database-per-service (Store_Catalog/Store_Sales/Store_Identity, each with its own outbox), collaborating via Result-over-the-wire gRPC and MassTransit integration events, and consuming MMCA.Common.* in lockstep with MMCA.ADC. Its strongest ground is inherited framework substance guarded by 53 architecture fitness-test classes, reference front-end security (§26), and an operational floor of two-phase Bicep IaC, OIDC + managed identity, a post-deploy smoke gate with auto-rollback, a drilled DR restore and freshness-gated deploys. The weight of the remaining gap sits on the implementation axis: 18 categories are at M4/I8, led by the weight-3 lockstep deploy (§7), messaging (§10), security (§11), UI architecture (§18), state management (§19) and front-end testing (§28).

    Top 5 risks

    1. Accessibility maturity is capped pending a human pass: §21 (mat 3, weight 3): the 32-scan axe suite gates the deploy (impl 8), but the rubric pairs axe-in-CI with a recorded manual screen-reader pass and the ACCESSIBILITY-SCREENREADER-PASS.md results log holds only the placeholder row (store-ACCESSIBILITY-SCREENREADER-PASS.md:70), matching ADC's M3.
      • Remediation: record a dated NVDA/VoiceOver pass in the runbook against the running app (needs a human; cannot be done headless). Expected: §21 mat 3→4.
    2. Load evidence is capacity-planning cadence, not a merge gate: §12 (mat 3): the k6 suite is real with pass/fail thresholds and a load-freshness deploy gate, but the test itself runs monthly/on-demand (load-test.yml:21 cron, workflow_dispatch at :12), so a latency regression can merge and deploy inside the freshness window. load-freshness also carries a break-glass skip (deploy.yml:825-839, exit 0 at :838, job at :804) and keys on the latest successful run (:841).
      • Remediation: right-size deliberately: either accept the monthly cadence as the recorded posture (matching ADC's accepted §12 M3) or add a cheap latency-regression smoke to the merge path. Expected: decision recorded either way; §12 mat 3→4 only with a gate.
    3. Design-system residual palette: §20 (impl 8): the inline-style sweep is at zero and pinned by CategoryListTests.cs:127, but the StoreHome landing stylesheet hard-codes a hex palette behind !important with only --mmca-primary tokenized (Catalog.UI/Pages/Home/StoreHome.razor.css:218,289, the one stylesheet both hosts share).
      • Remediation: tokenize the StoreHome palette onto the theme variables and drop the !important overrides in the shared stylesheet, extending BrandColorTokenTests to the full literal set. Expected: §20 impl 8→9.
    4. Client validation short of server parity: §24 (impl 8): the four create forms' guard/dirty/validated-MudForm markers are CI-gated (FormsConventionTests, M4), but client validation is DataAnnotations-level rather than full FluentValidation parity with the server rules.
      • Remediation: mirror the remaining server-only rules client-side where they do not need the DB. Expected: §24 impl 8→9.
    5. Services deploy in lockstep: §7 (impl 8, weight 3): the build half of independent deployability is per-image incremental, but the deploy half is one azure/arm-deploy of the whole main.bicep (deploy.yml:1424) with all five images pinned to one IMAGE_SHA (:1306) and a whole-fleet rollback (:1566), the rubric's "services that must deploy together" red flag.
      • Remediation: split the container-app image parameters so an unchanged service keeps its current revision and the rollback iterates only the apps the deploy touched, or record the lockstep as the accepted posture for a five-app fleet. Expected: §7 impl 8→9, or a Deliberate and accepted entry.

    Top 5 strengths

    1. Clean Architecture + DDD + CQRS depth, fitness-enforced: §3/§4 (impl 9): inherited framework substance, guarded by the shared NetArchTest suite (53 test classes, StoreArchitectureMap.cs:14-43).
    2. Full microservices parity on a race-safe data layer, §7 (impl 8) / §8 (impl 9): database-per-service + per-service outbox + versioned gRPC + MassTransit broker + RS256/JWKS, extractable modules (infra/main.bicep:919-943 per-service DBs, :965 Service Bus), with the oversell race closed by an atomic conditional UPDATE under deterministic lock ordering plus a schema CHECK backstop (InventoryAllocationService.cs:71-73, InventoryItemConfiguration.cs:57-59) and destructive migrations blocked at the merge gate (deploy.yml:365-416).
    3. Exemplary DevOps / operational floor: §17 (impl 9) / §31 / §12: two-phase Bicep, OIDC + Key Vault MI, passwordless MI-SQL active in prod, post-deploy smoke gate with auto-rollback (rollback loop deploy.yml:1566 over the app list at :1468), cost-guard/dr-drill/load-test workflows.
    4. Reference front-end security, §26 (impl 9): in-memory access token + HttpOnly refresh cookie (no localStorage), hardened origin-pinned CSP, runtime-config fetch (ServerTokenStorageService.cs:9-12, BlazorCspPolicyProvider.cs:105).
    5. Drilled DR + real erasure path (§29 impl 9 / §30 impl 8): recorded 28.9-min restore (DISASTER-RECOVERY.md:209, drill-history table :207-212), the dr-freshness deploy gate + weekly cron + CI-gated GracefulShutdownTests, IAnonymizable anonymize-in-place + export + residency/PII fitness functions.

    Scoring notes

    • Two axes per category: Maturity (0-4, process/governance) and Implementation (0-10, substance/execution). The indices are computed deterministically from the table: every non-N/A category is in both denominators.
    • N/A (excluded from denominators): §16 AI-Native Application Architecture (rubric v2, ADR-110: no product feature calls a model); its weight 2 leaves both denominators, Σweight 79.
    • §10 is Messaging & Integration Architecture under rubric v2, at the v2 default weight 3.
    • §27 is scored: ADR-027 (en-US + es with a CI-gated translation-completeness fitness function) supersedes ADR-011's single-locale exclusion.
    • §32 weight = 2 (default; 3 only for the published framework MMCA.Common).
    • The implementation index reads directly against 100%: a 10 is awardable for an almost perfect implementation. The denominators stay ×4 and ×10 so the trend line stays comparable across re-scores.
    • Axis calibration: a new CI gate is an enforcement gain and scores on the maturity axis, not the implementation axis; a CI-cadence change is not a substance regression; documentation drift scores on the implementation axis.
    • Axis-gap reading: §21 and §12 are M3/I8, strong substance with enforcement short of automatic, which is the healthy direction of the gap. The maturity-over-implementation gap sits in the 18 categories at M4/I8, where enforcement is automatic but substance is short of 9.
