    MMCA Business Specification Document

    As of: 2026-10-27 (MMCA.Store #236, MMCA.Common v1.265.0).

    1. System Overview

    MMCA is an e-commerce platform built with .NET 10.0 using DDD and Clean Architecture. The business logic is organized as modules (Catalog, Sales, Identity), each running as its own service host behind a YARP Gateway. The storefront is branded C.A.S.A Boutique. It enables shoppers to browse a product catalog, fill a bag, check out with or without an account, and pay; customers additionally keep a server-side cart, an order history and a profile. Administrators manage the product catalog, inventory, order fulfillment, user accounts and role permissions.

    The system operates in the online retail / e-commerce domain, supporting the full purchase lifecycle from product browsing through payment and delivery.

    Major Business Areas:

    • Product Catalog Management: categories, products, and product variants with pricing and promotions
    • Shopping & Ordering: cart management, customer checkout, guest checkout (no account), order placement
    • Shipping & Tax: a flat shipping rate with a free-shipping threshold, optional Stripe Tax sales tax, a shipping label per order
    • Payment Processing: Stripe-integrated checkout with webhook confirmation, a per-order payment deadline, and a reconciliation sweep
    • Order Fulfilment: carrier shipment tracking from payment through delivery
    • Inventory Management: stock tracking per product variant
    • Product Reviews: verified-purchase star ratings and reviews, with moderation
    • Customer Identity & Authentication: registration, login, multi-device refresh sessions, password reset, email confirmation
    • Administration: user accounts (lock, unlock, change role) and role-to-permission grants

    Technical Stack:

    • .NET 10.0 (LangVersion: preview), Blazor Server + WebAssembly hybrid (InteractiveAuto), MudBlazor UI, installable web app (manifest plus service worker)
    • SQL Server, one database per service (Store_Catalog, Store_Identity, Store_Sales)
    • Stripe payment gateway and Stripe Tax, PBKDF2-HMAC-SHA512 password hashing, JWT authentication
    • .NET Aspire orchestration (SQL Server container, Redis, a message broker, MailDev, the Stripe CLI, Gateway :6001, 3 service hosts, UI :6002)

    Property Description

    2.3 Product Variant

    Description: A specific purchasable configuration of a product (e.g., "Gold Ring - Size 7"). Variants carry the actual price and SKU used for inventory and order processing.

    Key Properties:

    Property Description
    SKU Stock-keeping unit identifier (max 50 chars, globally unique, optional)
    Price LIST unit price as Money (amount + currency, must be non-negative). A discount never rewrites it, so clearing the discount restores the original price with no bookkeeping
    Discount Optional promotional pricing as an owned VariantDiscount value object: either a percentage off or a fixed special price, with an optional activation window (inclusive start, exclusive end, either bound open) and an optional storefront label (max 50 chars)
    Effective price Derived, never stored: GetEffectivePrice(now) returns the list price with the discount applied when the window covers that instant, and the list price otherwise

    Relationships:

    • A Product Variant belongs to exactly one Product
    • A Product Variant has zero or one Inventory Item
    • A Product Variant can appear in Shopping Cart Items and Order Lines

    Source: Source/Modules/Catalog/MMCA.Store.Catalog.Domain/Products/ProductVariant.cs, Source/Modules/Catalog/MMCA.Store.Catalog.Shared/Products/VariantDiscount.cs

    2.4 Shopping Cart

    Description: A temporary collection of items a customer intends to purchase. Each customer has exactly one shopping cart (the cart ID equals the customer ID).

    Key Properties:

    Property Description
    Status Active or CheckedOut
    ShoppingCartItems Collection of items in the cart

    Relationships:

    • A Shopping Cart belongs to exactly one Customer (1:1 relationship, ID = CustomerId)
    • A Shopping Cart contains zero or more Shopping Cart Items

    A shopper who has not signed in has no Shopping Cart aggregate: their bag lives on the device (variant ids and quantities only) and is merged into the server cart when they sign in (Section 11.2).

    2.6 Order

    Description: A confirmed purchase transaction created when a customer checks out their shopping cart, or when a shopper with no account places a guest order. Orders track payment status and progress through a defined lifecycle.

    Key Properties:

    Property Description
    CustomerId The customer who placed the order, or null for a guest order (Order.cs:49)
    IsGuest Computed: true when CustomerId is null (Order.cs:52)
    CustomerName The customer's full name frozen at checkout (the guest's name on a guest order), max 201 characters. Marked [Pii]
    ContactEmail The guest's email, where a guest order's mail goes; null on a customer's order, whose address Identity owns. Max 100 characters. Marked [Pii] (Order.cs:59)
    ContactPhone Optional contact phone given at checkout for the carrier, max 30 characters. Marked [Pii]
    ShippingAddress / BillingAddress Frozen at checkout exactly as entered (Address value objects); billing equals shipping when the shopper says so. Marked [Pii]
    ShippingLabel The label generated when the order was placed, attached only when the order has a shipping address (value object)
    GuestAccessTokenHash Hex SHA-256 of a guest order's private access token; null on a customer's order and once a guest order is claimed into an account (Order.cs:90)
    Subtotal The sum of all line totals: what the merchandise costs before shipping and tax
    ShippingCost / TaxAmount The shipping and sales tax charged, zero when free or when none applies
    TaxCalculationId The tax provider's id for the calculation behind TaxAmount, or null when none was made
    Total What the order charges: Subtotal + ShippingCost + TaxAmount. The amount the payment session asks for and a payment has to match (Order.cs:111)
    TotalSavings Computed: the sum of every line's Savings, in the order's currency. Zero when nothing on the order was discounted. Derived on read, never persisted
    Status Current lifecycle stage (see state machine below)
    LineCount The number of lines the order was created with, denormalized for list views
    StripeSessionId Payment gateway session reference
    StripePaymentIntentId Payment confirmation reference ("manual-admin-override" for a manual payment)
    InventoryRestored The idempotency marker for the compensation that returns stock after a cancellation
    Shipment The parcel the order left with (carrier, tracking number, dates), or null before it ships (value object)
    FulfilledPublishedOn When the OrderFulfilled integration event was published for this order; the idempotency marker the startup backfill sweeps on

    Relationships:

    • An Order belongs to one Customer, or to no account (a guest order) until it is claimed
    • An Order contains one or more Order Lines

    Erasure: the aggregate is IAnonymizable: anonymizing clears CustomerName, ContactEmail, ContactPhone and both addresses (Order.cs:432).

    Source: Source/Modules/Sales/MMCA.Store.Sales.Domain/Orders/Order.cs, Source/Modules/Sales/MMCA.Store.Sales.Domain/Orders/OrderCharges.cs, Source/Modules/Sales/MMCA.Store.Sales.Domain/Orders/OrderDelivery.cs

    2.7 Order Line

    Description: A single item within an order, capturing the product variant, quantity, and price at time of purchase.

    Key Properties:

    Property Description
    ProductVariantId The product variant ordered
    Quantity Units ordered (must be positive)
    UnitPrice Price per unit actually charged at time of order (Money)
    ListPrice The undiscounted price the charge was struck from (Money), frozen alongside UnitPrice. Equal to UnitPrice when no promotion was in force
    PromotionLabel The storefront name of the promotion that moved the price (max 50 characters), or null when none was in force or the one in force carried no label
    LineTotal Computed: UnitPrice x Quantity
    Savings Computed: (ListPrice - UnitPrice) x Quantity, in the line's currency. Zero when the line was not discounted. Derived on read, never persisted

    Relationships:

    • Belongs to exactly one Order

    Description: An authentication account with credentials and role-based access. Users are either administrators or customers, and each account holds exactly one role.

    2.12 Product Review

    Description: A shopper's review of a product: a star rating plus optional headline and text, written by a customer who received the product. Every review is a verified purchase by construction, so the aggregate carries no "verified" flag of its own.

    Key Properties:

    Property Description
    ProductId The reviewed product
    CustomerId The customer who wrote it
    OrderId The delivered order that entitled them to write it
    Rating Star rating, 1 through 5
    Title / Body Optional headline and text
    ReviewerName Display name frozen at submission from the caller's token, so a later profile rename does not rewrite published content. Marked [Pii]
    Status Published (the state every review is created in) or Hidden (moderator action)

    Relationships:

    • One review per (customer, product); the entitling order is recorded on the row
    • Counted into the product's RatingSummary while published and not deleted

    Erasure: the aggregate is IAnonymizable (ADR-005). Anonymizing clears the reviewer name, title and body and keeps the rating, because a bare star with no name and no words identifies nobody while removing it would silently rewrite every product average an erasure touched.

    Source: Source/Modules/Catalog/MMCA.Store.Catalog.Domain/Reviews/ProductReview.cs

    2.13 Verified Purchase

    Description: Catalog's own record that a customer received a product: one row per (order, product). It is the entitlement behind a review, so "verified purchase" is answerable without a query into Sales.

    Key Properties:

    Property Description
    ProductId The product the customer received
    CustomerId The customer who received it
    OrderId The delivered order the entitlement came from
    DeliveredOn When the order was marked delivered (UTC)

    Relationships:

    • Written only by the consumer of Sales' OrderFulfilled integration event; nothing else creates one and nothing revokes one (delivery is terminal, so an entitlement earned stays earned)
    • Unique on (OrderId, ProductId), which is the database-level backstop for an at-least-once redelivery

    Carries no personal data (three identifiers and a date), so it is deliberately neither audited nor anonymizable, and it is deliberately not repeated in the data-subject export: it is a derived copy of order facts Sales already owns and already exports.

    3. Business Workflows

    3.1 Customer Registration

    Trigger: A new user submits registration with first name, last name, email, and password.

    Steps:

    1. Validate registration request (email format, password requirements) and apply the registration rate limit
    2. Verify email is not already registered (uniqueness check)
    3. Hash the password using PBKDF2-HMAC-SHA512 (210,000 iterations) with a per-user salt
    4. Create a User entity with "Customer" role
    5. Domain event UserRegistered is published, which drives two independent handlers:
      • UserRegisteredHandler creates a Customer with the same name, email, and address and links the User to it via CustomerId, both in one transaction. When a Customer with that email already exists (typically created by an administrator) the account is deliberately left unlinked, because registration does not prove ownership of the address; an administrator links it by hand (Section 3.15)
      • UserRegisteredEmailConfirmationHandler schedules the confirmation email as the Identity.SendEmailConfirmation internal command (Section 3.14)
    6. Re-read the user untracked so the first token already carries the customer_id claim
    7. Issue a JWT access token (15 min; claims sub, jti, iat, name, email, role, customer_id when linked, sid, and one permission claim per capability the role holds) and a refresh token (7 days) stored as its own refresh-session row
    8. Return authentication tokens to the caller (HTTP 201)

    Implemented in:

    • Source/Modules/Identity/MMCA.Store.Identity.Application/Users/AuthenticationService.cs (over the framework's AuthenticationServiceBase<User>)
    • Source/Modules/Identity/MMCA.Store.Identity.Application/Users/DomainEventHandlers/UserRegisteredHandler.cs
    • Source/Modules/Identity/MMCA.Store.Identity.Application/Users/DomainEventHandlers/UserRegisteredEmailConfirmationHandler.cs

    3.2 Customer Login

    Trigger: A registered user submits email and password.

    Steps:

    1. Validate login request and check the lockout state for the address (ADR-029)
    2. Look up user by email
    3. Verify password using PBKDF2-HMAC-SHA512 with constant-time comparison; a miss counts as a failed attempt
    4. Verify user is active (Auth.UserDeactivated, checked after the password so only the account owner learns it, AuthenticationService.cs:112)
    5. Reset the failed-attempt counter and issue a new access token plus a new refresh-session row (one per signed-in device)
    6. Upgrade the stored hash when it is in the earlier format or at another iteration count; a rehash failure never fails a sign-in that already succeeded
    7. Return authentication response with both tokens

    Token refresh (POST /Auth/refresh) rotates the presented refresh token and treats a token that was already rotated as reuse (ADR-050); the deactivated-account gate runs on refresh too, so a locked account stops refreshing immediately. A signed-in user can list their sessions (GET /Auth/my-sessions) and sign one device out (POST /Auth/revoke/{sessionId}) or the current one (POST /Auth/revoke).

    Implemented in:

    • Source/Modules/Identity/MMCA.Store.Identity.Application/Users/AuthenticationService.cs (over the framework's AuthenticationServiceBase<User>)
    • Source/Modules/Identity/MMCA.Store.Identity.API/Controllers/AuthController.cs

    3.3 Add Item to Shopping Cart

    Trigger: An authenticated customer adds a product variant to their cart.

    Steps:

    1. Validate the request (quantity must be positive)
    2. Verify the product variant exists in the Catalog (cross-module check via IProductVariantService)
    3. Fetch or create the customer's shopping cart
    4. If the cart was previously checked out, reactivate it (clears all old items, sets status back to Active)
    5. If the same product variant already exists in the cart, increase its quantity
    6. Otherwise, add a new cart item
    7. Persist changes

    Business Rules Applied:

    • Cart must be in Active status to accept items (or will be reactivated)
    • Product variant must exist in the catalog
    • Quantity must be greater than zero
    • Duplicate variants merge (quantities are combined)
    • Reactivation clears all previous items

    Implemented in:

    • Source/Modules/Sales/MMCA.Store.Sales.Application/ShoppingCarts/UseCases/AddItem/AddItemHandler.cs
    • Source/Modules/Sales/MMCA.Store.Sales.Domain/ShoppingCarts/ShoppingCart.cs (AddShoppingCartItem)

    3.4 Checkout (Cart to Order)

    Trigger: A customer (or an admin on the customer's behalf) checks out an active shopping cart with PUT /ShoppingCarts/{id}/checkout. The optional body carries the shipping address, the billing address and a phone; an empty body checks out with no addresses and therefore no shipping label, which is how the admin cart page checks a cart out on a customer's behalf.

    Steps:

    1. Fetch the customer's shopping cart with all items, and validate the delivery addresses (a missing billing address takes the shipping address) before any cross-service call
    2. Retrieve current pricing for all product variants from the Catalog module (cross-module call): the effective price, the list price it was struck from, and the active promotion's label. Reject the checkout if any variant is missing from the price map (it was soft-deleted between cart-add and checkout), naming the offending variant. Resolve the customer's display name from Identity (best effort)
    3. Quote the charges: a flat shipping rate waived at the free-shipping threshold, and sales tax when tax is enabled and a ship-to address is known (Section 3.16)
    4. Inside one retriable transaction, fetch inventory items for all product variants and execute the checkout domain service, which: a. Validates the cart is not empty b. Validates inventory exists for every item in the cart c. Runs a fail-fast sufficiency check per item against the loaded snapshot d. Creates Order Lines with the current pricing triple (price snapshot at time of purchase) e. Creates the Order with status PendingPayment, the frozen customer name, addresses and phone f. Transitions the cart to CheckedOut status
    5. Apply the quoted shipping and tax to the order (Order.ApplyCharges), refuse the checkout when the bag changed between the quote and the order (Order.Charges.BagChanged, OrderQuoteApplier.cs:28), and refuse a total below what the payment provider can charge (CheckOutHandler.cs:188)
    6. In the same transaction: the order insert, the atomic conditional inventory decrements, the cart transition, then the shipping label (only when the order has a shipping address; a label failure is logged, never fatal) and the order's payment deadline (Section 3.17)
    7. Return the Order details

    Business Rules Applied:

    • Cart must contain at least one item
    • Every product variant must still exist in the Catalog module
    • All product variants must have corresponding inventory records
    • Sufficient inventory must be available for each item
    • Prices are locked at checkout time (not at cart-add time)
    • The order total is Subtotal + ShippingCost + TaxAmount, and it must be chargeable by the payment provider
    • The price locked is the effective price: Catalog resolves each variant's list price against any active discount at the instant of the call, so the order line, the receipt and the Stripe total all carry the discounted amount and Sales never reasons about promotions (ADR-112)
    • The list price and the promotion label are frozen beside the effective price on the same line, so the order can say what it saved later without asking Catalog again. Only the effective price is money owed: the line total, the order total and the Stripe amount all follow from it alone
    • The write phase is atomic, but the command is deliberately not ITransactional: the handler opens the transaction itself so the cross-module price fetch stays outside it and cross-service latency never extends lock hold time

    Concurrency: the domain service's sufficiency check reads a point-in-time snapshot and is only a fail-fast. The real oversell guard is IInventoryAllocationService.DecrementAsync, which issues one atomic conditional UPDATE per variant: a row that no longer has enough stock matches zero rows, the Result fails, and the whole transaction rolls back. Because that path uses ExecuteUpdateAsync it bypasses the save pipeline, so no InventoryAdjusted domain event is raised on checkout.

    Implemented in:

    • Source/Modules/Sales/MMCA.Store.Sales.Application/ShoppingCarts/UseCases/CheckOut/CheckOutHandler.cs
    • Source/Modules/Sales/MMCA.Store.Sales.Application/ShoppingCarts/UseCases/CheckOut/CheckOutPreflight.cs
    • Source/Modules/Sales/MMCA.Store.Sales.Application/ShoppingCarts/UseCases/CheckOut/PlacedOrderFinalizer.cs
    • Source/Modules/Sales/MMCA.Store.Sales.Domain/Orders/CheckOutDomainService.cs

    3.5 Payment Processing (Stripe)

    Trigger: After checkout, the customer initiates payment for a pending order (POST /Orders/{id}/checkout); a guest pays through POST /Orders/guest/{id}/checkout with the order's access token, which runs the same use case (Section 3.18).

    Steps:

    1. Fetch the order with its order lines and check it is payable before Stripe is called: a PendingPayment order, or a PaymentFailed order on retry, gets a new session; a PaymentInitiated order resumes the session it is waiting on rather than opening a second one (an expired session is retired through PaymentFailed first); every other status is refused
    2. Call Stripe API to create a checkout session (converts Money to smallest currency unit: cents). The session carries the subtotal, shipping and tax, which must add up to the order total (Payment.Stripe.ChargesDoNotAddUp, StripePaymentService.cs:153), and it expires when the order's unpaid window closes, clamped to what Stripe accepts (StripePaymentService.cs:166)
    3. Transition order status to PaymentInitiated
    4. Store the Stripe session ID on the order
    5. Return the checkout URL for the customer to complete payment

    Webhook Confirmation (asynchronous):

    1. Stripe sends a webhook notification to POST /Payments/webhook
    2. System verifies the webhook signature with Stripe's EventUtility.ValidateSignature() against either trusted signing secret (the runtime one and the configured Stripe:WebhookSecret), then parses the body as a separate step with EventUtility.ParseEvent() (StripePaymentService.cs:644, :374)
    3. Based on event type:
      • checkout.session.completed -> Mark order as Paid, store payment intent ID, but only when the session is paid and the amount and currency it collected match the order total (PaymentProof, the one rule every path that marks an order paid from provider data applies)
      • checkout.session.expired or payment_intent.payment_failed -> Mark order as PaymentFailed
    4. Idempotent: skips processing if order is already in the appropriate terminal state

    In production StripeWebhookRegistrationService verifies (or creates) the Stripe webhook endpoint at startup; locally the Stripe CLI started by the Aspire AppHost forwards events to the Gateway.

    Implemented in:

    • Source/Modules/Sales/MMCA.Store.Sales.Application/Orders/UseCases/CreateCheckoutSession/CreateCheckoutSessionHandler.cs
    • Source/Modules/Sales/MMCA.Store.Sales.Application/Orders/UseCases/ProcessPaymentWebhook/ProcessPaymentWebhookHandler.cs
    • Source/Modules/Sales/MMCA.Store.Sales.Application/Orders/Interfaces/PaymentProof.cs
    • Source/Modules/Sales/MMCA.Store.Sales.Infrastructure/Payments/Stripe/StripePaymentService.cs

    3.6 Order Cancellation

    Trigger: A customer or admin cancels an order (PUT /Orders/{id}/cancel, mandatory If-Match), or a guest cancels from the private link (POST /Orders/guest/{id}/cancel, Section 3.18), which runs the same use case. The order's payment deadline (Section 3.17) and the reconciliation sweep reach the same Cancelled state, the same compensation and the same notice.

    Steps:

    1. Fetch the order with its order lines
    2. Validate the order is in a cancellable state (PendingPayment, PaymentInitiated, or PaymentFailed)
    3. For a PaymentInitiated order, retire the Stripe checkout session first, so the hosted page can no longer take money; a session Stripe reports already paid refuses the cancellation (the order needs a refund, not a cancel)
    4. Transition order status to Cancelled and persist. The cancellation commits on its own; no inventory work happens inside this transaction.
    5. After the commit, the OrderCancelled domain event drives OrderCancelledSagaHandler, which runs in its own DI scope and restores inventory for each order line
    6. Independently of the saga, OrderCancelledHandler schedules the Sales.SendOrderCancelledEmail internal command with the event's OrderCancellationReason (OrderCancelledHandler.cs:36-41). The email goes to the order's recipient (the customer, or a guest's contact email): Requested reads as "Order Cancelled", and PaymentExpired (the deadline and the sweep) as "Your unpaid order expired" with its items released (SendOrderCancelledEmailInternalCommandHandler.cs:54-78)

    Business Rules Applied:

    3.8 Order Shipping and Delivery

    Trigger: An administrator records that a paid order left with a carrier, corrects what was recorded, or confirms the order arrived.

    Ship (PUT /Orders/{id}/ship, OrdersManage permission, mandatory If-Match):

    1. Fetch the order
    2. Validate status is Paid (the only state that may ship)
    3. Build the Shipment value object: carrier, tracking number, ship date, optional estimated delivery
    4. Transition status to Shipped and raise OrderShipped
    5. Persist changes; OrderShippedHandler schedules the Sales.SendOrderShippedEmail internal command, which emails the order's recipient (the customer, or a guest's contact email) the carrier, the tracking number and the tracking link

    Correct the shipment (PUT /Orders/{id}/shipment, OrdersManage permission, mandatory If-Match): Same request body, because the shipment is a value object and a correction replaces it whole rather than patching a field. Allowed from Shipped only, and the status does not move. OrderShipped is raised again on purpose, so a customer who was told the wrong tracking number gets the right one. The two verbs stay separate endpoints deliberately: ship must refuse an already-shipped order, the correction must refuse an order that never shipped, and folding them together would make "silently re-ship" indistinguishable from "fix the tracking number".

    Deliver (PUT /Orders/{id}/deliver, OrdersManage permission, mandatory If-Match):

    1. Fetch the order
    2. Validate status is Paid or Shipped (the carrier leg is optional; see the state machine)
    3. Transition status to Delivered, stamp FulfilledPublishedOn, and raise the in-process OrderDelivered domain event; on a customer's order also raise the OrderFulfilled integration event carrying the delivered line snapshot. A guest order has no account to hold a verified purchase, so it raises no OrderFulfilled (Order.cs:756)
    4. Persist changes; OrderFulfilled leaves through the outbox and Catalog turns it into the verified-purchase entitlements behind product reviews (Section 3.13)
    5. After the commit, OrderDeliveredHandler schedules the Sales.SendOrderDeliveredEmail internal command (OrderDeliveredHandler.cs:32-34), which tells the order's recipient (the customer, or a guest's contact email) that the order was delivered (SendOrderDeliveredEmailInternalCommandHandler.cs:43-58)

    Tracking links: for UPS, FedEx, USPS and DHL the public link is computed from the carrier's own template plus the tracking number, so the URL is written down in exactly one place; only the Other carrier accepts a caller-supplied absolute https URL, and supplying one for a known carrier is refused rather than stored as a second copy that could contradict the template.

    Backfill: OrderFulfilledBackfillService is a settings-gated, bounded one-shot startup sweep that publishes OrderFulfilled for orders that reached Delivered before the event existed, which is the only way those customers can ever review what they demonstrably bought. Order.FulfilledPublishedOn is the marker: the sweep selects only Delivered orders where it is still null, and the marker and the outbox row commit in the same unit of work, so a run converges, every later start is a no-op, and a host that dies mid-sweep resumes where it stopped.

    3.12 Password Reset

    Trigger: A customer who cannot sign in asks for a reset link from /forgot-password, then sets a new password on /reset-password.

    Steps (request):

    1. POST /Auth/forgot-password with { "email": "..." }. The request validator checks the shape of the address only
    2. Look up the account behind the address without tracking it
    3. Increment the per-address request counter and check it against the rolling-hour throttle
    4. Mint a 256-bit single-use token, store only its SHA-256 hash under the address with the configured TTL, and hand the raw token back
    5. Email the reset link ({PasswordReset:ResetUrl}#email=...&token=...) plus the raw token, so a client that cannot follow a deep link can have the token entered by hand. The address and token ride in the URL fragment, which a browser never sends to a server, so the live token stays out of access logs, telemetry and Referer headers (ForgotPasswordHandlerBase.cs:155)
    6. Return HTTP 202 Accepted, which is also what an unknown address, a throttled address and a failed email send return: the response never discloses whether an address holds an account

    Steps (reset):

    1. POST /Auth/reset-password with { "email": "...", "token": "...", "newPassword": "..." }. The new password goes through the same strength rules registration uses
    2. Validate the presented token against the stored hash in constant time and consume it before any write, so it cannot be redeemed twice
    3. Revoke every live refresh session on the account (persisted before the password is applied), because a reset is the remediation for a suspected intruder
    4. Load the account, hash the new password (PBKDF2-HMAC-SHA512), and apply it through the aggregate (User.ChangePassword, which raises UserPasswordChanged)
    5. Persist, then clear the account's login brute-force counters so a customer who was locked out can sign in immediately
    6. Return HTTP 204 No Content. Every rejection (unknown, expired, replayed, mismatched or attempt-capped token, or an unresolvable account) collapses to one generic Auth.InvalidResetToken HTTP 401

    Both endpoints are anonymous by necessity (the caller has lost the credential), carry the auth-ip per-IP rate limit that login and register carry, and are [Idempotent]. They come from the framework's PasswordResetAuthControllerBase, bound to Store's commands by a controller routed to the same Auth prefix, which the Gateway's /Auth/{**catch-all} route already forwards.

    No schema change: the token lifecycle lives entirely in the cache, so expired tokens are reaped by cache TTL rather than by a sweeper and the feature ships without a migration. A cache eviction invalidates outstanding tokens, which costs the user one more request. See ADR-091.

    3.13 Product Reviews

    Trigger: A customer who received a product rates it; anyone reads the ratings; a moderator hides a review that should not be public.

    Aggregates: ProductReview (Section 2.12) and VerifiedPurchase (Section 2.13), both in the Catalog module, with the derived RatingSummary on Product.

    Entitlement (the verified-purchase rule): a review can only be written by a customer who holds a VerifiedPurchase for the product. Those rows are minted by Catalog's consumer of Sales' OrderFulfilled integration event, one per (order, product): the event names variants, because that is all Sales knows, and Catalog resolves them to products and de-duplicates, so the entitlement is "you received this product", not "you received this variant". A variant Catalog cannot resolve is logged and skipped rather than failing the whole order's entitlements. Delivered, not Paid, is the trigger on purpose: it is terminal and never reversed, so an entitlement never needs revoking.

    Submission rules: the submit handler enforces the two checks the aggregate cannot make for itself, because both read rows outside it: no entitlement fails with Review.NotVerifiedPurchase, and a second review of the same product by the same customer fails with Review.AlreadyReviewed rather than landing as a unique-index violation. The entitling row also supplies the order the review is filed against (the lowest order id, the earliest entitlement). The reviewing customer and the frozen display name both come from the caller's validated token, never from the body.

    Rating summary: every review transition (submitted, revised, hidden, unhidden, anonymized, removed) raises the ProductReviewChanged domain event, and the handler recomputes the product's average and count from its published, non-deleted reviews rather than adjusting them incrementally, so a lost or redelivered event still converges on the right numbers.

    Moderation: reviews publish immediately (there is no approval queue). A moderator holding the catalog:reviews:moderate permission can hide a review and restore it; hidden reviews leave the storefront and drop out of the rating summary. Hide and unhide are conditional writes on the same terms as every other review write (ADR-035), so two moderators acting on the same stale list cannot silently overwrite each other.

    Erasure: Catalog consumes Identity's CustomerErased and anonymizes every review that customer wrote, soft-deleted and hidden rows included. The name, title and body are cleared and the rating is kept (ADR-005, PRIVACY.md section 5). Because the rating does not move, erasure disturbs no product average.

    Export: the reviews a customer wrote are a section of the data-subject export document, served by Catalog through the IUserCatalogExportService cross-module contract and aggregated by Identity's GET /Users/{userId}/export (Section 3.11). Hidden reviews are included: a moderator's decision does not stop the text from being the subject's own data. The verified-purchase rows are deliberately not exported, because they duplicate order facts Sales already exports.

    4. Order Status State Machine

                      InitiatePayment                     MarkAsPaid
 PendingPayment ------------------> PaymentInitiated -------------> Paid -----Ship-----> Shipped
       |                              |          ^                   |                     |
       |         MarkAsPaymentFailed  |          | InitiatePayment   | MarkAsDelivered     | MarkAsDelivered
       |                              v          | (retry)           | (no carrier leg)    |
       |                          PaymentFailed -+                   v                     |
       |                              |                          Delivered <---------------+
       |  MarkAsCancelled             |  MarkAsCancelled
       +-----------------> Cancelled <+  (PaymentInitiated cancels the same way)

 MarkAsPaidManually (admin) reaches Paid from PendingPayment, PaymentInitiated or PaymentFailed.
 MarkAsPaid (webhook, verify-payment, reconciliation sweep) reaches Paid from PaymentInitiated only.
 UpdateShipment is a self-transition on Shipped: it replaces the recorded shipment and
 re-raises OrderShipped without moving the status.

    Cancellable States: PendingPayment, PaymentInitiated, PaymentFailed. Shipped is deliberately NOT cancellable, for the same reason Paid is not: the goods and the money have both already moved. Shippable States: Paid (only) Shipment-correctable States: Shipped (only) Deliverable States: Paid, Shipped. The carrier leg is optional: a fulfilment with no tracking to record still goes Paid -> Delivered directly, which is why Paid keeps both outgoing edges. Manual Payment States: PendingPayment, PaymentInitiated, PaymentFailed Payment-initiating States: PendingPayment, PaymentFailed (a PaymentInitiated order resumes its existing session instead) Payment-failure States: PaymentInitiated (only) Terminal States: Cancelled, Delivered

    The Cancelled edges are taken by a customer or admin cancel (Section 3.6), by the order's own payment deadline (Section 3.17, from PendingPayment or PaymentFailed) and by the reconciliation sweep (Section 3.9); all three land in the same OrderCancelled compensation. Each state is its own IOrderState class under Sales.Domain/Orders/States/, selected from the order's Status.

    The OrderStatus numeric values are persisted and travel on the user_sales_export gRPC contract, so members are only ever appended: Shipped is last in the enum even though it sits mid-lifecycle.

    8.1 Stripe Payment Gateway

    Purpose: Processes online customer payments for orders.

    Business Impact: Enables the system to collect payments from customers and confirm payment success or failure asynchronously via webhooks.

    Integration Points:

    • Checkout Session Creation: Creates hosted payment pages with order details, converting internal Money values to Stripe's smallest currency unit (cents).     9. Authorization Model

    Authorization is capability-based (ADR-020): an endpoint is anonymous, requires any signed-in user ([Authorize]), or names the capability it needs with [HasPermission(...)]; ownership of a record is a separate check layered on top. There are no role-named policies.

    Gate Access Level Where it applies
    Anonymous No auth required Catalog browsing (GET categories, products, the storefront product page, the variant lookup, product images), published product reviews (GET /Reviews/by-product/{productId}/paged), login, registration, token refresh, password reset, email confirmation, the order quote, best sellers, guest checkout and the guest order endpoints (read, pay and cancel require the order's access token instead), the guest link request (always 202), payment webhooks
    Authenticated Any logged-in user Shopping cart operations, order viewing and paying (own), cancelling an own order, profile management, preferences, session management, writing and revising own reviews, claiming a guest order
    Permission A role granted the capability Catalog, inventory and fulfilment management, manual payment, review moderation, customer, user and role administration (table below)

    Permissions: each module declares its capabilities in {Module}Permissions and grants them to roles in {Module}PermissionGrants (Shared layer), applied both by the module's own API registration and by the token-minting host. Admin holds every one; Customer holds none. The token carries one permission claim per capability its role holds, so a client gates its own surface on a capability rather than a role name.

    Module Permission Guards

    Catalog catalog:products:manage Product create, delete, attribute edits, CSV export

    Beyond the compiled grants, an operator can attach further STORED grants to a role through PUT /Admin/Roles/{role}/permissions (Section 3.15).

    Writing a review needs a customer profile, not a role. The reviews controller resolves the caller through the customer_id claim and fails closed when the token carries none; admins are deliberately not exempted, because writing a review is an act by a customer and an admin account with no customer profile has nothing to write one as.

    Ownership Enforcement (ADR-033):

    • OwnerOrAdminFilter guards the shopping cart and customer controllers: the route parameter id must match the caller's customer_id claim, or the caller holds the Admin role. It denies by default when the owner cannot be resolved and returns 403 Forbidden.
    • Orders scope every query to the caller through OrdersByCustomerSpecification and check ownership on every mutation; a resolvable caller who does not own the order is answered 404, not 403, so another customer's order ids cannot be probed. A caller with no resolvable customer_id is refused outright.
    • Data-subject export and erasure authorize the owner or an Admin inside the handlers.

    JWT Claims: Access tokens contain: sub, jti, iat, name (the linked customer's display name, never the email), email, role, customer_id (when applicable), sid (the refresh session) and one permission claim per capability (TokenService.cs:116-121, :141).

    Service-to-service calls: the Identity customer gRPC service requires either an end user's JWT or a service token minted with the shared Grpc:ServiceToken signing key, because the order emails run from the anonymous Stripe webhook with no user token to forward.

    12.2 Idempotency

    The IdempotencyFilter (applied via [Idempotent] on create and checkout endpoints) caches the first response for a given Idempotency-Key header value for 24 hours (IdempotencyFilter.cs:81). Duplicate requests receive the cached response with an X-Idempotent-Replay: true header. The cache key binds the caller's identity, the HTTP method and the route template, and a key reused with a different request body is answered 422 rather than replayed. Concurrent duplicates are serialized by a distributed lock when the host registers one (both deployed apps run more than one replica) and by a per-process keyed lock otherwise; a cache or lock fault degrades to executing without the guarantee rather than failing the request. Endpoints that must re-evaluate state on every call are marked [NonIdempotent] with a reason.

    12.3 Exception Handling

    Five exception handlers (registered as middleware in priority order):

    1. OperationCanceledExceptionHandler -> HTTP 499
    2. DomainExceptionHandler -> HTTP 400
    3. DbUpdateExceptionHandler -> HTTP 409 Conflict (a concurrency conflict is counted on its own metric)
    4. ValidationExceptionHandler (FluentValidation) -> HTTP 400 with grouped errors
    5. GlobalExceptionHandler -> HTTP 500 (catch-all)

    12.4 Data Storage

    Each service owns its database and outbox (ADR-006): Catalog, Identity and Sales each read the DataSources:{Module} connection (Store_Catalog, Store_Identity, Store_Sales) and migrate through their own MMCA.Store.Migrations.SqlServer.{Module} assembly. Every Store data source is SQL Server; the framework's IDbContextFactory strategy also supports SQLite and Cosmos DB engines, which no Store data source selects. Entity types are routed to data sources via the [UseDataSource] attribute, and the IDataSourceService caches entity-to-datasource mappings.

    12.5 Optimistic Concurrency

    Conditional writes carry [SupportsIfMatch]: the response to a read carries an ETag, the If-Match header is mandatory on the guarded mutation, a stale tag is answered 412 Precondition Failed and a missing one 428 Precondition Required (SupportsIfMatchAttribute.cs:16, ADR-035). It guards the rename, re-parent, attribute, SKU, price and discount edits, image reordering, inventory increase and decrease, the order transitions (pay, ship, shipment, deliver, cancel), review revision and moderation, and the customer profile edits.

    12.6 Internal Commands and the Outbox

    Work that must survive a host restart after the triggering transaction committed is scheduled as a durable internal command row and run by the framework's processor (ADR-114).     14. Missing or Unclear Business Logic

    14.1 No Email When a Signed-In Customer Places an Order

    Observation: Email goes out for the password reset and the email confirmation (Sections 3.12, 3.14), the guest's order-received message and a guest's replacement order link (Section 3.18), the payment confirmation (which prints a struck "Was" amount and the promotion label on a discounted line and a "You saved" total when the order saved anything), the shipping notice (re-sent on every shipment correction), the payment-failed notice, the delivery notice (OrderDeliveredHandler) and the cancellation notice (OrderCancelledHandler). The cancellation notice covers all three cancellation paths, worded by the event's OrderCancellationReason: a customer, guest or administrator cancel reads as a cancellation, and the payment deadline (Sales.ExpireUnpaidOrder) or the payment reconciliation sweep reads as an unpaid order that expired (SendOrderCancelledEmailInternalCommandHandler.cs:54-56). The delivery and cancellation notices go to customers and guests alike (OrderRecipient). A signed-in customer gets no email when the order is placed (OrderChanged with the Added state); that absence is deliberate: the payment confirmation is the customer's receipt. Recommendation: None; the signed-in order-placed email is deliberately absent, and this entry records the decision so the absence is not mistaken for a gap.

    14.2 No Return/Refund Workflow

    Observation: Cancellation is possible only from PendingPayment, PaymentInitiated and PaymentFailed. Once an order is Paid it can only move forward: to Shipped or straight to Delivered, then from Shipped to Delivered, with shipment corrections allowed while Shipped. Delivered and Cancelled are terminal. No return, refund or exchange workflow exists, and the payment service has no refund operation. A cancel that finds the Stripe session already paid is refused with a message saying the order must be refunded instead, which the system cannot do, so any refund happens outside the system and the order keeps its paid status. Recommendation: Clarify whether returns/refunds are in scope and whether Stripe refund integration is needed.

    14.3 No Inventory Check at Cart-Add Time

    Observation: When a customer adds an item to the cart, the system verifies the product variant exists but does not check if inventory is available. Stock is checked and reserved only at checkout (an atomic conditional decrement), and the cart shows no stock indicator; only the administrator inventory pages show in-stock and out-of-stock status. Recommendation: This may be intentional (allowing customers to add items that are temporarily out of stock) or may warrant a stock availability indicator on the cart.

    14.4 A Customer's Failed or Cancelled Order Does Not Restore the Bag

    Observation: A guest's device bag is not affected: guest checkout keeps it and takes the ordered lines out only once the order is paid (Section 3.18), so an abandoned, failed, expired or cancelled guest order leaves the bag as it was. A signed-in customer's server cart behaves differently. The cart turns CheckedOut when checkout creates the order, before payment. The next add reactivates it and soft-deletes the previous lines (ShoppingCart.Reactivate), which is correct for an order that goes on to be paid, because those lines have become the order. When the order's payment fails, its payment deadline expires or it is cancelled, the lines are not returned to the bag: the shopper rebuilds it by hand. A PaymentFailed order can still be paid again from the order itself, but a cancelled or expired one cannot. Recommendation: Decide whether a cancellation (and possibly a payment failure) should restore the order's lines to a customer's bag, which would be a handler on OrderCancelled or OrderPaymentFailed, or whether starting over is the intended recovery.

    14.5 Prices Can Change Between Bag and Checkout Without Notice

    Observation: Product variant prices can be changed at any time by administrators, and a cart line stores no price: every line is priced at checkout, not at cart-add time. The cart drawer and the checkout page show a server quote at the prices current when it was drawn, but checkout does not compare against that displayed quote. It builds a fresh quote from the prices it fetches in the same request, and Order.Charges.BagChanged compares the order against that fresh quote, so it fires only when the bag's contents change during the checkout request itself (an item added in another tab), never on a price change. A price that moved after the shopper last saw the drawer is charged at the new amount with nothing flagged; the Stripe payment page is the only place the final amount appears before payment. Recommendation: Decide whether checkout should carry the displayed quote (or its subtotal) and refuse or re-confirm when the charge differs, and whether the bag should mark lines whose price moved since they were added, which needs the add-time price stored on the cart line.

    14.6 One Parcel Per Order

    Observation: Delivery tracking exists (Section 3.8): an order carries a single Shipment value object with a carrier, a tracking number and the two dates. An order that physically leaves in two parcels can therefore only record one of them, and correcting the recorded shipment replaces it rather than adding to it. Recommendation: A second parcel needs the shipment to become a collection on the order, which is the same modelling change 14.7 asks for; clarify whether split shipments are a real business case before making it.

    14.7 No Partial Order Fulfillment

    Observation: Orders are delivered as a whole: there is no concept of partial shipments or split deliveries, and Shipped applies to the order rather than to individual lines. Recommendation: Clarify if partial fulfillment is a future requirement.

    14.8 Shipping Labels Come From a Mock Carrier

    Observation: Every order with a ship-to address gets a ShippingLabel at placement, but the only registered IShippingLabelProvider is MockShippingLabelProvider, which invents a CASA- label number and a MOCK tracking number with no carrier call. The label and the shipment the admin records when shipping (Section 3.8) are separate records: nothing carries the label's tracking number into the shipment, which the admin types into the ship dialog. The dialog pre-fills only from an already-recorded shipment, when correcting one, never from the label. Recommendation: Decide on a carrier integration and whether the label's tracking number should seed the recorded shipment.

    14.9 Sales Tax Is Off by Default

    Observation: Tax:Enabled defaults to false (TaxSettings.cs:18) and no appsettings or infrastructure file sets the Tax section, so every quote and every order carries zero tax until Stripe Tax and the store's registrations are activated on the account. Recommendation: Confirm the tax registrations and the go-live date for collecting sales tax.

    14.10 Email Confirmation Is Not Enforced

    Observation: Accounts are sent a confirmation link and IsEmailConfirmed is recorded, but RequireConfirmedEmail is false, so an unconfirmed account signs in and checks out exactly like a confirmed one. Registration also deliberately leaves an account unlinked from an existing Customer with the same address, which an administrator must link by hand (PUT /Users/{userId}/customer-link). Recommendation: Decide whether confirmation should gate sign-in (or the automatic link to an existing profile) before turning the setting on.

    14.11 Guest Purchases Earn No Review Entitlement Unless Claimed

    Observation: A guest order raises no OrderFulfilled at delivery, so a guest who never creates an account cannot review what they bought, and a guest who claims the order only after it was delivered stays without the entitlement: delivery stamps FulfilledPublishedOn even though it published nothing, the claim raises no fulfilment, and the backfill sweep skips an order whose FulfilledPublishedOn is already stamped. A guest who claims the order before delivery does earn the entitlement, because delivery reads the order's customer at that moment. Recommendation: Confirm whether a claim after delivery should publish the fulfilment for the new account.

    15. Seed Data (Initial System State)

    The system seeds the following data at startup, each module only when it is enabled and only when its configuration flag is on:

    Users (when Seeding:IncludeSampleUsers is true, IdentityModuleSeeder.cs:28):

    • Admin: one seeded administrator account (Admin role, no Customer record; credentials are environment-specific and not published)
    • Customer: one seeded demo customer account (Customer role)

    Catalog (when Seeding:IncludeSampleCatalog is true, CatalogModuleSeeder.cs:27):

    • Categories: "Jewelry" (id=1), "Watches" (id=2)
    • Product: "Gold Ring" (id=11, description "18K Gold Ring", brand: "WhatNot", category: Jewelry)
    • Variants: "Gold Ring - Size 6" ($15.00), "Gold Ring - Size 7" ($15.50), "Gold Ring - Size 8" ($16.00): all USD, the SKU doubling as the variant name (CatalogModuleDbSeeder.cs:166-168)

    Inventory (Sales, under the same Seeding:IncludeSampleCatalog flag): 100 units per variant for all 3 Gold Ring sizes (SalesModuleDbSeeder.cs:135-137). Sales resolves each SKU to its variant id through Catalog's gRPC service and skips a SKU when Catalog is unreachable; the ProductVariantChanged event creates the row later.

    Seeding is idempotent: the Identity and Catalog seeders check for existing data via ExistsAsync() before inserting. The inventory seeder creates a missing row and lifts an existing row only while it still holds zero, because any other count is live stock (SalesModuleDbSeeder.cs:97).
