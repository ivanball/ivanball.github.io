    1. Identity Module Workflows

    1.1 User Registration

    Entry Point: POST /auth/register, AuthController.RegisterAsync(), AllowAnonymous, auth-ip rate-limit policy, [NonIdempotent] (a replay would hand back tokens minted for an earlier call)

    Execution Path:

    AuthController.RegisterAsync()  (201 Created)
  -> AuthenticationService.RegisterAsync()   [AuthenticationServiceBase<User> in MMCA.Common]
    -> validate request, registration rate limit (ADR-029)
    -> EmailExistsAsync() -> Conflict when taken
    -> PasswordHasher.HashPassword() (PBKDF2-HMAC-SHA512, 210,000 iterations, per-user salt)
    -> CreateUser() -> User.Create() factory (default role Customer)
    -> Repository.AddAsync() + UnitOfWork.SaveChangesAsync()
    -> [Domain Event] UserRegisteredHandler (own DI scope, one transaction)
      -> Customer.Create() + User.LinkCustomer(customerId)
    -> [Domain Event] UserRegisteredEmailConfirmationHandler
      -> schedules Identity.SendEmailConfirmation (internal command, ADR-114)
    -> OnUserRegisteredAsync(): untracked re-fetch so the first token carries customer_id
    -> IssueTokensAsync(): access token + a new refresh session row

    Business Steps:

    1. Validate registration input (email, password, first name, last name, optional address)
    2. Check email is not already registered
    3. Hash password with PBKDF2-HMAC-SHA512 (210,000 iterations, per-user salt; PasswordHasher.cs:34)
    4. Create User aggregate (IsActive=true, Role="Customer")
    5. Persist user: triggers UserRegistered domain event
    6. UserRegisteredHandler creates the Customer profile and links it to the User
    7. UserRegisteredEmailConfirmationHandler schedules the confirmation email (1.10)
    8. Issue an access token (15 min) and a refresh token (7 days, RefreshTokenExpirationDays) stored as its own refresh-session row (ADR-097)
    9. Return the authentication response with tokens

    Decision Points:

    • Email already exists -> Conflict error
    • Role="Admin" -> no Customer profile created; Role="Customer" -> Customer auto-created
    • A Customer profile with the registering address already exists (typically created by an admin) -> the account is deliberately left UNLINKED, because registration does not prove ownership of the address; an admin links it through PUT /users/{userId}/customer-link (1.11, UserRegisteredHandler.cs:21-26)

    State Changes:

    • Creates User (Active) and one refresh session
    • Creates Customer (linked via User.CustomerId) unless the address collides

    Domain Events: UserRegistered -> UserRegisteredHandler creates the linked Customer, which raises CustomerChanged with the Added state

    1.2 User Login

    Entry Point: POST /auth/login, AuthControllerBase.LoginAsync() (MMCA.Common, inherited by AuthController), AllowAnonymous, auth-ip rate-limit policy, [NonIdempotent]

    Execution Path:

    AuthController.LoginAsync()
  -> AuthenticationServiceBase.LoginAsync()
    -> validate request
    -> loginProtection.CheckLockoutAsync()   (ADR-029 exponential-backoff lockout)
    -> FindUntrackedByEmailAsync()            (soft-deleted accounts excluded)
    -> PasswordHasher.VerifyPassword()        (constant-time; failed attempt counted on a miss)
    -> ValidateLoginCandidateAsync()          (Store gate: deactivated account rejected)
    -> tracked re-fetch by id
    -> ResetFailedAttemptsAsync()
    -> IssueTokensAsync()                     (access token + new refresh session row)
    -> RehashPasswordIfNeededAsync()          (best effort, after the tokens are issued)

    Business Steps:

    1. Check the lockout state for the address
    2. Look up user by email (untracked)
    3. Verify password against stored hash+salt
    4. Verify user is active (checked AFTER the password, so only the account owner learns it is deactivated)
    5. Issue new access + refresh tokens; the refresh token lives in its own session row, not on the user
    6. Upgrade the stored hash when the hasher reports NeedsRehash (the User implements IPasswordRehashableUser); a rehash failure never fails a sign-in that already succeeded (AuthenticationServiceBase.cs:237, :676)
    7. Return tokens

    Decision Points:

    • Locked out -> refused before any lookup
    • Email not found -> Unauthorized
    • Password mismatch -> Unauthorized (failed attempt counted)
    • User deactivated -> Unauthorized

    State Changes: a new refresh session row; the password hash when a rehash is due; the failed-attempt counter reset

    1.3 Token Refresh

    Entry Point: POST /auth/refresh, AllowAnonymous, [NonIdempotent]

    Execution Path:

    AuthControllerBase.RefreshAsync()
  -> AuthenticationServiceBase.RefreshTokenAsync()
    -> read claims from the expired access token (signature validated, lifetime skipped)
    -> fetch User from the sub claim
    -> ValidateRefreshCandidateAsync()   (Store gate: deactivated account rejected)
    -> session issuer resolves the presented refresh token, with reuse detection, and rotates it

    Decision Points:

    • Invalid/expired refresh token -> Unauthorized
    • A refresh token that was already rotated is presented again -> treated as reuse (ADR-050)
    • User deactivated -> Unauthorized

    State Changes: the refresh session is rotated (the presented token retired, a successor issued)

    Decision Points: Current password incorrect -> Unauthorized (ChangePasswordHandler.cs:12)

    All four actions are AllowAnonymous, [Idempotent] and throttled by the auth-ip policy. They come from the framework bases PasswordResetAuthControllerBase and EmailConfirmationControllerBase; Store's PasswordResetController and EmailConfirmationController only bind the Store commands.

    Workflow Endpoint Handler Notes

    Reset password POST /auth/reset-password ResetPasswordHandler Redeems the token, re-hashes, clears the lockout; one generic rejection error

    2. Catalog Module Workflows

    2.1 Category Management

    Create Category

    Every mutation on CategoriesController requires catalog:categories:manage, stated once at the controller level; the reads opt out with [AllowAnonymous].

    Entry Point: POST /categories, catalog:categories:manage, [Idempotent]

    CategoriesController.CreateAsync()
  -> CreateCategoryHandler
    -> CategoryCreateRequestValidator (name: required, max 255)
    -> Category.Create(id, name, parentCategoryId?) -> raises CategoryChanged (Added)
    -> Repository.AddAsync() + SaveChangesAsync()

    Response: 201 Created with CategoryDTO

    Rename Category

    Entry Point: PUT /categories/{id}/name, catalog:categories:manage, mandatory If-Match

    CategoriesController.RenameAsync()
  -> RenameCategoryHandler
    -> Validate name (max 255)
    -> Fetch category -> category.Rename(name)
    -> Only updates if name differs (case-insensitive comparison)
    -> Raises CategoryChanged (Updated) if changed
    -> Cache invalidation + evicts the catalog:categories and catalog:products output-cache tags

    Assign Parent Category

    Entry Point: PUT /categories/{id}/parentcategory, catalog:categories:manage, mandatory If-Match

    Sets or clears ParentCategoryId to establish hierarchy. No domain event raised.

    Delete Category

    Entry Point: DELETE /categories/{id}, catalog:categories:manage

    Soft delete (IsDeleted=true). Refused while products are assigned (Category.HasProducts) or child categories hang beneath it (Category.cs:87-99); the delete handler eager-loads both for the check. Raises CategoryChanged with the Deleted state.

    Query Endpoints

    Endpoint Auth Notes
    GET /categories AllowAnonymous Returns all categories (capped at MaxPageSize)
    GET /categories/paged AllowAnonymous Paginated with filters, sorting, field projection
    GET /categories/lookup AllowAnonymous Returns ID + name pairs for dropdowns
    GET /categories/{id} AllowAnonymous Single category with optional FK/children includes
    GET /categories/export catalog:categories:manage CSV export, inherited from EntityControllerBase; unscoped by design

    The anonymous reads are output-cached under the CategoriesCache policy.

    2.2 Product Management

    Create Product

    Entry Point: POST /products, catalog:products:manage, [Idempotent]

    ProductsController.CreateAsync()
  -> CreateProductHandler
    -> Validate: name (required, max 100), description (max 4000), brand (max 100, no whitespace if provided)
    -> Product.Create() factory -> raises ProductChanged (Added)
    -> Repository.AddAsync() + SaveChangesAsync()

    Update Operations

    Workflow Endpoint Validation Event
    Rename PUT /products/{id}/name Max 100, required ProductChanged (Updated) plus the ProductInfoChanged integration event (Updated)
    Change Description PUT /products/{id}/description Max 4000, nullable None
    Change Brand PUT /products/{id}/brand Max 100, no whitespace None
    Assign Category PUT /products/{id}/category Nullable FK None

    The four attribute edits live on ProductAttributesController (same /products prefix), which requires catalog:products:manage at the controller level; each is conditional on a mandatory If-Match header and evicts the catalog:products and catalog:categories output-cache tags.

    Delete Product

    Entry Point: DELETE /products/{id}, catalog:products:manage. Soft delete, raises ProductChanged with the Deleted state plus the ProductInfoChanged integration event (Deleted).

    Query Endpoints

    Endpoint Auth Notes
    GET /products AllowAnonymous Returns all products (capped at MaxPageSize)
    GET /products/paged AllowAnonymous Paginated with filters, sorting, field projection
    GET /products/lookup AllowAnonymous Returns ID + name pairs for dropdowns
    GET /products/storefront AllowAnonymous One page of the public shop: search, categoryId, onSale, sort, pageNumber, pageSize (default 12); returns the paged products with category, variants and images plus the X-Pagination header (ProductsController.cs:96-118)
    GET /products/variant-lookup AllowAnonymous Returns ProductVariantCartInfoDTO rows: the variant detail the cart UI needs without a per-variant round trip
    GET /products/{id} AllowAnonymous Single product with optional FK/children includes
    GET /products/export catalog:products:manage CSV export (ProductsController.cs:148-149)

    The anonymous reads ride the ProductsCache output-cache policy, whose TTL is 60 seconds rather than the 5 minutes the other Catalog policies use: a variant's effective price moves on the clock when a discount window opens or closes, with no mutation to evict on (ADR-040).

    Storefront page: GetStorefrontProductsHandler runs StorefrontProductsSpecification. The search matches the product name OR its description (a contains match, joined only when a term is given), the category and on-sale filters join only when asked for, and on-sale keeps a product with at least one variant whose discount is in force now (StorefrontProductsSpecification.cs:70-86). The six orderings are typed members of StorefrontProductSort rather than client-chosen column names (StorefrontProductSort.cs:13-32): NameAsc (the default), NameDesc, Newest, PriceAsc, PriceDesc and TopRated. The two price orderings sort by the lowest price any variant sells at right now, the effective price after a discount in force, restated as a translatable expression at the caller's clock, with a product that has no variants last in both directions; TopRated sorts by average rating and then review count; every ordering ends on name and id so a page boundary is stable (StorefrontProductsSpecification.cs:91-124).

    2.3 Product Variant Management

    Add Product Variant

    Entry Point: POST /products/{id}/productvariants, catalog:product-variants:manage, [Idempotent]

    ProductVariantsController.CreateAsync()
  -> AddVariantHandler   (AddVariantCommand: ITransactional, ICacheInvalidating)
    -> Validate: SKU (max 50), Price (positive Money)
    -> IProductVariantService.SkuExistsAsync() -> global SKU uniqueness check
    -> Fetch Product with variants
    -> product.AddProductVariant(variantId, sku, price)
      -> ProductVariant.Create() validates price not negative
      -> Raises no Catalog domain event
    -> SaveChangesAsync()
    -> schedules Catalog.PublishProductVariantChanged (internal command, ADR-114) with the
       database-generated variant id; the transactional pipeline commits that row with the variant

    Cross-Module: SKU uniqueness checked via IProductVariantService. The ProductVariantChanged (Added) integration event goes out when the scheduled internal command runs, so consumers always see the real variant id (AddVariantHandler.cs:19-23).

    Change Variant SKU

    Entry Point: PUT /products/{id}/productvariants/{variantId}/sku, catalog:product-variants:manage, mandatory If-Match

    SKU uniqueness verified globally (excluding current variant). Raises the ProductVariantChanged integration event with the Updated state if changed.

    Change Variant Price

    Entry Point: PUT /products/{id}/productvariants/{variantId}/price, catalog:product-variants:manage, mandatory If-Match

    Price must be positive. Raises the ProductVariantChanged integration event with the Updated state if changed. The price edited here is the LIST price. A variant that carries a discount re-validates it against the new price and the change is refused when the pair would be inconsistent (a special price no longer below the list price, or a percentage leaving nothing), so the discount is cleared first.

    Set Variant Discount

    Entry Point: PUT /products/{id}/productvariants/{variantId}/discount, catalog:pricing:manage

    ProductVariantsController.SetDiscountAsync()
  -> SetProductVariantDiscountCommand (If-Match product ETag + VariantRowVersion in the body)
    -> VariantDiscountRules validates kind, percentage, special price, window order, label
    -> ProductVariantSetDiscountRequest.ToDiscount()
      -> VariantDiscount.CreatePercentage() / CreateSpecialPrice() -> Result<VariantDiscount>
    -> product.SetProductVariantDiscount(variantId, discount)
      -> ProductVariant.SetDiscount() runs VariantDiscount.ApplyTo(Price) first
      -> Publishes ProductVariantChanged (Updated) with the LIST price
    -> SaveChangesAsync()
  -> Evicts the catalog:products output-cache tag

    Replaces any discount already on the variant. Returns 204; 400 on a broken invariant, 404 on an unknown product or variant, 412 on a stale ETag, 428 when If-Match is missing (ADR-035 two-token rule: the header carries the product's ETag, the body carries the variant's row version).

    Clear Variant Discount

    Entry Point: DELETE /products/{id}/productvariants/{variantId}/discount, catalog:pricing:manage

    Returns the variant to its list price, which was never rewritten, so there is nothing to restore. Clearing a variant that carries no discount changes nothing, so clearing twice is safe. Publishes ProductVariantChanged (Updated) and evicts the catalog:products tag. The body carries only the variant's row version; the status codes match the set action.

    Discount All Variants

    Entry Point: PUT /products/{id}/discount, catalog:pricing:manage

    ProductsController.SetDiscountAsync()
  -> SetProductDiscountCommand (If-Match product ETag)
    -> ProductSetDiscountRequest.ToDiscount() -> Result<VariantDiscount>
    -> product.SetDiscountOnAllVariants(discount)
      -> A product with NO active variant is refused first: Product.NoActiveVariants (400)
      -> ApplyTo() is checked against EVERY active variant's list price FIRST
      -> All-or-nothing: one refusal leaves the product exactly as it was
      -> Publishes one ProductVariantChanged (Updated) per variant, each with its LIST price
    -> SaveChangesAsync()
  -> Evicts the catalog:products output-cache tag

    A product whose variants are priced differently either takes the promotion whole or is left untouched, so a half-discounted catalog page is not reachable. A product with nothing to discount, because it has no variants yet or every one is soft-deleted, is a 400 rather than a write that succeeds over an empty set.

    Remove Product Variant

    Entry Point: DELETE /products/{id}/productvariants/{variantId}, catalog:product-variants:manage

    Soft delete on variant. Raises the ProductVariantChanged integration event with the Deleted state.

    2.5 Product Reviews

    Earn the Entitlement (OrderFulfilled -> VerifiedPurchase)

    Entry Point: the Sales.OrderFulfilled.v1 integration event, consumed by OrderFulfilledHandler in its own DI scope. No HTTP surface: nothing else in the system creates a verified purchase.

    Sales: order.MarkAsDelivered()
  -> raises OrderDelivered (in-process) AND, for a customer's order only, OrderFulfilled
     (integration, line snapshot); a guest order has no account to hold a verified purchase
  -> stamps Order.FulfilledPublishedOn in the same unit of work
  -> outbox row commits with the order write, then ships to the broker

Catalog: OrderFulfilledHandler
  -> resolve the event's variant ids to product ids in ONE projection
     (soft-deleted variants are not resolved: a delisted product stays unreviewable)
  -> de-duplicate: two sizes of the same shirt are one entitlement
  -> read the order's existing entitlement rows (first idempotency guard)
  -> VerifiedPurchase.Create() for each missing product, one SaveChangesAsync

    Idempotency: twice over. The existing-rows read means a redelivered event inserts nothing, and the unique (OrderId, ProductId) index is the backstop for two deliveries racing. Deliveries are at-least-once, so both halves are load-bearing. A variant that does not resolve is logged and skipped rather than thrown, because a redelivery would fail on it identically forever and take the customer's other entitlements down with it.

    Backfill: OrderFulfilledBackfillService publishes the event on startup for orders delivered before it existed, selecting only Delivered orders whose FulfilledPublishedOn is still null. Bounded per run and settings-gated (OrderFulfilledBackfill:Enabled).

    Submit Review

    Entry Point: POST /reviews/by-product/{productId}, authenticated customer, [Idempotent]

    ReviewsController.SubmitAsync()
  -> resolve the caller: customer_id claim (fail closed with 403 when absent, admins not exempt)
  -> reviewer display name read from the token's name claim, never from the body
  -> SubmitReviewHandler
    -> VerifiedPurchase for (customer, product)?  no -> Review.NotVerifiedPurchase
    -> existing review by this customer for this product?  yes -> Review.AlreadyReviewed
    -> entitling order = lowest matching OrderId (the earliest entitlement)
    -> ProductReview.Create() -> validates rating 1..5, title <= 120, body <= 2000
       -> raises ProductReviewChanged (Added), status Published
    -> AddAsync + SaveChangesAsync
  -> evict the catalog:products output-cache tag

  (then, after commit)
  -> ProductReviewChangedHandler [own DI scope]
    -> recompute AVG/COUNT over the product's published, non-deleted reviews
    -> Product.UpdateRatingSummary(), written only when the summary actually differs

    Response: 200 OK with ProductReviewDTO

    Revise / Withdraw Review

    Entry Point: PUT /reviews/{id} and DELETE /reviews/{id}, owner or Admin

    Ownership is checked in the controller and a non-owner is answered 404, not 403, so the existence of another customer's review id cannot be probed for. The revise path is conditional (ADR-035): the If-Match header is mandatory and an edit decided against a stale view answers 412. The delete is unconditional (soft delete; a delete has no field to lose to a concurrent edit). Both raise ProductReviewChanged, so the rating summary is recomputed either way. The frozen ReviewerName is deliberately not revisable.

    Hide / Unhide Review (Moderation)

    Entry Point: PUT /reviews/{id}/hide, PUT /reviews/{id}/unhide, catalog:reviews:moderate

    Both are idempotent at the aggregate (a review already in the target status succeeds without raising a second event) and conditional on the same If-Match terms, so two moderators working from the same stale list cannot silently overwrite each other. A hidden review leaves the public list and drops out of the product's rating summary; the moderation list still shows it.

    Erasure

    CustomerErasedHandler consumes Identity's CustomerErased.v1 and anonymizes every review that customer wrote, hidden and soft-deleted rows included: name, title and body cleared, star rating kept (ADR-005). Only rows that still carry personal data are loaded, so a redelivery finds nothing to do and churns no audit fields.

    Query Endpoints

    Endpoint Auth Notes

    GET /reviews/by-product/{productId}/mine Authenticated customer HasPurchased and CanReview as separate booleans, plus the caller's own review; the pair is what lets the UI tell "never bought it" apart from "already had their say"

    The /reviews prefix is served by three controllers: ReviewsController (public list, submit, revise, withdraw), ReviewEligibilityController (/mine) and ReviewModerationController (moderation list, hide, unhide). Every mutation evicts the catalog:products and catalog:categories output-cache tags (a category read can embed its products) as well as invalidating the application cache, because a review moves the stars the product reads carry.

    3.2 Checkout (Cart to Order): Primary Business Workflow

    Entry Point: PUT /shoppingcarts/{customerId}/checkout, authenticated (owner or admin via OwnerOrAdminFilter), [Idempotent], marked ICacheInvalidating. The optional body is a CheckoutDeliveryRequest (shipping address, billing address, phone); an empty body {} still checks out, with no addresses and no shipping label, which is how the admin cart page checks a cart out on a customer's behalf (ShoppingCartsController.cs:275-286). CheckOutCommand is deliberately NOT ITransactional (CheckOutCommand.cs:10): the handler opens its own transaction around the write phase only, so the cross-service reads never hold database locks.

    ShoppingCartsController.CheckOutAsync()
  -> CheckOutHandler
    -> Fetch ShoppingCart with items (NON-tracking snapshot: only names the variants to price)
    -> CheckoutDeliveryMapper.ToDomain(delivery)       (Address invariants; missing billing = shipping)
    -> CheckOutPreflight.ResolveAsync()                [OUTSIDE the transaction, once per checkout]
         -> IProductVariantService.GetUnitPricesAsync(ids)   [cross-module: Catalog]
              each entry is effective price + list price + promotion label (VariantUnitPrice),
              translated into Sales' own OrderLinePricing at the module boundary
         -> reject any variant missing from the price map (soft-deleted between add and checkout)
         -> ICustomerService.GetContactInfoByIdAsync()       [cross-module: Identity, best effort]
    -> CheckOutPreflight.QuoteChargesAsync()            [OUTSIDE the transaction]
         -> OrderChargesCalculator: subtotal, shipping, and sales tax when a ship-to is known
    -> unitOfWork.ExecuteInTransactionAsync(WriteAsync):     <-- one retriable transaction
         -> re-read the cart (tracking) and the InventoryItems (non-tracking snapshot)
         -> CheckOutDomainService.Execute():
              1. Validate cart not empty
              2. Validate inventory exists for all items
              3. Fail-fast sufficiency check per item against the point-in-time snapshot
                 (NOT the oversell guard: that is the atomic decrement below)
              4. Build order items (variant + pricing triple + quantity)
              5. Order.Create(customerId, items, customerName, delivery) -> raises OrderChanged (Added)
              6. shoppingCart.MarkAsCheckedOut() -> raises ShoppingCartCheckedOut
         -> OrderQuoteApplier.Apply(order, quote)     -> order.ApplyCharges(shipping, tax)
         -> IPaymentService.EnsureChargeable(order.Total)   (below the provider minimum -> refused)
         -> orderRepository.AddAsync(order)
         -> IInventoryAllocationService.DecrementAsync(decrements)
              atomic conditional UPDATE per variant (ExecuteUpdateAsync); a row that no longer has
              enough stock matches zero rows and fails the Result, rolling the transaction back
         -> unitOfWork.SaveChangesAsync()              <-- order insert + cart transition
         -> PlacedOrderFinalizer.FinalizeAsync(order)
              -> IShippingLabelProvider.CreateLabelAsync() + order.AttachShippingLabel()
                 (only when the order has a shipping address; a label failure is logged, never fatal)
              -> CheckOutDeadlineScheduler.ArmAsync()  -> schedules Sales.ExpireUnpaidOrder
                 for UnpaidOrderExpiry:Minutes (30) from now, in the SAME transaction
    -> Return OrderDTO

    Business Steps:

    1. Validate cart exists and has items, and validate the delivery addresses before any cross-service call is spent
    2. Fetch current pricing from Catalog module, and reject variants that no longer exist; resolve the customer's display name (best effort: an unreachable Identity leaves it null)
    3. Quote the charges: shipping is a flat Shipping:FlatRate (5.99) waived once the merchandise subtotal reaches Shipping:FreeShippingThreshold (50) (ShippingSettings.cs:16, :20); sales tax is calculated by Stripe Tax only when Tax:Enabled is on and a ship-to address is known, and is zero otherwise (TaxSettings.cs:18, OrderChargesCalculator.cs:59-81)
    4. Fail-fast inventory sufficiency check against the loaded snapshot
    5. Create Order aggregate with OrderLines. Each line freezes the effective price it is charged, the list price that price was struck from and the active promotion's label, so the order can say what it saved without asking Catalog again. Only the effective price is money owed: the line total and the order subtotal follow from it alone. OrderLine.Savings and Order.TotalSavings are computed from the frozen pair on read and never stored (ADR-112)
    6. Apply the quoted shipping and tax: Order.Total = Subtotal + ShippingCost + TaxAmount, the amount the payment session asks for and a payment has to match (Order.cs:485)
    7. Transition cart to CheckedOut status
    8. Commit the write phase in one explicit transaction: the order insert, the atomic inventory decrements, the cart transition, the shipping label and the payment-deadline row

    Decision Points:

    • Cart empty -> Validation error
    • Shipping address present but invalid -> the Address invariant errors, before any pricing
    • Product variant no longer exists in Catalog -> ProductVariant.NotFound, naming the offending variant
    • Bag changed between the quote and the order (the subtotals differ) -> Order.Charges.BagChanged Conflict, so the shopper reviews the bag (OrderQuoteApplier.cs:25-31)
    • Total below what the payment provider can charge (including a zero total) -> refused before anything is written (CheckOutHandler.cs:188)
    • Tax enabled and the tax calculation fails -> the checkout stops rather than charging a guessed tax
    • Insufficient inventory at snapshot time -> Invariant error (fail-fast)
    • Insufficient inventory at commit time -> the conditional UPDATE matches no row, the transaction rolls back
    • Inventory record missing -> NotFound (specific missing variant ID reported)
    • Commit itself fails -> surfaced as non-retriable TransactionCommitAmbiguousException; the [Idempotent] filter replays a client retry safely (ADR-107)

    State Changes:

    • Creates Order (status: PendingPayment) with OrderLine children, the frozen customer name, shipping and billing addresses, phone, ShippingCost, TaxAmount, TaxCalculationId and, when there is a ship-to, a ShippingLabel
    • Decrements InventoryItem.AvailableQuantity for each item
    • ShoppingCart.Status -> CheckedOut
    • One Sales.ExpireUnpaidOrder internal-command row (3.3)

    Domain Events: OrderChanged (Added), ShoppingCartCheckedOut.

    No InventoryAdjusted on the checkout path. The decrement runs as ExecuteUpdateAsync, which bypasses the save pipeline (and therefore the audit interceptor and domain-event dispatch) by design: that is what makes it a single atomic statement and the real oversell guard. InventoryAdjusted is still raised by the admin adjustment endpoints in 3.4, which go through the aggregate.

    3.3 Order Lifecycle

    Order Status State Machine

                      InitiatePayment                     MarkAsPaid
 PendingPayment ------------------> PaymentInitiated -------------> Paid -----Ship-----> Shipped
       |                              |          ^                   |                     |
       |         MarkAsPaymentFailed  |          | InitiatePayment   | MarkAsDelivered     | MarkAsDelivered
       |                              v          | (retry)           | (no carrier leg)    |
       |                          PaymentFailed -+                   v                     |
       |                              |                          Delivered <---------------+
       |  MarkAsCancelled             |  MarkAsCancelled
       +-----------------> Cancelled <+  (PaymentInitiated cancels the same way)

 MarkAsPaidManually (admin) reaches Paid from PendingPayment, PaymentInitiated or PaymentFailed.
 MarkAsPaid (webhook, verify-payment, reconciliation sweep) reaches Paid from PaymentInitiated only.

    Each edge is the state class's CanMark* guard under Sales.Domain/Orders/States/ (PaymentInitiatedState.cs:13-22, PaidState.cs:22, ShippedState.cs:26).

    Terminal States: Cancelled, Delivered

    The Cancelled edges are taken by a customer or admin cancel, by the order's own payment deadline (Sales.ExpireUnpaidOrder, below) and by the reconciliation sweep; all three land in the same OrderCancelled compensation.

    Shipped is an optional stop, not a mandatory one: a fulfilment with no tracking to record still goes Paid -> Delivered directly, which is why Paid keeps both outgoing edges. Cancellation is refused from Shipped exactly as it is from Paid. UpdateShipment is a self-transition on Shipped. The enum's numeric values are persisted and travel on the user_sales_export gRPC contract, so Shipped is appended LAST in OrderStatus even though it sits mid-lifecycle.

    Create Stripe Checkout Session

    Entry Point: POST /orders/{id}/checkout, Authenticated (owner or admin, ownership validated in the controller with a 404 for a non-owner), [Idempotent]. A guest order reaches the same use case through POST /orders/guest/{id}/checkout (3.5).

    OrdersController.CreateCheckoutSessionAsync()
  -> CreateCheckoutSessionHandler   (CreateCheckoutSessionCommand: ICacheInvalidating, IHasTimeout)
    -> validator: success/cancel URIs must sit on CheckoutRedirectSettings.AllowedRedirectOrigins
    -> Fetch Order with OrderLines
    -> order.CanInitiatePayment()   (status gate BEFORE any provider call)
      PendingPayment / PaymentFailed -> new session:
        -> IPaymentService.EnsureChargeable(order.Total)
        -> IPaymentService.CreateCheckoutSessionAsync(..., CheckoutSessionCharges.ForOrder(order, email))
          -> StripePaymentService: separate line items for the merchandise, shipping and sales tax,
             converted to the smallest currency unit and checked to add up to the order total;
             pre-filled payer email (guest ContactEmail, else the token's email claim);
             orderId in the session and payment-intent metadata; ExpiresAt set on the session
        -> order.InitiatePayment(sessionId) -> status PaymentInitiated, raises OrderPaymentInitiated
        -> SaveChangesAsync()
      PaymentInitiated -> resume the session it is waiting on:
        -> IPaymentService.GetCheckoutSessionStatusAsync(order.StripeSessionId)
          paid for exactly this order (PaymentProof) -> order.MarkAsPaid(), no new session
          expired                                   -> retired via MarkAsPaymentFailed, then a new session
          still open                                -> hand back the SAME checkout page
          taken but unsettled                       -> tell the customer to wait, open nothing
      Paid / Shipped / Delivered / Cancelled -> refused, no provider call
    -> Return sessionId + checkoutUri

    External Interaction: Stripe API: creates (or reads) the hosted checkout session. A PaymentInitiated order never re-runs InitiatePayment, because the webhook finds the order BY the stored session id and a second session would orphan the first one's confirmation (CreateCheckoutSessionHandler.cs:65-80, :150).

    Stripe Payment Webhook

    Entry Point: POST /payments/webhook, AllowAnonymous, [NonIdempotent] (Stripe sends no Idempotency-Key; replay protection is the signature plus the order's own state), [RequestSizeLimit(1_000_000)]. ProcessPaymentWebhookCommand is ICacheInvalidating and deliberately NOT ITransactional (ProcessPaymentWebhookCommand.cs:9): each branch performs one atomic SaveChangesAsync, and the event handlers run post-commit with no transaction held. The Gateway exempts /Payments from its edge rate limiter.

    PaymentsController.HandleWebhookAsync()
  -> read the raw body (signature verification needs the unmodified payload)
  -> ProcessPaymentWebhookHandler
    -> IPaymentService.ParseWebhookEvent() (Stripe signature verification)
    -> Route by event type:

      checkout.session.completed:
        -> Find Order by StripeSessionId
        -> Already Paid / Shipped / Delivered -> success; a DIFFERENT payment intent is logged
           as a second charge that may need a refund
        -> Already Cancelled / PaymentFailed -> success, anomaly logged
        -> PaymentProof.IsPaymentForOrder(): Stripe reports the session paid, for exactly the
           order's total in its currency; anything else is acknowledged and left for an operator
        -> order.MarkAsPaid(paymentIntentId) -> status Paid, raises OrderPaid

      checkout.session.expired:
        -> Find Order by StripeSessionId
        -> Already PaymentFailed / Cancelled -> success; already Paid -> success, anomaly logged
        -> order.MarkAsPaymentFailed() -> status PaymentFailed, raises OrderPaymentFailed

      payment_intent.payment_failed:
        -> logged only: the session is still open and the customer can submit another card

      Other events: ignored (returns success)

    Idempotency: Already-transitioned orders return success without modification.

    Controller behavior: Returns 400 only when the event was never ACCEPTED (no body, no signature header, signature verification failed, no signing secret configured, or an unparseable payload; PaymentsController.cs:39), logged at Critical so the misconfiguration surfaces before Stripe disables the endpoint. Everything past acceptance, including an unknown order, returns 200, because a retry would fail identically forever.

    Receipt email: OrderPaidHandler schedules SendOrderPaidEmailInternalCommand (ADR-114, OrderPaidHandler.cs:38) rather than sending inline, so an SMTP outage retries instead of losing the receipt. The command handler re-reads the order and its lines and sends to the customer's Identity contact, or to the guest's ContactEmail. A discounted line prints a struck "Was" amount above the price charged with the label (HTML-encoded) beneath it, and the order gets a "You saved" total; each appears only when there is a saving to show. Delivery is at-least-once by decision: a host dying after the SMTP call re-sends.

    Manual Admin Payment

    Entry Point: PUT /orders/{id}/pay, sales:orders:manage, mandatory If-Match, no body

    Validates status allows manual payment (PendingPayment, PaymentInitiated, or PaymentFailed). Sets StripePaymentIntentId = "manual-admin-override", status -> Paid. Publishes OrderPaid. 204 on success, 412 on a stale token, 428 when the header is absent.

    Verify Payment (webhook backstop)

    Entry Point: PUT /orders/{id}/verify-payment, owner or Admin (ownership validated in the controller). VerifyPaymentCommand is IFeatureGated on Sales.PaymentVerification (SalesFeatures.cs:23), a permanent kill switch over the live Stripe call, and IHasTimeout with a 20-second budget.

    Polls Stripe directly for the order's checkout session instead of waiting on a webhook, for the case where webhook delivery failed or is delayed. If Stripe reports the session paid for exactly the order total (PaymentProof), the order is marked Paid exactly as the webhook would have marked it; if the order is already Paid or is not in a verifiable state, the call succeeds without changes. This is the reconciliation half of ADR-054: the webhook is the fast path, this is the backstop that keeps a paid customer from sitting in PaymentInitiated forever.

    Expire Unpaid Order (payment deadline)

    Entry Point: the Sales.ExpireUnpaidOrder internal command (ExpireUnpaidOrderInternalCommand), scheduled per order by checkout (3.2) and re-armed by OrderPaymentFailedSagaHandler on every failed payment. No HTTP surface.

    ExpireUnpaidOrderInternalCommandHandler
  -> load the order; gone, or in any status other than PendingPayment or PaymentFailed
     (paid, cancelled, or PaymentInitiated, which the reconciliation sweep below resolves)
     -> success (Debug log, nothing to do) (ExpireUnpaidOrderInternalCommandHandler.cs:61)
  -> re-derive the due instant from LastModifiedOn ?? CreatedOn (not from the schedule time),
     so an older deadline left behind by a re-arm runs as a no-op
  -> still unpaid and past the window -> order.MarkAsCancelled(PaymentExpired) -> raises OrderCancelled
       -> OrderCancelledSagaHandler returns the stock checkout committed
       -> OrderCancelledHandler schedules the "your unpaid order expired" email
  -> a concurrency conflict (a webhook moved the order first) -> success: the concurrent writer wins

    The window is UnpaidOrderExpiry:Minutes (30, Enabled: true in the Sales service settings). PaymentReconciliationService keeps the same window under PaymentReconciliation:StuckAgeMinutes and is the backstop for a deadline that was never written: it reconciles PaymentInitiated orders against Stripe (paid -> MarkAsPaid, expired -> MarkAsPaymentFailed) and expires stranded PendingPayment and PaymentFailed orders with the same PaymentExpired reason (PaymentReconciliationService.cs:274).

    Payment-failed path: OrderPaymentFailedSagaHandler schedules SendOrderPaymentFailedEmailInternalCommand (the "you can retry" notice) and re-arms the deadline from now, so a failed payment hands the customer the whole retry window again (OrderPaymentFailedSagaHandler.cs:35, :81).

    Correct Shipment

    Entry Point: PUT /orders/{id}/shipment, sales:orders:manage, mandatory If-Match

    Same request body as ship, because the shipment is a value object and a correction replaces it whole rather than patching a field. Allowed from Shipped only; the status does not move, and OrderShipped is raised again on purpose so a customer who was told the wrong tracking number gets the right one (the notification is a re-send, not a duplicate). Kept as a separate endpoint from ship deliberately: ship must refuse an already-shipped order and this one must refuse an order that never shipped, so folding them together would make "silently re-ship" indistinguishable from "fix the tracking number".

    Deliver Order

    Entry Point: PUT /orders/{id}/deliver, sales:orders:manage, mandatory If-Match

    Validates status is Paid or Shipped. Status -> Delivered, FulfilledPublishedOn stamped in the same unit of work. Raises the in-process OrderDelivered and, for a customer's order, the OrderFulfilled integration event carrying the delivered line snapshot, which Catalog turns into the verified-purchase entitlements behind product reviews (Section 2.5). A guest order raises OrderDelivered only, since it has no account to hold an entitlement (Order.cs:743-757). The snapshot travels on the event because the consumer lives in another service and cannot query back (ADR-006), which is also why callers load OrderLines with the aggregate.

    Delivery email: OrderDeliveredHandler schedules SendOrderDeliveredEmailInternalCommand (ADR-114, order id only) after the commit; a scheduling failure is logged, not thrown, because the order is already Delivered (OrderDeliveredHandler.cs:25-43). The handler tells the order's recipient (the customer through ICustomerService, or a guest's ContactEmail, OrderRecipient) that the order arrived (SendOrderDeliveredEmailInternalCommandHandler.cs:43-58).

    The admin order grid searches tracking numbers: the filter name ShipmentTrackingNumber maps to the scalar column the owned shipment flattens onto, so it is one server-side CONTAINS rather than a client scan.

    Cancel Order

    Entry Point: PUT /orders/{id}/cancel, Owner or Admin (ownership validated in the controller), mandatory If-Match, no body

    OrdersController.CancelAsync()
  -> CancelOrderHandler   (CancelOrderCommand: ICacheInvalidating)
    -> Fetch Order; refuse a stale If-Match token first (OrderConcurrency.EnsureCurrent)
    -> leaving PaymentInitiated: retire the live Stripe checkout session inline
       (PaymentSessionRetirement); a session Stripe reports PAID refuses the cancellation
    -> order.MarkAsCancelled()
      -> Validates status is PendingPayment, PaymentInitiated, or PaymentFailed
      -> Status -> Cancelled, publishes OrderCancelled
    -> SaveChangesAsync()          <-- cancellation commits here; no inventory work inline

  (then, after commit)
  -> OrderCancelledSagaHandler  [ADR-054 compensating action, own DI scope]
    -> Skip if order.InventoryRestored is already set (idempotent under redelivery)
    -> Restore stock for each OrderLine
    -> order.MarkInventoryRestored()
    -> ONE SaveChangesAsync commits the marker and the inventory increases together
  -> OrderCancelledHandler      [notification, independent of the saga]
    -> schedules SendOrderCancelledEmailInternalCommand(orderId, reason)   (ADR-114)
    -> SendOrderCancelledEmailInternalCommandHandler
      -> recipient: OrderRecipient (the customer, or the guest's ContactEmail)
      -> Requested: "Order Cancelled"; PaymentExpired: "Your unpaid order expired"

    Cancellation email: every cancellation path raises the same OrderCancelled, which carries an OrderCancellationReason: Requested for a customer, guest or admin cancel, PaymentExpired for the payment deadline and the reconciliation sweep (OrderCancellationReason.cs:13-23, Order.cs:879). The reason rides the event and the internal command row only; no column stores it. OrderCancelledHandler schedules the notice beside the inventory saga, neither depending on the other (OrderCancelledHandler.cs:24-50), and the send picks the wording from the reason, so an order the shopper never cancelled is described as an expired unpaid order whose items were released (SendOrderCancelledEmailInternalCommandHandler.cs:54-78).

    Inventory Impact: All reserved inventory is restored on cancellation, by a compensating handler that runs after the cancellation transaction, not inside it (ADR-054). Order.InventoryRestored is the idempotency marker, committed by the same SaveChangesAsync as the restoration, so an at-least-once redelivery cannot double-restore; the order's rowversion token makes two concurrent deliveries mutually exclusive. The same saga runs whatever cancelled the order: a customer or admin here, a guest from the private link (3.5), the payment deadline, or the reconciliation sweep. Splitting compensation out of CancelOrderHandler is what lets further actions (the cancellation email above, a refund) be added as new handlers rather than edits. The one compensating step that stays inline is retiring the payment session, because it has to answer "has this already been paid?" BEFORE the cancellation commits.

    3.5 Guest Checkout

    A shopper who has not signed in can buy without an account. The order keeps the guest's name, email, phone and addresses itself (Order.CustomerId is null, Order.IsGuest is true), and a private access token is the guest's only credential for it. Every action but the claim is anonymous; the token travels in the GuestOrderHeaders.AccessToken request header, and every refusal (wrong token, a customer's order, an order already claimed, an order that does not exist) answers the same NotFound, so the endpoints cannot be used to learn which order numbers exist (GetGuestOrderHandler.cs:32).

    Workflow Endpoint Auth Notes
    Place guest order POST /orders/guest AllowAnonymous, [Idempotent], auth-ip rate limit 201 with the order and its access token (GuestCheckoutResponse)
    Read guest order GET /orders/guest/{id} AllowAnonymous + access token The order with its lines
    Pay for guest order POST /orders/guest/{id}/checkout AllowAnonymous + access token, [Idempotent] Checks the token, then runs the same CreateCheckoutSessionCommand as 3.3
    Claim into an account POST /orders/guest/{id}/claim Authenticated + access token, [NonIdempotent] Moves the order into the caller's account; 403 when the account has no customer profile
    Cancel guest order POST /orders/guest/{id}/cancel AllowAnonymous + access token, mandatory If-Match, [NonIdempotent] Checks the token, then runs the same CancelOrderCommand as a customer's cancel (3.3); 204, and every refusal (a status that can no longer be cancelled included) answers 404 (GuestOrdersController.cs:163-186)
    Request a new link POST /orders/guest/lookup AllowAnonymous, [Idempotent], auth-ip rate limit Order number and checkout email; always 202 with no body (GuestOrdersController.cs:198-216)

    Place guest order:

    GuestOrdersController.PlaceOrderAsync()
  -> GuestCheckOutHandler   (GuestCheckOutCommand: ICacheInvalidating, NOT ITransactional)
    -> CheckoutDeliveryMapper.ToDomain(request.Delivery)   (shipping address REQUIRED for a guest)
    -> CheckOutPreflight.ResolvePricesAsync(variantIds)    [OUTSIDE the transaction]
    -> CheckOutPreflight.QuoteChargesAsync(lines, prices, shipTo)
    -> mint the access token: GuestOrderLinks.NewAccessToken(), 32 random bytes, base64url (256 bits)
    -> unitOfWork.ExecuteInTransactionAsync(WriteAsync):
         -> inventory snapshot for existence + fail-fast sufficiency
         -> CheckOutDomainService.ExecuteForGuest() -> Order.CreateForGuest()
              (guest name, contact email and token validated; only the token's SHA-256 hash is kept)
         -> OrderQuoteApplier.Apply() + IPaymentService.EnsureChargeable()
         -> AddAsync, atomic inventory decrements, SaveChangesAsync
         -> PlacedOrderFinalizer.FinalizeAsync()  (shipping label + payment deadline, as in 3.2)
    -> GuestOrderPlacedNotifier.NotifyAsync(order, token)   [after commit, best effort]
         -> "Order Received" email with the private link
            <storefront origin>/orders/guest/{id}#t=<token>
    -> Return order + token

    The lines come from the shopper's device cart (GuestCheckoutRequest.Lines), not from a server cart. The plaintext token exists only in the checkout response and in the order-received email: the order stores GuestAccessTokenHash, an upper-hex SHA-256 compared in constant time (Order.cs:528-547), so a database read cannot open anyone's order. That is also why the email is sent inline rather than as an internal command, whose row would put the plaintext back at rest (GuestOrderPlacedNotifier.cs:17-20). The token sits in the URL FRAGMENT, which the browser never sends to a server, so it stays out of request logs and Referer headers.

    Claim: ClaimGuestOrderHandler checks the token against the stored hash, then Order.ClaimForCustomer(customerId) sets CustomerId, clears GuestAccessTokenHash (the account, not the link, is the credential from then on) and raises OrderChanged (Updated) (Order.cs:600-616). The guest order page offers this right after registering from the order's own details.

    Cancel: the guest order page offers Cancel while the order is unpaid (PendingPayment, PaymentInitiated or PaymentFailed), after a confirmation (GuestOrderDetail.razor.cs:61-65, GuestOrderDetail.Lifecycle.razor.cs:50-92). The controller reads the order through the token first, then runs the customer's cancel use case unchanged: the live Stripe session is retired, the cancellation saga returns the stock, and the cancellation email goes to ContactEmail (3.3).

    Request a new link (find my order):

    GuestOrdersController.RequestLinkAsync()
  -> RequestGuestOrderLinkHandler
    -> load the order; no match unless it is an UNCLAIMED guest order whose ContactEmail equals
       the given email (trimmed, case-insensitive; Order.IsGuestOrderFor)
    -> on a match: schedule SendGuestOrderLinkInternalCommand(orderId)   (ADR-114)
    -> every outcome (match, wrong email, customer's or claimed order, unknown number,
       a scheduling failure) -> Result.Success -> 202
  -> SendGuestOrderLinkInternalCommandHandler
    -> still a guest order with a contact email and a storefront origin configured, else
       success with a log line and NO token change
    -> mint a new token, Order.ReplaceGuestAccessToken() (raises OrderChanged, Updated)
    -> email "Your order link" with the new private link to the order's own ContactEmail
    -> THEN SaveChangesAsync: only after a successful send is the new hash saved

    The handler answers the same success whatever it found, so the endpoint cannot be used to learn which orders exist or who placed them, and the link only ever goes to the address already on the order (RequestGuestOrderLinkHandler.cs:16-21, :38-55). The internal command carries the order id only: the token is minted inside the handler, so no row ever holds a plaintext token. The send runs before the save, so a transport fault fails the row with nothing saved and the link the guest already holds keeps working; a save conflict after the send fails the row too, and the retry mints and sends a fresh token (SendGuestOrderLinkInternalCommandHandler.cs:17-32, :66-99). Saving the new hash retires every earlier link (Order.cs:571-591). Both guest emails build the link the same way (GuestOrderLinks.cs:19-37).

    The device bag through guest checkout: placing a guest order does not empty the browser bag. Checkout remembers the order id and the lines it was placed with (Checkout.razor.cs:294-298, GuestCartStore.cs:104-111); once the guest order page sees the order paid, or the Stripe success return lands on an order that is neither Cancelled nor PaymentFailed, exactly those quantities are subtracted from the bag, clamped at zero, so anything added since survives (GuestOrderDetail.Lifecycle.razor.cs:23-43, GuestCartStore.cs:128-150). A shopper who abandons the Stripe page comes back to the bag they left. The sign-in merge settles the same memory first (4.1, CartStateService.cs:635-681).

    Downstream differences for a guest order: the payment, shipping, payment-failed, delivered and cancelled emails go to ContactEmail (OrderRecipient.cs:23-40), the payment confirmation points the guest at the earlier order-received email rather than repeating the link, and delivery raises no OrderFulfilled, so a guest purchase earns no review entitlement until it is claimed before delivery.

2. Quote             POST /orders/quote            -> Totals, then tax once the address is complete
3. Place order       POST /orders/guest            -> Guest order + private token; order-received
                                                     email with the private link
4. Pay               POST /orders/guest/{id}/checkout -> Stripe session (token in a header)
5. Payment Complete  POST /payments/webhook        -> Order marked Paid, receipt to ContactEmail
6. Follow the order  GET /orders/guest/{id}        -> Status, tracking and totals from the link;
                                                     once paid, the ordered lines leave the bag
7. Optional claim    POST /orders/guest/{id}/claim -> After registering, the order joins the account
8. Lost the link     POST /orders/guest/lookup     -> Always 202; on a match a new link is emailed
                                                     and every earlier link stops working

    Alternative Flows:

    • Payment fails -> Order status PaymentFailed -> retry notice emailed, payment window restarted -> customer can retry (create new Stripe session)
    • Payment never lands -> Sales.ExpireUnpaidOrder (or the reconciliation sweep) cancels the order after 30 minutes -> inventory restored -> "your unpaid order expired" email
    • Cancel order (customer after a confirmation, guest from the private link, or admin) -> Status Cancelled (from PendingPayment, PaymentInitiated, or PaymentFailed) -> live Stripe session expired -> inventory restored -> cancellation email
    • Cart reactivation -> Checked-out cart auto-reactivated on next add-item (all old items cleared)
    • Manual payment -> Admin bypasses Stripe, sets StripePaymentIntentId = "manual-admin-override"
    • Admin checkout on behalf -> Admin checks a customer's cart out from /shoppingcarts/{id} with an empty body (no addresses, no label, no tax)

    9. Potentially Missing or Incomplete Workflows

    Observation Evidence Recommendation
    No refund workflow Order can be cancelled only before payment completes (PendingPayment/PaymentInitiated/PaymentFailed); no refund logic for Paid orders. A second charge on an already-paid order is only logged "may require a refund" (ProcessPaymentWebhookHandler.cs:199-200) Verify if refunds are handled externally via Stripe dashboard or if a refund workflow is planned
    No order editing Once checkout completes, order lines cannot be modified Confirm if this is intentional or if order amendment is planned
    No email when a signed-in customer places an order Email exists for guest order placement (GuestOrderPlacedNotifier), payment, shipment, payment failure, delivery (OrderDeliveredHandler) and cancellation (OrderCancelledHandler, worded by OrderCancellationReason), for customers and guests alike; a customer's order gets nothing on OrderChanged (Added). The absence is a deliberate owner decision: the payment receipt is what confirms a customer's order None; recorded so the absence is not mistaken for a gap
    No full-text search The storefront search is a contains match over the product name or description (StorefrontProductsSpecification.cs:70-74, E2E-covered); there is no full-text, fuzzy or ranked search Consider full-text search for larger catalogs
    Inventory not checked during cart add Inventory validation only happens at checkout, not when adding to cart (AddItemHandler checks only variant existence) Could lead to poor UX if items go out of stock between add and checkout
    No post-payment cancellation Cancellation allowed from PendingPayment, PaymentInitiated, or PaymentFailed; cannot cancel after payment succeeds Verify if post-payment cancellation with Stripe refund is needed
    No partial fulfillment Orders ship and are delivered as a whole: Shipped applies to the order, not to individual lines, and an order carries one Shipment value object A second parcel means turning the shipment into a collection; clarify whether split shipments are a real business case first
    No refund compensation handler ADR-054 makes refunds a natural further saga handler alongside OrderCancelledSagaHandler and OrderPaymentFailedSagaHandler, but none exists Add when post-payment cancellation lands
    Shipping labels are mock only MockShippingLabelProvider is the only IShippingLabelProvider; the label is invented and is not linked to the Shipment an admin records later Wire a real carrier provider behind the same interface when label purchase is in scope
    Sales tax off by default TaxSettings.Enabled defaults to false and the Sales service settings declare no Tax section, so every order carries zero tax until Stripe Tax is activated on the account An owner decision plus a setting; no code change
    Guest orders delivered unclaimed earn no review entitlement MarkAsDelivered raises OrderFulfilled only when CustomerId is set but stamps FulfilledPublishedOn either way (Order.cs:750-757), so neither a later claim, the backfill nor RepublishFulfillment publishes it Decide whether a claim after delivery should mint the entitlement
