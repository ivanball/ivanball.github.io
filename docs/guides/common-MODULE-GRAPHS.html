    Module Dependency Graphs

    Generated from the committed project files of MMCA.ADC, MMCA.Store and MMCA.Helpdesk. Do not hand-edit: regenerate it instead.

    How the modules of each application depend on one another, at two levels:

    • Compile-time references (solid arrows): a ProjectReference from one module's project to another module's project. Each repository pins this exact list in its CrossModuleReferenceTests (the CrossModuleReferenceTestsBase fitness function in MMCA.Common), so adding or removing one is a reviewed change to that test. The label counts the project references behind the arrow.
    • Runtime calls (dashed arrows): a service host that references a peer module's *.Contracts project wires that peer's gRPC client, so the module calls the peer across the process boundary when the modules run as separate services. The table beside each graph says whether the calling module lists the peer in its IModule.Dependencies; a "no" is a runtime edge the module loader's ordering and RequiresDependencies check do not know about (ADR-059, Trade-offs).

    Cross-module references target a peer's Shared (contracts) project, except UI composing another module's UI; the IL-level isolation rules (ADR-059) and this project-level list together cover the boundary.
