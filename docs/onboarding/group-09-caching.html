    9. Caching

    What this group covers. Caching in this codebase is small, deliberate, and woven into the CQRS pipeline rather than scattered across handlers. The group is twelve types: one port the Application layer depends on (ICacheService), two Infrastructure adapters that implement it (the in-process MemoryCacheService and the two-level HybridCacheService, the one cache service over a shared Redis), the prefix rule both adapters enforce (CachePrefixContract), the generation-token engine that lets the two-level cache invalidate a prefix without walking the keyspace (CachePrefixGenerations and its per-boundary RememberedToken), a static TTL-policy factory (CacheOptions) with the bound settings object that reproduces its defaults from configuration (CacheSettings), the key-namespace pair (CacheKeyPrefixOptions plus its internal applier CacheKeyNamespace) that keeps two applications sharing one Redis instance out of each other's keyspace by default, and the hook every framework Redis connection runs before it connects (IRedisConfigurationOptionsConfigurator and its options-pipeline bridge RedisConfigurationOptionsPostConfigure). No handler ever talks to Redis or IMemoryCache directly: the read-through and invalidate-on-write behavior lives in two pipeline decorators taught in Group 5, CQRS Pipeline. This chapter is the cache's own machinery, the contract, the two backends, the prefix rule and the generation tokens, the TTL policy and its configuration object, the namespace and the connection hook, plus how they plug into that pipeline.

    The contract. ICacheService (MMCA.Common/Source/Core/MMCA.Common.Application/Interfaces/ICacheService.cs:10) is a textbook Clean Architecture port/adapter split (see primer §1): the interface lives in MMCA.Common.Application, both implementations live in MMCA.Common.Infrastructure, and application code compiles against the interface alone. It declares eight members. Four are abstract: GetAsync<T> returning T? with null for a miss (ICacheService.cs:17), SetAsync<T> with an optional TimeSpan? TTL (ICacheService.cs:79), RemoveAsync for one key (ICacheService.cs:89), and RemoveByPrefixAsync for bulk eviction by key prefix (ICacheService.cs:113). Four are default interface members with working bodies, so each one shipped without breaking an implementer. TryGetAsync<T> (ICacheService.cs:34) reports presence separately from the value, because for a value-type T a GetAsync miss answers default(T) and cannot be told apart from a cached 0 or false (ICacheService.cs:19-23); the default infers presence from a non-null value (ICacheService.cs:36-37), and the shipped stores override it with a real presence check (ICacheService.cs:30-32). GetFromSharedStoreAsync<T> (ICacheService.cs:69) reads past any process-local copy, for values whose change on one replica must be visible on every other one at once (ICacheService.cs:40-46): single-use records (an OAuth exchange code, a password-reset or email-confirmation token, a second-factor time step), the counters IncrementAsync maintains, since a store with a local tier increments in the shared store and a local copy would pin the first count it saw (ICacheService.cs:54-57), and flags another replica can set or clear, the login lockout flag and the soft-deleted-user marker (ICacheService.cs:58-59). Everything read many times stays on GetAsync and loses only the local hit rate by coming here (ICacheService.cs:59-61); the default simply calls GetAsync, which is exact for a store with no local tier (ICacheService.cs:64-66). IncrementAsync (ICacheService.cs:133) is a read-modify-write counter (ICacheService.cs:135-138) that gives the ADR-029 brute-force and rate-limit counters one entry point instead of scattered get-then-set pairs; its doc states plainly that it is not atomic in any shipped implementation (the default and HybridCacheService both read then write, so concurrent increments can undercount, ICacheService.cs:115-120) and that none overrides it with Redis INCR, because the distributed cache stores entries as Redis hashes and an INCR string at the same key would fail the next read with WRONGTYPE (ICacheService.cs:126-132); ADR-026 records the resulting undercount as an accepted position, not an open defect. GetOrCreateAsync<T> (ICacheService.cs:173) folds read, per-key stripe, double-check, factory and write into one call (ICacheService.cs:178-199), taking presence from TryGetAsync on both checks so a cached default(T) counts as a hit (ICacheService.cs:181-193), using the process-wide CacheKeyLocks table (ICacheService.cs:217-221), cross-referenced in Group 5. Its XML doc is explicit about two limits that matter: it caches whatever the factory returned, failed Result included, which is exactly why the caching decorators do not route through it, and its stampede protection is per process (ICacheService.cs:154-171). RemoveByPrefixAsync is the load-bearing member: it is what lets a single write evict every cached read it could have staled. Its argument has a contract: the prefix must be empty (every entry) or end at a : boundary, so "MMCA.Sample.Event:" is accepted and "MMCA.Sample.Ev" is rejected with an ArgumentException (ICacheService.cs:91-112). That boundary rule is what lets the two-level store invalidate with one write instead of enumerating keys (ICacheService.cs:101-105), and the backends had to be built rather than used off the shelf because neither primitive offers it (IMemoryCache has no key enumeration, and HybridCache's tag invalidation does not reach a replica that has already met the tag, as the generation-token section below explains). [Rubric §3, Clean Architecture] assesses whether dependencies point inward and infrastructure stays replaceable; this is that rule in one file, since the only thing Application knows about caching is eight method signatures.

    Backend selection happens once, at the composition root, and refuses to guess. AddCaching(IConfiguration?) (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/DependencyInjection.Caching.cs:30, called from AddInfrastructure at DependencyInjection.cs:141) always calls AddMemoryCache() (DependencyInjection.Caching.cs:32), then binds the shared Cache configuration section three ways when configuration was supplied (DependencyInjection.Caching.cs:44-57): to CacheKeyPrefixOptions for the key namespace (DependencyInjection.Caching.cs:46), to CacheSettings for the TTL policy, validated at start-up (DependencyInjection.Caching.cs:48-51), and to QueryCachePipelineSettings for the one knob the Application-layer query decorator needs (DependencyInjection.Caching.cs:53-56, defined in that layer because it cannot reference Infrastructure). Without configuration both settings objects are still registered at their defaults (DependencyInjection.Caching.cs:58-62), so IOptions<T> always resolves. It also post-configures the Redis output-cache store, when one is registered, with the same key namespace as its InstanceName unless a host set one, so two applications on one Redis do not share output-cache entries or tag sets (DependencyInjection.Caching.cs:64-77). ICacheService itself is registered through TryAddSingleton with a factory (DependencyInjection.Caching.cs:79-99) that has only one answer to give: a MemoryCacheService over the registered IMemoryCache, handed the bound cache settings (DependencyInjection.Caching.cs:96-98). If the factory finds a real out-of-process IDistributedCache registered (anything but the default MemoryDistributedCache), it throws an InvalidOperationException that names AddCommonHybridCache and its guarded form instead (DependencyInjection.Caching.cs:86-93), because falling back to the in-process cache would silently make single-use records, counters and the lockout flag per-replica (DependencyInjection.Caching.cs:81-85). A shared store is served by the two-level cache only. The same method registers the IDistributedLock that the five in-framework callers pair with the cache (the API idempotency filter, password-reset token redemption, the two-factor authenticator, OAuthControllerBase when given a lock, and passkey challenges, DependencyInjection.Caching.cs:101-108), Redis-backed when a multiplexer is present and process-local otherwise (DependencyInjection.Caching.cs:109-123). A single-process monolith therefore caches in-process for free, and the identical application code uses Redis the moment the host wires it: no flag, no per-environment branch in a handler. This is the same "abstraction in Application, transport chosen at the edge" pattern the message bus and gRPC clients use, which is what [Rubric §7, Microservices Readiness] looks for (can a module move to its own process without a code change) and part of what [Rubric §12, Performance and Scalability] rewards (the scaled-out deployment gets a shared cache without touching business code).

    The shared-store substrate is explicit. AddCommonHybridCache(Action<HybridCacheOptions>?) (DependencyInjection.Caching.cs:162) is required for, and intended for, hosts with a distributed L2 (DependencyInjection.Caching.cs:137-140). It calls AddHybridCache() (DependencyInjection.Caching.cs:164) and then configures HybridCacheOptions through the options pipeline rather than through the AddHybridCache callback (DependencyInjection.Caching.cs:170-184), because the TTL policy comes from the bound CacheSettings and the callback has no service provider to read it from; the framework sets Expiration from DefaultDuration and LocalCacheExpiration from LocalCacheDuration (falling back to HybridCacheService.LocalCacheDefault) at DependencyInjection.Caching.cs:177-181, and the host's own hook runs last so it can override anything (DependencyInjection.Caching.cs:183). The swap of the cache implementation is deliberately RemoveAll<ICacheService>() followed by AddSingleton (DependencyInjection.Caching.cs:186-205) rather than TryAdd, so the call wins whether it runs before or after AddInfrastructure; the source is equally explicit that this also removes a host's own bespoke ICacheService, so calling it is a statement that the two-level cache is the cache (DependencyInjection.Caching.cs:150-153). The factory hands the new service the optional IConnectionMultiplexer that holds the generation tokens, the host's key namespace, the bound settings and the cross-service namespace (DependencyInjection.Caching.cs:189-204). AddCommonHybridCache has no guard of its own, so the framework also ships the guarded form, AddCommonHybridCacheWhenRedisConfigured(IConfiguration, string) (DependencyInjection.Caching.cs:226), which calls it only when the redis connection string (the default connectionName) is non-empty (DependencyInjection.Caching.cs:232-235) and otherwise leaves the registration untouched. Service hosts do not make these calls by hand: the composed start-up AddMmcaServiceHost (MMCA.Common/Source/Hosting/MMCA.Common.ServiceHost/ServiceHostBuilderExtensions.cs:65) runs AddRedisCaching(), then AddRedisOutputCaching() when the host asks for it, then the guarded hybrid call (ServiceHostBuilderExtensions.cs:91-97), and both deployed applications compose through it (ADC Conference at MMCA.ADC/Source/Services/MMCA.ADC.Conference.Service/Program.cs:82, Store Catalog at MMCA.Store/Source/Services/MMCA.Store.Catalog.Service/Program.cs:32). Without Redis the guard declines and the host keeps the in-process substrate, which is the point: an L1 in front of an in-process L2 buys nothing (DependencyInjection.Caching.cs:215-217, ADR-077).

    The in-process adapter. MemoryCacheService (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/MemoryCacheService.cs:19) wraps IMemoryCache, takes the bound CacheSettings (framework defaults when none is passed, MemoryCacheService.cs:25) so an entry written without an expiration gets the same DefaultDuration every other store applies (MemoryCacheService.cs:84), and carries one side structure: a ConcurrentDictionary<string, object> of live keys (MemoryCacheService.cs:38), because IMemoryCache cannot enumerate its own keys and without that shadow index RemoveByPrefixAsync (MemoryCacheService.cs:144-148) would be impossible. Keeping the cache and the index in agreement is the whole design. Every mutation takes that key's stripe from a per-instance KeyedSemaphoreStripe (MemoryCacheService.cs:45) and touches the cache before the table (MemoryCacheService.cs:111-115), because ordering alone cannot close the window: track-then-write lets a concurrent removal drop the record between the steps, and write-then-track lets a removal run entirely between them, both leaving a live entry nothing can find. The post-eviction callback is deliberately lock-free, since IMemoryCache queues it to the thread pool, and it removes the record only while the record is still its own, comparing the entry token by reference and skipping EvictionReason.Replaced outright (MemoryCacheService.cs:103-109). Prefix removal walks a snapshot of the tracked keys and takes one stripe at a time, never accumulating handles, so two prefix removals cannot deadlock on each other's stripes (MemoryCacheService.cs:130-136, MemoryCacheService.cs:154-164). GetAsync also matches on the stored object rather than using the generic TryGetValue<T> overload (MemoryCacheService.cs:53), so a key reused under a different T surfaces as a clean miss instead of an InvalidCastException, and it overrides TryGetAsync with the same type-matched lookup so presence is real rather than inferred from a non-null value (MemoryCacheService.cs:62-64).

    One prefix rule, enforced by both stores. CachePrefixContract (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/CachePrefixContract.cs:8) is the argument contract of RemoveByPrefixAsync in one internal static class: the boundary character : (CachePrefixContract.cs:11) and EnsureBoundary, which throws ArgumentNullException for null and ArgumentException for a non-empty prefix that does not end with it (CachePrefixContract.cs:17-27). Both adapters call it first, MemoryCacheService at MemoryCacheService.cs:146 and HybridCacheService at HybridCacheService.cs:335. The in-process store could honor a mid-segment prefix, and that is exactly why it checks anyway: a prefix only the in-process store accepts would otherwise first fail in production on the two-level cache (MemoryCacheService.cs:137-141). On the write path the caching command decorator treats that exception as a bug in the command rather than a transient fault, logging it at Error and skipping the delayed retry, which would fail identically (MMCA.Common/Source/Core/MMCA.Common.Application/UseCases/Decorators/CachingCommandDecorator.cs:76-83).

    Prefix invalidation by generation token. CachePrefixGenerations (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/CachePrefixGenerations.cs:69) is how the two-level cache evicts a prefix without walking the keyspace. Every invalidation boundary of a key, the empty root and each prefix ending at a : (A:B:C yields "", A: and A:B:, CachePrefixGenerations.cs:240-259), carries a generation token, and SuffixAsync folds the non-empty tokens in force into the key the entry is stored under (CachePrefixGenerations.cs:149-202, CachePrefixGenerations.cs:264-272), after a | separator (CachePrefixGenerations.cs:79). A key whose boundaries were never invalidated keeps its plain shape (CachePrefixGenerations.cs:141-143). InvalidateAsync (CachePrefixGenerations.cs:217) replaces one token, so every entry written under the old token simply stops being addressed and expires on its own TTL (CachePrefixGenerations.cs:8-14): one Redis write whatever the size of the keyspace. The source records why this is not HybridCache.RemoveByTagAsync: in Microsoft.Extensions.Caching.Hybrid 10.11.0 each process reads a tag's invalidation timestamp once and never refreshes it, so a replica that has already met the tag never learns of a later invalidation (CachePrefixGenerations.cs:17-25); the Redis-tier HybridCacheCrossInstanceInvalidationTests (MMCA.Common/Tests/Core/MMCA.Common.Infrastructure.Redis.Tests/HybridCacheCrossInstanceInvalidationTests.cs:22) pins the property this class provides instead. Tokens are 64 random bits, hex encoded (CachePrefixGenerations.cs:276), not INCR counters, so concurrent invalidations need no atomicity (CachePrefixGenerations.cs:27-29). They live under {namespace}hcg:{prefix} (CachePrefixGenerations.cs:76, CachePrefixGenerations.cs:281), a segment disjoint from the cache entries, with no TTL, so Redis holds one short string per distinct invalidated prefix (CachePrefixGenerations.cs:43-45). Each process remembers the tokens it has seen as a RememberedToken (CachePrefixGenerations.cs:417), a private record struct of the token, the tick count it must be refreshed after, a monotonic version stamp and whether this process stored it by invalidating. A remembered token is reused without a read for one local cache duration, then still served while one background read per boundary refreshes it (CachePrefixGenerations.cs:175-183), for up to RetentionMultiplier = 10 local durations, five minutes at the default (CachePrefixGenerations.cs:81-86); concurrent readers of one boundary share a single in-flight read (CachePrefixGenerations.cs:107-108, CachePrefixGenerations.cs:291-297), and long-expired entries are swept once per 1024 inserts (CachePrefixGenerations.cs:92, CachePrefixGenerations.cs:394-401). The invalidating process adopts its new token locally before the Redis write, so it stops serving the prefix even if the write fails (CachePrefixGenerations.cs:234-237), and the version snapshot taken before any read means a read that began before that invalidation can never put the old token back (CachePrefixGenerations.cs:167-169, CachePrefixGenerations.cs:387-392). Another replica therefore sees an invalidation within one local duration plus one refresh round trip (CachePrefixGenerations.cs:37-46). The failure posture is spelled out too: a failed token read never fails the cache call, it answers with the last token this process knew or the empty baseline (CachePrefixGenerations.cs:357-370), and the baseline is deliberate, since the lockout flag, the failure counters and the idempotency records sit under boundaries nobody invalidates, so lockout and rate limits keep working on a cold replica during an outage; the cost, a cold replica addressing pre-invalidation entries of an invalidated prefix during a partial outage, is stated beside it (CachePrefixGenerations.cs:52-67), as is the matching caveat that a lost generation key brings back only the baseline, never an older non-baseline token (CachePrefixGenerations.cs:29-35). Without a multiplexer the tokens live in this process only (CachePrefixGenerations.cs:110-111), which is exact for a single-process host, and the first such invalidation logs one warning naming AddRedisCaching (CachePrefixGenerations.cs:224-231, CachePrefixGenerations.cs:409). That warn-once-versus-silent choice is a small but real [Rubric §13, Observability and Operability] decision: an invalidation that quietly reaches no other replica is exactly the failure mode that hides from dashboards. This is also why Cache:LocalCacheDuration, when set, must be at least one second: it bounds how long a token is reused, so zero would turn every cache call into a Redis read (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/CacheSettings.cs:42-47).

    The two-level cache. HybridCacheService (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/HybridCacheService.cs:55) puts an in-process L1 in front of the registered distributed L2 and lets the platform's HybridCache supply serialization, L1 promotion and stampede protection. It builds its own CachePrefixGenerations from the multiplexer, the namespace and the local duration (HybridCacheService.cs:167-171). Its structural decision is the disjoint keyspace: every key is written as {prefix}hc:{key} plus any generation suffix (HybridCacheService.cs:61, HybridCacheService.cs:440-449), so an entry can never meet a value another writer put on the same server, a host's own IDistributedCache use or the hcg: generation keys, in a format it cannot parse (HybridCacheService.cs:19-24). RemoveByPrefixAsync checks the boundary contract and replaces one generation token; nothing is scanned or deleted (HybridCacheService.cs:318-337). Reads are fail-soft: a fault is logged, answered as a miss, and the offending entry is dropped best-effort so the next write repopulates it (HybridCacheService.cs:183-202, HybridCacheService.cs:479-489). Two members bypass L1 entirely, and both share one options instance that disables the L1 read and the L1 write (SharedStoreReadOptions, HybridCacheService.cs:92-97), because both are values whose correctness depends on every replica seeing the same thing; the reasoning is a [Rubric §11, Security] point rather than a performance one. GetFromSharedStoreAsync overrides the interface default so a single-use record (an OAuth exchange code, a password-reset or email-confirmation token, the last accepted second-factor time step) consumed on one replica is a miss on every other replica at once rather than usable a second time for up to the local expiration (HybridCacheService.cs:35-39, HybridCacheService.cs:266-285); it stays fail-soft like GetAsync, and for such a record a miss is a refusal, the safe direction. The same path serves a counter read without an increment and the reads whose correctness depends on seeing a removal at once, the login lockout flag and the soft-deleted-user marker (HybridCacheService.cs:40-46). Its single-use callers are OAuthControllerBase (MMCA.Common/Source/Presentation/MMCA.Common.API/Controllers/OAuthControllerBase.cs:332), PasswordResetTokenService (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Auth/PasswordResetTokenService.cs:128), EmailConfirmationTokenService (.../Auth/EmailConfirmationTokenService.cs:95) and TwoFactorAuthenticator (.../Auth/TwoFactor/TwoFactorAuthenticator.cs:197); the others are LoginProtectionService for the lockout flag and the registration count (.../Auth/LoginProtectionService.cs:82, LoginProtectionService.cs:213) and SoftDeletedUserMiddleware (MMCA.Common/Source/Presentation/MMCA.Common.API/Middleware/SoftDeletedUserMiddleware.cs:95). That last record is also the one key outside the host's namespace: a CrossServiceCacheKeys key is qualified with the cross-service namespace every service of a deployment shares and carries no generation suffix, so the record Identity writes is the record every other service reads (HybridCacheService.cs:48-53, HybridCacheService.cs:442-445). IncrementAsync bypasses L1 on both legs (HybridCacheService.cs:362-383): a counter cached per replica would let one process read its own stale count and write it back, so a brute-force limiter could be held near its starting value indefinitely by a steady stream of attempts against a single replica. Its faults are deliberately not swallowed, unlike the reads, since a counter that silently reads zero resets the limit it exists to enforce (HybridCacheService.cs:357-360). TryGetAsync is overridden too (HybridCacheService.cs:224-249), because the interface default would report a value-type miss as found and HybridCache has no presence-reporting read: presence is read from whether HybridCache had to call the factory, which on a miss throws a KeyNotFoundException tagged with a private marker (HybridCacheService.cs:64, HybridCacheService.cs:420-425) that the method catches as "not found" (HybridCacheService.cs:239-242). A thrown sentinel rather than a flag the factory sets, because a concurrent read of the key joins the first caller's in-flight lookup and never runs its own factory, while the exception reaches every joined caller (HybridCacheService.cs:207-215). The probe carries its own PresenceProbeOptions (HybridCacheService.cs:106-109), whose flags no other call uses, since HybridCache joins only callers with identical flags and a GetOrCreateAsync in flight on the same key must never be handed that miss (HybridCacheService.cs:218-220); faults stay fail-soft as on GetAsync (HybridCacheService.cs:243-248). GetOrCreateAsync overrides the interface default with HybridCache's own implementation (HybridCacheService.cs:394-413). Replica staleness after an invalidation is bounded by the local expiration, the shorter of the entry's TTL and Cache:LocalCacheDuration (30 seconds by default, HybridCacheService.cs:71, HybridCacheService.cs:458-469), the same window in which another replica picks up a replaced generation token (HybridCacheService.cs:26-32), and the source names that as the accepted cost of the L1 hit rate.

    The key namespace and the TTL policy. CacheKeyPrefixOptions (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/CacheKeyPrefix.cs:30) binds the Cache configuration section (CacheKeyPrefix.cs:33) and carries two settings. KeyPrefix still defaults to empty (CacheKeyPrefix.cs:45), but empty does not mean "no prefix": it means take the framework's per-application default, and a host sets the value explicitly only to pin a keyspace two hosts of the same application must share (CacheKeyPrefix.cs:35-40). The reason is recorded on the property itself: it used to default to no prefix at all, so two applications sharing one Redis shared one keyspace for both cache entries and distributed locks, silently (CacheKeyPrefix.cs:41-44). CrossServiceKeyPrefix (CacheKeyPrefix.cs:55) names the keyspace of the cross-service records, defaulting to the token audience (Jwt:Audience), which every service accepting the same tokens shares and two applications do not (CacheKeyPrefix.cs:47-54). CacheKeyNamespace (CacheKeyPrefix.cs:59) is the internal applier. It keeps a None instance for the untouched case (CacheKeyPrefix.cs:65) and an options-taking From overload that tolerates an unregistered section (CacheKeyPrefix.cs:71-75), but the composition root calls the container-taking overload (CacheKeyPrefix.cs:85-100), which returns the configured prefix when a host set one (CacheKeyPrefix.cs:89-93) and otherwise builds {application namespace}: from ApplicationNamespace.Resolve (CacheKeyPrefix.cs:95-99). That resolver reads Application:Namespace, falls back to the host's application name, and falls back again to the literal app (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Configuration/ApplicationNamespace.cs:60-74, keys at ApplicationNamespace.cs:38 and ApplicationNamespace.cs:41), so the resolved prefix is never empty and isolation is automatic rather than opt-in. CrossServiceFrom resolves the second namespace the same way: configured value, then the sanitized audience, then this host's own namespace (CacheKeyPrefix.cs:116-130). Qualify (CacheKeyPrefix.cs:133-134) prepends a prefix. The same namespace instance is handed to the Redis distributed lock registered beside the cache (DependencyInjection.Caching.cs:116-117) and becomes the output-cache store's InstanceName (DependencyInjection.Caching.cs:70-77), so one application's cache entries, generation keys, lock keys and output-cache entries carry one prefix. The two-level cache applies it inside the adapter rather than through RedisCacheOptions.InstanceName; the rationale in the source (CacheKeyPrefix.cs:16-24) is precise, since InstanceName is prepended by IDistributedCache below this abstraction, where the generation keys written directly to Redis would not carry it, so two applications on one server would share invalidation tokens while keeping separate entries. MemoryCacheService ignores prefixes entirely because a per-process keyspace is private by construction (CacheKeyPrefix.cs:25-28). TTL policy is centralized the same way: CacheOptions (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/CacheOptions.cs:15) exposes a deliberately short 30-second DefaultDuration (CacheOptions.cs:23) as a bare TimeSpan, so implementations that do not speak DistributedCacheEntryOptions still default to the same policy, plus DefaultExpiration (CacheOptions.cs:28) and Create(TimeSpan?) (CacheOptions.cs:38) for callers that do. Those values are the hard-coded framework defaults and the single source of truth for the configurable path as well: CacheSettings defaults DefaultDuration to CacheOptions.DefaultDuration (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/CacheSettings.cs:34), so a host that configures nothing behaves exactly as it did before that section existed. The short default is a staleness guard: caching is opt-in and conservative, and a read earns a longer life only by asking for one. One policy object with many call sites is the [Rubric §12, Performance & Scalability] habit this framework applies everywhere.

    One hook for every Redis connection. IRedisConfigurationOptionsConfigurator (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/IRedisConfigurationOptionsConfigurator.cs:30) has a single member, Configure(ConfigurationOptions) (IRedisConfigurationOptionsConfigurator.cs:34), that adjusts the StackExchange.Redis options of a connection before it connects: a token credential, a client certificate, a timeout (IRedisConfigurationOptionsConfigurator.cs:5-9). It reaches every Redis connection the framework opens, the Redis client and the distributed cache over it, the output-cache store, the SignalR backplane and the PING health check's own connection, each running every registered configurator once on its own options instance parsed from the connection string (IRedisConfigurationOptionsConfigurator.cs:10-15). It runs synchronously, may run more than once per process, and throwing from it fails that connection, which is the place to reject a connection string it cannot serve (IRedisConfigurationOptionsConfigurator.cs:25-29). With none registered every connection is made from the connection string exactly as before (IRedisConfigurationOptionsConfigurator.cs:20-23).     How it fires at runtime. Nothing above runs unless a use case opts in, via two marker interfaces consumed by the CQRS decorator pipeline (ViewAs then FeatureGate then Authorization then Logging then Caching then Validating then Timeout then Transactional then handler for commands, and the same chain without ViewAs and Transactional for queries; the order is documented at MMCA.Common/Source/Core/MMCA.Common.Application/DependencyInjection.cs:77-101, Authorization sits outside Caching so a denied request neither reads nor populates the cache (DependencyInjection.cs:110-112), and the two caching decorators are registered at DependencyInjection.cs:155 and DependencyInjection.cs:164, taught in Group 5). On the read path, CachingQueryDecorator<TQuery, TResult> tests the query for IQueryCacheable and passes straight through when it is absent (MMCA.Common/Source/Core/MMCA.Common.Application/UseCases/Decorators/CachingQueryDecorator.cs:64-65). When present it scopes the key to the target user for a caller-scoped query through UserCacheKey and then to the resolved tenant through TenantCacheKey (CachingQueryDecorator.cs:58-59, so two tenants or two users can never share an entry), takes a lock-free fast path on a hit (CachingQueryDecorator.cs:74-79), and on a miss acquires a per-key stripe from the process-wide QueryCacheKeyLocks (CachingQueryDecorator.cs:185), re-checks (CachingQueryDecorator.cs:100-105), records the miss on CqrsMetrics exactly once (CachingQueryDecorator.cs:113), and only then runs the inner handler. That stripe wait is itself bounded by Cache:PopulateLockTimeout (CachingQueryDecorator.cs:84-85, default Timeout.InfiniteTimeSpan on CacheSettings at CacheSettings.cs:62): when a finite budget elapses the waiter logs, counts a miss, and runs the query itself uncached rather than queueing behind a pathologically slow populate (CachingQueryDecorator.cs:87-96, CachingQueryDecorator.cs:179-198). The lock table is a fixed-width KeyedSemaphoreStripe (MMCA.Common/Source/Core/MMCA.Common.Shared/Concurrency/KeyedSemaphoreStripe.cs:22, 256 stripes by default at KeyedSemaphoreStripe.cs:25), which bounds memory no matter how many parameterized cache keys the process sees. Every cache call is fail-open: a read fault is logged and treated as a miss (CachingQueryDecorator.cs:208-223) and a populate fault returns the result uncached (CachingQueryDecorator.cs:120-131), so a cache outage degrades reads instead of turning cacheable queries into 500s, which is the [Rubric §29, Resilience] posture in miniature. Results are stored only when they are not a failed Result (CachingQueryDecorator.cs:118). On the write path, CachingCommandDecorator<TCommand, TResult> runs the inner handler first and then, only if the command implements ICacheInvalidating, the prefix is non-blank (a blank prefix is the opt-out, and the guard is load-bearing since an empty prefix would evict the whole cache) and the result is not a failure, invalidates the tenant-scoped prefix with CancellationToken.None (.../Decorators/CachingCommandDecorator.cs:59-75); a prefix that breaks the boundary contract is logged at Error and not retried (CachingCommandDecorator.cs:76-83), and any other fault is logged without failing the committed command (CachingCommandDecorator.cs:84-89). It then schedules a second invalidation five seconds later (CachingCommandDecorator.cs:45, CachingCommandDecorator.cs:97, CachingCommandDecorator.cs:107-112) to catch a read that began before the commit and repopulated the entry with pre-write state. Because the Caching decorator sits outside the Transactional one, eviction runs after the transaction committed: against persisted state, never in-flight state, and never at all when the write failed.

    Two tiers, not one. These twelve types are only Tier 1 of the caching story that ADR-026 records. Tier 2 is a separate HTTP output-cache edge: MMCA.Common.API always runs app.UseOutputCache() as a named step in the shared middleware pipeline (MMCA.Common/Source/Presentation/MMCA.Common.API/Startup/Pipeline/MiddlewarePipelineBuilder.cs:139-141, see MiddlewarePipelineBuilder) but ships no policies, so each host opts in with its own output-cache configuration. The read-heavy public services declare real cacheable policies through OutputCacheOptionsExtensions and its AddPublicEndpointPolicy (MMCA.Common/Source/Presentation/MMCA.Common.API/Caching/OutputCacheOptionsExtensions.cs:20), backed by PublicEndpointOutputCachePolicy (.../Caching/PublicEndpointOutputCachePolicy.cs:35), which caches GET and HEAD regardless of an Authorization header (PublicEndpointOutputCachePolicy.cs:110, ADR-040), and evict it across replicas through the OutputCacheEvictionRequested integration event and its OutputCacheEvictionHandler. Both adopters back that edge with Redis by setting UseRedisOutputCaching (MMCA.ADC/Source/Services/MMCA.ADC.Conference.Service/Program.cs:129; MMCA.Store/Source/Services/MMCA.Store.Catalog.Service/Program.cs:53), which the composed host turns into AddRedisOutputCaching() (ServiceHostBuilderExtensions.cs:92-95), so the two tiers ride the same Redis instance from opposite ends: Tier 1 through HybridCache, Tier 2 through the output-cache store. There is no third tier on the client: ADR-026 records that the optional client-side read cache was removed in MMCA.Common v1.301.0, so a UI service read in EntityServiceBase<TEntityDTO, TIdentifierType> is a plain GET through the retry pipeline, SendGetAsync<T> (MMCA.Common/Source/Presentation/MMCA.Common.UI/Services/Api/EntityServiceBase.cs:226), and any client-side memoization is an application decision that belongs to Group 15, Common UI Framework. Tier 2 belongs to Group 12, API Hosting; both are named here only so you do not confuse them with Tier 1 when you meet [OutputCache] on a controller.

    Adoption reality, so you read the code with the right expectations. Prefix invalidation against Redis is live in the deployed services: the composed host registers the Aspire Redis integration through RedisCachingExtensions, whose AddRedisCaching() brings the IConnectionMultiplexer the generation tokens live on along with the distributed cache, and then the hybrid substrate through the framework's connection-string guard (ServiceHostBuilderExtensions.cs:91-97). Write-side adoption is broad: about forty types across ADC's Conference, Engagement and Identity modules implement ICacheInvalidating, for example MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.Application/Categories/UseCases/UpdateCategoryItem/UpdateCategoryItemCommand.cs:18 with its aggregate-scoped CachePrefix at :21. Read-side adoption is not: no ADC query implements IQueryCacheable. Its one hot public read, GetNowNextQuery, opts out on purpose and relies on a Redis-backed output-cache policy instead (MMCA.ADC/Source/Modules/Conference/MMCA.ADC.Conference.Application/Sessions/UseCases/NowNext/GetNowNextQuery.cs:10-12), so the write-side query-cache invalidation currently replaces tokens for prefixes no ADC query wrote under. The substrate's other production consumers are not decorators at all: LoginProtectionService (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Auth/LoginProtectionService.cs:38) injects ICacheService for its brute-force and rate-limit counters (LoginProtectionService.cs:140, LoginProtectionService.cs:242), reading the lockout flag and the registration count back through GetFromSharedStoreAsync (LoginProtectionService.cs:82, LoginProtectionService.cs:213), covered in Group 8, Authentication and Authorization, the password-reset and email-confirmation token services, which count requests through IncrementAsync (PasswordResetTokenService.cs:68, EmailConfirmationTokenService.cs:58) and redeem their single-use records through GetFromSharedStoreAsync as described above, and IdempotencyFilter resolves it per request to store and replay responses (MMCA.Common/Source/Presentation/MMCA.Common.API/Idempotency/IdempotencyFilter.cs:141). The key namespace is live in both deployed applications, and the two pin it differently. ADC's services share one keyspace: Cache:KeyPrefix is adc: alongside Application:Namespace adc, pinned to exactly what the namespace resolves to so a host rename cannot move it (MMCA.ADC/Source/Services/MMCA.ADC.Conference.Service/appsettings.json:53-62, rationale at :45-52 and :56-59). Store goes the other way: its services share Application:Namespace store for the broker topics but keep separate Redis keyspaces, so Catalog pins store-catalog: (MMCA.Store/Source/Services/MMCA.Store.Catalog.Service/appsettings.json:39-44, rationale at :29-38), a value the per-application default would not have produced. CacheKeyNamespace.None is therefore only the constructor fallback the adapter uses when no namespace is passed, not the deployed state. Two honest caveats round this out. The stampede lock is per process (CachingQueryDecorator.cs:239-245): across replicas over a shared Redis you get at most one handler execution per replica, not one cluster-wide, which is deliberate (a distributed lock is not attempted) and harmless because the duplicated writes carry equal content. And GetOrCreateAsync has no first-party caller outside tests today: it is a published extension point plus the member HybridCacheService overrides.

    What the cache is not. This is a request-result read-through cache for query handlers plus a counter store and an idempotency record store, not a session store and not a write-behind buffer; cross-source consistency in this codebase is the outbox's job (ADR-003, ADR-006), not the cache's. The short default TTL and the two failure-skipping rules (never cache a failed result, never invalidate on a failed command) mean the layer errs toward correctness over hit rate, which is the right default for an opt-in cache bolted onto a database-per-service system. Everything in the bound Cache section is fail-open by design (CacheSettings.cs:12-17): no value there can turn a cache outage or a slow populate into an error. The unit tests for these types, including the Redis-backed HybridCacheServiceRedisTests and HybridCacheCrossInstanceInvalidationTests, are catalogued in Group 27, Testing and Quality Infrastructure.

    MMCA.Common.Infrastructure · MMCA.Common.Infrastructure.Caching · MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/CachePrefixGenerations.cs:69 · Level 2 · class (internal sealed partial)

    • What it is: prefix invalidation for HybridCacheService without walking the keyspace. Every invalidation boundary of a key (the empty root, then each prefix ending at :) carries a generation token, and the tokens in force are folded into the key the entry is stored under. Invalidating a prefix replaces its token, so every entry written under the old token stops being addressed and expires on its own TTL (CachePrefixGenerations.cs:8-14).

    • Depends on: CacheKeyNamespace (the generation keys share the entries' namespace) and RememberedToken (nested). Externals: StackExchange.Redis.IConnectionMultiplexer (optional), ConcurrentDictionary, RandomNumberGenerator, ILogger (BCL/NuGet).

    • Concept introduced, generation tokens as O(1) invalidation. [Rubric §12, Performance & Scalability] assesses whether cost stays flat as data grows. A SCAN-and-delete invalidation costs time proportional to the keyspace; here an invalidation is one Redis write whatever the keyspace size (HybridCacheService.cs:26-32). The remarks record three design choices:

      • Why not HybridCache.RemoveByTagAsync (CachePrefixGenerations.cs:17-24): in Microsoft.Extensions.Caching.Hybrid 10.11.0 each process reads a tag's invalidation timestamp once and keeps it for its lifetime, so another replica that already saw the tag never learns of a later invalidation. HybridCacheCrossInstanceInvalidationTests pins the property this class provides instead.
      • Tokens, not counters (:26-34): a fresh random value rather than an INCR, so concurrent invalidations need no atomicity and a lost generation key can never come back at an older non-baseline token. It can come back at the baseline: a lost hcg: key re-addresses entries written before that prefix's first invalidation until their TTL.
      • Staleness bound (:36-46): a token is reused without a read for one local cache duration (Cache:LocalCacheDuration, 30 seconds by default), then served while one background read refreshes it, so another replica's invalidation is seen within one local duration plus one round trip.

      [Rubric §29, Resilience & Business Continuity]: a failed token read never fails the cache call. It answers with the last token this process knew or, for a boundary it never saw, the empty baseline (CachePrefixGenerations.cs:51-65). The baseline is chosen deliberately over a random token: the lockout flag, failure counters and registration throttles live under boundaries nobody invalidates, so the baseline keeps them in the keyspace every replica shares and rate limits keep working on a cold replica during an outage, where a random fallback would fail open. The remarks state the cost plainly: in a partial outage a cold replica can address pre-invalidation entries of a prefix that was invalidated, until their TTL.

The remarks (:434-438) say why cross-service keys skip the suffix: generation tokens are per namespace, so a prefix wipe in one service would otherwise move its copy away from the others'.

It is fail-soft (HybridCacheService.cs:175-182): any exception that is not OperationCanceledException is logged at warning and answered as a miss (HybridCacheService.cs:196-201), and the offending entry is dropped best-effort through SelfHealAsync so the next write repopulates it.

HybridCache has no presence-reporting read, so presence is read from whether it had to call the factory. The factory is static _ => throw CacheMiss(): a hit never calls it, and a miss throws a KeyNotFoundException that catch ... when (ex.Data.Contains(MissMarker)) turns into (false, default) (HybridCacheService.cs:239-242). CacheMiss() (HybridCacheService.cs:420-425) builds the tagged exception, so a KeyNotFoundException raised anywhere else cannot be mistaken for a miss. Other faults are fail-soft like GetAsync (HybridCacheService.cs:243-248).

It is fail-soft exactly like GetAsync (HybridCacheService.cs:279-284); for a single-use record a miss is a refusal, which is the safe direction (HybridCacheService.cs:260-264).

      • RemoveByPrefixAsync (HybridCacheService.cs:333-337), a non-async method: it runs CachePrefixContract.EnsureBoundary (:335) and returns _generations.InvalidateAsync(prefix, ...) directly (:336). Nothing is scanned or deleted: the replaced token stops every entry under the prefix being addressed, here at once and on other replicas within Cache:LocalCacheDuration, and the orphaned entries expire on their own TTL (HybridCacheService.cs:321-325). Without a multiplexer the invalidation reaches this process only, warned once (:327-330).
      • IncrementAsync (HybridCacheService.cs:362-383), a read-modify-write deliberately not routed through this class's own GetAsync / SetAsync because both legs must bypass L1 (:366-371 reads with SharedStoreReadOptions, :375-380 writes with the two disable flags). The reason (HybridCacheService.cs:349-355) is the sharpest argument in this group: a counter is the one value whose correctness depends on every replica seeing the same number, so an L1 copy would let a process read its own stale count and write it back, and a brute-force counter could then be held near its starting value indefinitely by a steady stream of attempts against one replica. That is a security control silently weakened by a cache optimization, so [Rubric §11, Security] is the category that decided this member, not §12. Faults are also not swallowed here, unlike GetAsync (HybridCacheService.cs:358-359): a counter that silently reads as zero would reset the limit it exists to enforce.
      • GetOrCreateAsync<T> (HybridCacheService.cs:394-413), an override of the interface default that hands the work to HybridCache's own primitive, which folds the double-check and the stampede protection into one call and additionally deduplicates concurrent callers before they reach L2. The factory is passed as state rather than captured (HybridCacheService.cs:404-412), so the delegate stays static and no closure is allocated per call.
      • WriteOptions (HybridCacheService.cs:458-469) and SelfHealAsync (HybridCacheService.cs:479-489), the private helpers. WriteOptions is where both dials meet: ttl = expiration ?? _settings.DefaultDuration (:460), localCeiling = _settings.LocalCacheDuration ?? LocalCacheDefault (:461), and LocalCacheExpiration = ttl < localCeiling ? ttl : localCeiling (:466), so a long-lived entry does not sit in another replica's memory for its whole TTL after an invalidation that process never saw.
    • Why it's built this way: ADR-077 is the record. It is the only cache service over a shared store: AddCaching's fallback factory throws, naming the call, when a non-memory IDistributedCache is registered without AddCommonHybridCache, because silently falling back to the in-process cache would make single-use records, counters and the lockout flag per-replica (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/DependencyInjection.Caching.cs:81-93). The registration deliberately uses RemoveAll + Add rather than TryAdd so it wins in either call order (DependencyInjection.Caching.cs:186-189), with the honest warning that RemoveAll does not distinguish the framework's registration from a host's own custom ICacheService (DependencyInjection.Caching.cs:150-153). Generation tokens replace HybridCache.RemoveByTagAsync for the cross-replica reason recorded on CachePrefixGenerations. [Rubric §29, Resilience] shows up in the fail-soft read: the cache is an optimization, never the system of record, so an unreadable entry costs a database round trip rather than a failed request.
    • Where it's used: registered only by AddCommonHybridCache (MMCA.Common/Source/Core/MMCA.Common.Infrastructure/DependencyInjection.Caching.cs:162-208), which passes the host namespace (:194) and CacheKeyNamespace.CrossServiceFrom(sp) (:204). AddCommonHybridCacheWhenRedisConfigured calls it only when the redis connection string is configured (DependencyInjection.Caching.cs:226-238), and the composed service-host start-up calls that guard (MMCA.Common/Source/Hosting/MMCA.Common.ServiceHost/ServiceHostBuilderExtensions.cs:97). Everything downstream still talks to ICacheService and is unaware. Covered by HybridCacheServiceTests, the registration semantics by AddCommonHybridCacheTests, and against a real Redis by HybridCacheServiceRedisTests and HybridCacheCrossInstanceInvalidationTests (cross-replica invalidation).
    • Caveats / not-in-source: replica staleness after a removal or an invalidation is bounded by the local expiration (30 seconds by default, Cache:LocalCacheDuration to change it), not by the call itself, because only the calling process's L1 and remembered tokens change at once (HybridCacheService.cs:28-32). That is the same order as the delayed re-invalidation CachingCommandDecorator<TCommand, TResult> already performs. It does not apply to counters or to reads made through GetFromSharedStoreAsync, which never touch L1; a caller that reads a single-use record through plain GetAsync instead still gets the L1 window, so the protection depends on the call site choosing the right member. TryGetAsync reports a miss through a caught KeyNotFoundException, so it is the correctness path for value types, not the hot path. Because the keyspace is disjoint, a host that switches substrate starts cold: entries another writer put in the server are invisible here and age out on their own TTL, which ADR-077 records as a cost rather than a correctness problem (077-hybridcache-substrate.md:65-68).

    MemoryCacheService

    MMCA.Common.Infrastructure · MMCA.Common.Infrastructure.Caching · MMCA.Common/Source/Core/MMCA.Common.Infrastructure/Caching/MemoryCacheService.cs:19 · Level 5 · class (internal sealed)

    • What it is: the in-process implementation of ICacheService, backed by IMemoryCache. Because IMemoryCache exposes no way to enumerate its keys, this service maintains its own ConcurrentDictionary<string, object> tracking table so it can honor RemoveByPrefixAsync, the one capability the BCL memory cache lacks. The cache and that table are two structures that have to agree, so every mutation of a key runs under that key's lock stripe (MemoryCacheService.cs:9-18).
    • Depends on: IMemoryCache / MemoryCacheEntryOptions and ConcurrentDictionary<TKey, TValue> (both BCL), KeyedSemaphoreStripe from MMCA.Common.Shared.Concurrency (MemoryCacheService.cs:5, :45) for the per-key mutual exclusion, CachePrefixContract for the prefix guard, and the optional CacheSettings (MemoryCacheService.cs:19, :25) for the default TTL. Implements ICacheService and overrides TryGetAsync but none of the other default members, so it inherits the non-atomic IncrementAsync, the stripe-plus-double-check GetOrCreateAsync and the GetAsync-backed GetFromSharedStoreAsync (exact here, since there is no shared store beyond this process). It takes no CacheKeyNamespace.
    • Concept introduced, a shadow index to back-fill a missing API. [Rubric §12, Performance & Scalability] assesses cheap reads and sound invalidation; an in-process cache is the lowest-latency option available but is not shared across instances, so it is correct for a single-process monolith or for genuinely per-instance data and wrong for anything else. The teachable mechanic is the shadow index: IMemoryCache is a black box with no key listing, so the service mirrors every live key into _keys and keeps that mirror honest with a post-eviction callback, so an entry that expires or is dropped under memory pressure prunes its own tracking record instead of leaking. It presents the identical ICacheService surface as HybridCacheService, including the same prefix boundary rule, so swapping backends changes nothing for callers. Second concept, an invariant that write ordering cannot buy you. [Rubric §15, Best Practices & Code Quality] assesses everyday craftsmanship, including whether comments explain why rather than what. The SetAsync remarks (MemoryCacheService.cs:67-75) are the worked example: with two structures to update, track-then-write lets a concurrent removal drop the tracking record between the two steps, and write-then-track lets a removal run entirely between them; both leave a live entry nothing can find. Neither order closes the window, so the class buys the invariant with mutual exclusion instead, and says so in the code rather than leaving the next reader to rediscover it.

It exists so a post-eviction callback, which necessarily runs after its own entry may already have been superseded, can remove only its OWN record and never the record of a newer live entry. Ordinal comparison matches the ordinal prefix test below.

    • Why it's built this way: a parallel key index is the only way to give IMemoryCache a prefix-removal capability without replacing it, and the two guards on the callback (skip Replaced, and match the token) are what keep that index from drifting in either direction: a naive key set would accumulate phantom keys as entries expired, while a naive callback would delete records for entries that are still live. The stripe then covers what neither guard can, the window between the two writes that any single-threaded reading of the code hides. Striping rather than a semaphore per key is a bounded-memory choice made once in KeyedSemaphoreStripe and reused here. Taking CacheSettings gives both stores one TTL policy, so a caller's omitted expiration means the same thing whichever adapter the host resolved. The class is internal sealed because it is only ever resolved through the ICacheService registration.

AddCaching() always calls AddMemoryCache() first (DependencyInjection.Caching.cs:32). The factory only returns this service when no distributed cache, or only the in-memory MemoryDistributedCache, is registered; a real distributed cache without AddCommonHybridCache makes it throw instead (DependencyInjection.Caching.cs:86-93). A host with no Redis therefore behaves as a single-instance cached monolith with the full interface intact. Consumed through the interface by both CQRS caching decorators, LoginProtectionService, PasswordResetTokenService, SoftDeletedUserCache and IdempotencyFilter. Unit-tested by MemoryCacheServiceTests, which pins the default-TTL behavior (MMCA.Common/Tests/Core/MMCA.Common.Infrastructure.Tests/Caching/MemoryCacheServiceTests.cs:26), the value-type GetOrCreateAsync miss that depends on TryGetAsync (MemoryCacheServiceTests.cs:40), and the concurrency behavior deterministically rather than racing for it: the test takes the key's own stripe first, then asserts that a SetAsync and a RemoveByPrefixAsync both park on it (MemoryCacheServiceTests.cs:246) and that RemoveAsync waits on the same stripe as SetAsync (MemoryCacheServiceTests.cs:279).
    • Caveats / not-in-source: the cache is per-process, so two replicas hold independent and potentially divergent copies until each entry's TTL or an explicit eviction reconciles them. That is why HybridCacheService exists for scaled-out deployments, and why ADR-026 treats per-replica memory mode as a trade-off rather than a supported multi-replica posture. _keys is unbounded in the sense that only eviction prunes it, so a cache key embedding a high-cardinality value grows the table alongside the cache itself. Two limits of the locking are worth knowing: the stripe is per service instance, so the invariant holds for the singleton the container registers and not across two hand-constructed instances sharing one IMemoryCache; and RemoveMatchingAsync works from a snapshot, so a key written after the snapshot is taken is simply not a candidate for that call.
